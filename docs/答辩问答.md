## M1：装甲板角点几何（`ArmorDetector.cpp` / `ArmorDetector.hpp`）

### Q1. 灯条为什么用「上下两个端点」描述，不用 `cv::RotatedRect`？

`RotatedRect::angle` 的语义在 OpenCV 4.5 变了：3.x 取值区间 `[-90, 0)`，
4.5 改成 `[0, 90)`，符号含义也跟着变。靠 `angle` 判断"哪根朝上"会踩坑。

两个端点自身就带方向信息，没有歧义，也不依赖 OpenCV 版本。
约定 `top.y <= bottom.y`（top 是画面里在上面的那一端）。

### Q2. `quadSignedArea` 为什么是正数才代表顺序正确？

鞋带公式算的是有向面积。**图像坐标 y 轴向下**，所以
"左上→右上→右下→左下"在屏幕上走的其实是顺时针，鞋带公式给出正值。
如果得到负值，说明这四点走的是逆时针，即左右被镜像了。

这个判据在后面 PnP 里是致命的：角点顺序一镜像，解出来的位姿也跟着镜像，
现象是"车在动但角度反的"。

### Q3. `buildCorners` 里那道"面积为负就交换 c[1]/c[3]"的防御，它真的会触发吗？

**不会。它是死代码，我实测过。**

在"按 `center.x` 定序"和"约定 `top.y <= bottom.y`"这两条同时成立时，
生成的顺序必然给出正面积。我用 5000 万组任意倾角的随机灯条采样，
负面积出现 **0 次**，最小面积 6e-4（趋近 0 但不变负）。

代码里保留了它，并在注释里写明不可达。理由：它只花一次乘加，
且如果将来有人把定序依据从 `center.x` 改成 `top.x`，它会立刻开始干活。

**这个问题的答法是重点**：能说出"它是死代码、我做过实验证明、我为什么还留着"，
比说"这是一道防御"强得多。后者会被继续追问"那你怎么验证它生效过？"

### Q4. 那退化四边形（四点接近共线）怎么办？

那道防御**挡不住**这个。四点共线时面积趋近 0 而不是变负，
所以负面积检查不会触发。

退化四边形喂给 `warpPerspective` 会出 NaN，必须由调用方
按「面积下限」主动丢弃（这是一个正的阈值判断，不是符号判断）。
这一步在 M3 的 `detect()` 里做——`quadSignedArea` 已经备好了。

### Q5. `classifySize` 为什么用「灯条中心距 / 灯条长度」，不用角点外接矩形的长宽比？

外接矩形在装甲板倾斜时会变大，于是长宽比被压低，
**大装甲板会被误判成小装甲板**——而且是静默的，不报错。

中心距/灯条长度是**无量纲比值**：分辨率翻倍、距离变远，分子分母同比例变化，
比值不变。所以这个判据不需要随画面大小调参。

### Q6. 分界值 3.0 是怎么定的？

按物理尺寸算：小装甲板 135×57mm → 中心距/灯条长 ≈ 2.37；
大装甲板 230×57mm → ≈ 4.04。
取几何平均 √(2.37×4.04) ≈ 3.09，圆整到 **3.0**。

语义是"**≥** 分界即大板"，`>=` 而不是 `>`。
这个边界有单独的测试用例钉住——不然把 `>=` 写成 `>` 也没人发现。

### Q7. 五条配对判据里哪条最可靠？为什么？

**判据 4「间距比」**（灯条中心距 / 平均灯条长度，落在 [1.2, 6.0]）。

理由同 Q5：量纲相消。灯条长度本身就随距离缩放，
所以这个比值对**分辨率和距离都不敏感**，不用为不同分辨率重新调参。

其余四条：长度比 1.8（抗光照不均导致的断条）、
y 中心差 0.6（抗透视）、倾角差 15°（抗倾斜）、左右定序（保证契约）。

### Q8. `pairLightBars` 是 O(n²)，为什么不优化？

灯条数量通常个位数到十几根，`n < 30` 时暴力枚举的开销可以忽略。
换来的是**每条判据都能单独调试、单独注释、单独测**。

真要优化，也不该在这里——瓶颈在灯条提取的形态学运算和数字分类上。
先测再优化，别凭感觉优化。

### Q9. 三根等距灯条为什么会配出 3 对？

因为本函数只做「这两根灯条能不能构成一块板」的**局部**判断，不做全局去重。

三根灯条 左/中/右：左中、中右、左右，三对在局部都合法。
所以后面**必须做 NMS**，否则 `armor_count` 会虚高，
而且 `detections.front()` 可能选到歪框。

这条已经写成断言（`pairLightBars(three).size() == 3`）钉在测试里——
它不是 bug，是**已知行为**，用它提醒自己 NMS 不能省。

### Q10. 你怎么知道这些测试是有效的？（杀手锏）

**变异测试。** 我人工往实现里植入 15 个错误，逐个跑测试：

```
抓住 15 / 逃逸 0 / 共 15
```

包括：删掉五条判据中的任意一条、角点顺序填错、`>=` 改成 `>`、
倾角公式换成 `atan2(dy, dx)`、鞋带公式少乘 0.5、符号取反。

**第一轮跑出来是 5 个逃逸**，也就是说测试对它们完全是盲的。补完之后才是 15/15。
单看"3/3 通过"是没意义的——**一个永远为真的断言和一个有效的断言，输出一模一样**。

（这也是为什么作业提交时只交结果：自检脚本不提交，但开发时必须有。）

### Q11. 为什么专门测"两根退化灯条中心重合"？

因为 **NaN 与任何数比较都是 `false`**——既不大于也不小于。

两根长度都为 0 的灯条、且中心重合时：
长度比 `0/0 = NaN`、间距比 `0/0 = NaN`，
五条判据的 `if (x > 上限) continue;` 全部不成立，于是**全部放行**，
配出一块四个角点全是假的"装甲板"，一路传到 PnP 才爆炸。

这个洞很有意思：只要两根退化灯条**不重合**，间距比会算成 `+inf`，
反而被 `inf > 6.0` 挡下了。所以只放一根退化灯条是测不出来的。

实现上的修法是：在算任何比值**之前**，先检查两根灯条各自的长度是否 > 0，
而不是检查它们的**平均值**是否 > 0——
一根 0 一根 60 时平均值是 30，保护根本不触发。
