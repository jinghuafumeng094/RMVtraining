# 零、先看清楚这几件事在整个链路里的位置

任务书要求的完整链路是：

```
相机取流 → 图像预处理 → 灯条/装甲板检测 → 数字识别与目标筛选
        → PnP位姿解算 → EKF跟踪 → 弹道补偿 → 输出yaw/pitch → 串口发送
```

其中「灯条/装甲板检测」这一步，对应的就是函数 `armor_detect`（装甲板识别，25 分）。

`armor_detect` 内部又分 7 小步：

| 步 | 干什么 | 属于 | 状态 |
|---|---|---|---|
| ① | 按颜色做掩膜，只留敌方灯条 | 需要图像 | 等去队里拍整图 |
| ② | 从掩膜里找出每根灯条，转成"上下两个端点" | 需要图像 | 等去队里拍整图 |
| **③** | **把两根灯条配对成一块装甲板** | **M1** | **已完成** |
| **④** | **由一对灯条生成装甲板的四个角点** | **M1** | **已完成** |
| **⑤** | **判断这块板是大装甲板还是小装甲板** | **M1** | **已完成** |
| **⑥** | **把装甲板中间那块数字抠出来，识别是几号** | **M4 + M5** | **已完成** |
| ⑦ | 排序 + 去重（NMS），挑出最该打的那块 | 需要图像 | 等去队里拍整图 |

**M1 = ③④⑤，纯几何，不碰像素。**

这是刻意的：只要输入输出都是点，就可以用**手写构造的点**来测试，
不需要相机、不需要图片、不需要等去队里拍照。

**M4 + M5 = ⑥ 的后半段。** 它比 M1 多做了一件事：**依赖图像**，
但依赖的是**已经到手的数字数据集**，不是还没拍的整图。
所以它也是"现在就能做完并验证"的 —— 前提是补丁抠得出来，
而抠补丁只需要一张真实帧来核对（见 5.1）。

现在还剩 ①②⑦（都要整图）和标定、PnP、EKF。
**M1 + M4/M5 之后，`armor_detect` 只剩"把它们串起来"，不再有需要现场调参才能定的部分。**

# 一、M1 的文件：三个文件分别是什么

## 1.1 `student/include/ArmorDetector.hpp` —— 接口

**内容**：三个类型的定义（`LightBar`、`PairCriteria`、常量 `kGapRatioSplit`）和四个函数的**声明**。

**目的**：告诉别人"这套东西能干什么、怎么调用"。

**解决什么问题**：`armor_detect` 有 25 分，逻辑很多。如果全塞在 `StudentTasks.cpp` 一个文件里：
- 写测试没法链接（`StudentTasks.cpp` 里有匿名命名空间的相机全局变量）
- 后面要做 HOG+SVM 数字分类，训练程序和推理程序会各写一份特征代码，**训练 99%、现场 30%** 的经典事故

所以把管线单独拆出来。

**如何解决**：头文件只放"接口"（长什么样），`.cpp` 放"实现"（怎么做的）。
好处是改实现不用重新编译所有包含它的文件 —— 这叫"编译防火墙"。

**为什么不 include OpenCV 的 imgproc**：因为**这个头文件**里的东西不处理像素。
只 include `<opencv2/core.hpp>`（提供 `cv::Point2f`、`cv::norm`、`cv::Mat`），
这本身就是一个信号：接口层不该出现和图像处理有关的东西。

（实现文件 `ArmorDetector.cpp` 后来确实 include 了 `imgproc` ——
因为 `extractDigitPatch` 要用 `warpPerspective`/`resize`/`threshold`。
但那是**实现**的事，接口层没有跟着变脏。这个区分是有意的：
调用方只需要知道"给四个角点，还我一张 20×28 的补丁"，不需要知道里面做了几次变换。）

## 1.2 `student/src/ArmorDetector.cpp` —— 实现

**内容**：上面那些函数的具体实现，加一个只在内部用的辅助函数 `angleDifferenceDegrees`。

**目的**：把几何计算写对。

**解决什么问题**：这一层要解决的是"两个数字算错就全盘皆错"的问题：

| 问题 | 算错的后果 |
|---|---|
| 角点顺序 | PnP 解出的位姿镜像，车看着在动但角度是反的 |
| 大小板分类 | 用错三维尺寸，距离全错 |
| 灯条配对 | 配出一堆假板，`armor_count` 虚高 |
| 除零 | 出 NaN，一路传到 EKF 才炸 |

**如何解决**：
- 所有判据改成**无量纲比值**（分子分母同量纲，相除后消掉），这样与分辨率、与远近都无关，一套参数通吃
- 每个除法之前先挡退化输入
- 角点顺序不靠调用方自觉，函数内部自己按客观量（`center().x`）定序

## 1.3 `tests/test_armor_detect.cpp` —— 验证

**内容**：一个 `int main()`，用 `assert` 逐条断言上面那些函数的性质。

**目的**：证明实现是对的 —— 而且是**用能失败的检查**来证明，不是"跑一遍没崩"。

**解决什么问题**："编译通过 + 跑一遍没报错"根本不能说明任何事。
一个永远为真的断言和一个有效的断言，输出**一模一样**。

**如何解决**：这套测试经过了**变异测试**验证 ——
往实现里人工植入 15 个错误（删判据、改符号、改顺序、换公式），
逐个跑测试看抓不抓得住。第一轮逃逸 5 个，补完之后 **15/15**。
详见 4.12。

**为什么不引入 gtest**：沿用了工程里已有的 `tests/test_scaffold.cpp` 的裸 `assert` 风格，
不增加依赖。作业要求能从干净目录构建，少一个依赖少一个坑。

# 二、读代码前必须知道的 C++ 语法

你如果已经熟这些，直接跳到「三」。

## 2.1 `#include` —— 把别的文件的内容抄进来

```cpp
#include "AutoAimTypes.hpp"   // 双引号：先在自己的目录里找
#include <vector>             // 尖括号：去系统/标准库路径里找
```

`#include` 是**预处理器**指令，在真正编译之前执行，效果就是把那个文件的全部内容
原样插到这个位置。所以它不是"导入模块"，而是"文本替换"。

## 2.2 `#pragma once` —— 只展开一次

头文件会被很多地方 include，可能出现 "A include B，B 又 include A" 的循环。
`#pragma once` 告诉编译器：这个文件在一次编译里只展开一次。
（技术上不是标准，但 GCC/Clang/MSVC 全都支持，实际项目里比传统的 include guard 更常用。）

## 2.3 `namespace` —— 防止重名

```cpp
namespace armor {
    struct LightBar { ... };
}
```

包在 `armor` 里的东西，全名是 `armor::LightBar`。
好处：别人也可以写一个叫 `LightBar` 的类型，不会冲突。

访问时要写 `armor::LightBar`，或者用 `using namespace armor;` 省掉前缀
（但 `using namespace` 在头文件里是大忌，会污染所有包含它的人）。

## 2.4 匿名 `namespace` —— 只在本文件可见

```cpp
namespace armor {
namespace {                                   // ← 没有名字
    float angleDifferenceDegrees(float a, float b) { ... }
}  // namespace
}  // namespace armor
```

匿名 namespace 里的东西**只在这个 .cpp 文件里可见**，别的文件链接不到它。
作用相当于"文件私有"。用在 `angleDifferenceDegrees` 上，是因为它只是实现细节，
外面不需要也不该看到它。

## 2.5 `struct` —— 把几个数据打包成一个新类型

```cpp
struct LightBar {
    cv::Point2f top{};
    cv::Point2f bottom{};
    cv::Point2f center() const { ... }
};
```

`struct` 和 `class` 在 C++ 里几乎是同一个东西，
唯一的区别是 `struct` 的成员默认 **public**（外部能直接访问），`class` 默认 private。

**`{}` 这个初始化是必须讲的**：
```cpp
cv::Point2f top{};   // x=0, y=0
cv::Point2f top;     // x, y 是栈上的垃圾值！
```
不写 `{}` 的话，这个成员**不会被初始化**，里面是上一次别人用这块内存留下的内容。
危险之处在于它**不报错** —— 你会拿到一个看似正常的随机坐标。

## 2.6 成员函数与结尾的 `const`

```cpp
cv::Point2f center() const { return (top + bottom) * 0.5F; }
//                    ^^^^^
```

括号后面这个 `const` 是**承诺**：调用这个函数不会修改对象自己的内容。
好处有两个：
- 编译器帮你检查（你万一在里面改了 `top`，编译报错）
- 只有 `const` 成员函数才能在 `const` 对象上调用

```cpp
const LightBar bar = ...;
bar.length();        // ✓ length() 是 const 的
bar.someMutator();   // ✗ 编译错误
```

直接在类里面写函数体（像 `center()`）叫做**隐式 inline**，
编译器倾向于不真的发起函数调用，而是把代码贴到调用处。

## 2.7 `constexpr` —— 编译期常量

```cpp
constexpr float kGapRatioSplit = 3.0F;
```

`const` 是"运行时不可改"，`constexpr` 是"编译时就能算出来"。
好处：编译器可以把值直接填进指令里，也能用于数组长度等必须在编译期确定的场合。

命名习惯上用 `k` 开头表示常量（Google C++ 风格）。

## 2.8 引用 `&` —— 给对象起个别名，不复制

```cpp
void f(const std::vector<LightBar>& bars);
//     ^^^^^                      ^
```

`&` 表示 **引用**。参数写 `std::vector<LightBar> bars`（不加 `&`）会**把整个 vector 复制一份**，
灯条多的时候就是白花时间。写成 `&` 只是给原对象起个别名，**零开销**。

前面再加 `const`：函数内不修改它。既省了复制，又保证不被改坏。

**这是 C++ 里最常考的点之一**，一句话记法：
> 传引用避免复制，加 const 防止误改，两个一起用是默认选择。

## 2.9 三种容器

```cpp
std::array<cv::Point2f, 4>   // 固定 4 个元素，长度是类型的一部分
std::vector<LightBar>        // 长度可变，能 push_back
std::pair<LightBar, LightBar>  // 装两个东西，用 .first / .second 访问
```

`std::array` 和 C 数组的区别：`std::array` 知道自己的长度（有 `.size()`），
可以整体赋值，可以当值返回。**不能变长**。
选它的理由：角点永远是 4 个，用 `vector` 反而给了"可能不是 4 个"的错觉。

`std::pair<A, B>` 访问方式：
```cpp
std::pair<LightBar, LightBar> p = ...;
p.first    // 左边的灯条
p.second   // 右边的灯条
```

## 2.10 默认参数

```cpp
ArmorSize classifySize(const LightBar& left, const LightBar& right,
                       float split_ratio = kGapRatioSplit);
//                                     ^^^^^^^^^^^^^^^^^^^^^^^
```

调用时可以省略：
```cpp
classifySize(a, b);        // split_ratio 用默认值 3.0
classifySize(a, b, 5.0F);  // split_ratio = 5.0
```

**重要规则**：默认值只能写一次。
声明（`.hpp`）里写了，定义（`.cpp`）里**不能再写**，否则编译错误。
这就是为什么 `.cpp` 第 89-90 行的定义里看不到 `= kGapRatioSplit`。

## 2.11 三元运算符

```cpp
条件 ? 条件为真时取这个 : 条件为假时取这个
```

例子：
```cpp
const LightBar& l = left_is_left ? left : right;
// 如果 left_is_left 为真，l 就绑定到 left；否则绑定到 right
```

## 2.12 `static_cast<float>(x)` —— 显式类型转换

```cpp
return static_cast<float>(cv::norm(bottom - top));
```

`cv::norm` 返回 `double`（8 字节），函数返回类型是 `float`（4 字节）。
这叫**窄化转换**，会丢精度。

C++ 要求你**显式写出来**，用意是：
- 编译器不会偷偷替你转，想转就得签字
- 读代码的人一眼看到"这里类型变了"

比 C 风格的 `(float)x` 好在：编译器会检查这个转换是否合法，后者什么都能转。

## 2.13 `assert` —— 断言

```cpp
assert(corners[0] == left.top);
```

- 括号内为真 → 什么都不做
- 括号内为假 → 打印 `文件名:行号: 表达式`，然后 `abort()`（程序直接崩）

**致命细节**：`assert` 只在**没有定义 `NDEBUG` 宏**时才生效。
Release 构建通常会加 `-DNDEBUG`，那时候**所有 assert 都被整个删掉**，测试变成空壳。

所以第一次查这个工程时我确认了两件事：
```bash
grep -i "CMAKE_BUILD_TYPE:" build/CMakeCache.txt   # → 空，没有指定
grep -m1 "FLAGS = " build/CMakeFiles/test_armor_detect.dir/flags.make
# → CXX_FLAGS = -std=c++17    没有 -DNDEBUG
```
确认断言是活的。**如果哪天用 `-DCMAKE_BUILD_TYPE=Release` 构建，
所有测试会"通过"得毫无意义。**

## 2.14 浮点数不能用 `==` 比较

```cpp
0.1 + 0.2 == 0.3      // 在计算机里是 false！
```

因为 float/double 是二进制小数，0.1 和 0.2 都存不精确。
所有浮点比较都要加一个容差：

```cpp
bool near(float a, float b, float eps = 1e-3F) {
    return std::fabs(a - b) < eps;
}
```
`1e-3F` 是科学计数法 = 0.001。

### 第 11-14 行：文件说明和命名空间

```cpp
11 // 传统视觉装甲板检测管线。
12 // 拆成"纯几何"和"依赖图像"两层：纯几何部分不碰任何像素，

```

第 14 行的 `{` 一直到文件最后第 78 行才闭合。
中间所有东西的全名都带 `armor::` 前缀。

### 第 16-32 行：`LightBar` 类型

```cpp
16 // ---------------------------------------------------------------------------
17 // 灯条：用"上端中心 + 下端中心"两个点描述，而不是 cv::RotatedRect。
...
25 struct LightBar {
26     cv::Point2f top{};
27     cv::Point2f bottom{};
28
29     cv::Point2f center() const { return (top + bottom) * 0.5F; }
30     float length() const;       // top 到 bottom 的欧氏距离
31     float tiltDegrees() const;  // 与竖直方向的夹角：底端偏右为正
32 };
```

**第 26-27 行**：`cv::Point2f` 就是两个 `float`，名字是 `x` 和 `y`。
`{}` 把两个分量都初始化成 0 —— 不加这个 `{}` 就是栈上的垃圾值，而且不报错。

**第 29 行**逐段拆：
```cpp
cv::Point2f center() const { return (top + bottom) * 0.5F; }
//          ^^^^^^  ^^^^^   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//          返回类型  const   函数体
```
- `top + bottom`：OpenCV 给 `Point2f` 重载了 `+`，逐分量相加 →
  `{top.x + bottom.x, top.y + bottom.y}`
- `* 0.5F`：重载了 `*`，两个分量都乘 0.5
- 合起来 =「两端点的中点」
- 结尾的 `const` = 承诺不修改对象
- 直接写在类里 = 隐式 inline，编译器倾向于把代码贴到调用处，不真的跳转

**第 30-31 行**：只有声明、没有函数体 →
定义在 `.cpp` 里（第 29 行和第 33 行）。

**为什么不都写在头文件里**：改实现时，头文件没变，就只需要重编一个 `.cpp`，
不用重编所有包含这个头文件的文件。工程大了这个差别很可观。

### 第 34-42 行：`PairCriteria` 配对判据

```cpp
34 // 配对判据。全部是无量纲的比值或角度 —— 与分辨率和距离都无关，
35 // 所以不需要随画面大小缩放（"参数分三类"里的第一类）。
36 struct PairCriteria {
37     float max_length_ratio{1.8F};         // 长灯条 / 短灯条 的上限
38     float max_center_y_diff_ratio{0.6F};  // |Δy| / 平均灯条长度 的上限
39     float max_tilt_diff_deg{15.0F};       // 两根灯条倾角差的上限
40     float min_gap_ratio{1.2F};            // 中心距 / 平均灯条长度 的下限
41     float max_gap_ratio{6.0F};            // 同上，上限
42 };
```

**`{1.8F}` 是"默认成员初始值"**（C++11 起）：
```cpp
PairCriteria c;          // c.max_length_ratio == 1.8
PairCriteria c2{2.5F};   // c2.max_length_ratio == 2.5
```

**`F` 后缀**：`1.8` 是 `double` 类型，`1.8F` 是 `float`。
不加 `F` 相当于把 double 塞进 float，编译器可能警告。

**为什么这五条全是"比值或角度"**：
- 比值：分子分母量纲相同，相除后量纲消掉。画面放大 2 倍，分子分母都放大 2 倍，比值不变
- 角度：本来就跟尺度无关

所以这组参数**不需要随分辨率调整**。这是设计上刻意选的，
不是碰巧 —— 如果写成"灯条长度必须大于 20 像素"这种，分辨率一变就全废。

### 第 44-47 行：大小板分界值

```cpp
44 // 大小装甲板分界：间距比 ≥ 此值为大装甲板。
45 // 小装甲板物理 135×57 → ≈2.37；大装甲板 230×57 → ≈4.04。
46 // 取几何平均 √(2.37×4.04) ≈ 3.09，圆整到 3.0。
47 constexpr float kGapRatioSplit = 3.0F;
```

`constexpr` = 编译期常量，`k` 前缀是常量命名习惯。

注意注释里写了**这个数是怎么来的** —— 答辩时会问"3.0 凭什么"，
答"按物理尺寸算的，取几何平均"就够了，答"试出来的"就很弱。

### 第 53-58 行：`pairLightBars` 声明

```cpp
53 // 把两根灯条配成装甲板。返回的每一对都保证 first 在左、second 在右。
54 // 注意：本函数只做"这两根灯条能不能构成一块板"的局部判断。
55 // 三根等距灯条会产生 3 个合法配对（左中 / 中右 / 左右），
56 // 去重留给后面的 NMS。
```

### 第 12-21 行：角度环形距离

```cpp

14 // -179° 和 +179° 实际只差 2°，相减却是 358°。
15 float angleDifferenceDegrees(float a, float b) {
16     float difference = std::fmod(std::fabs(a - b), 180.0F);
17     if (difference > 90.0F) {
18         difference = 180.0F - difference;
19     }
20     return difference;
21 }
```

**第 15 行**：参数按值传 float。float 只有 4 字节，按值传反而比引用快。

**第 16 行**：

- `std::fmod(x, 180.0F)` = x 除以 180 的余数

**第 17-19 行**：把 `[0, 180)` 折叠到 `[0, 90]`。

折叠一下：`180 - 170 = 10` ✓

### 第 33-40 行：灯条倾角（**这一段的思路要讲透**）

```cpp
33 float LightBar::tiltDegrees() const {
34     // 方向向量取"从上端指向下端"，即图像里的向下方向。
35     // 竖直灯条 → atan2(0, 正数) = 0°；下端偏右 → 正角；偏左 → 负角。
36     // 因为约定 top.y <= bottom.y，这里 dy 恒为非负，不会出现 180° 翻转。
37     const float dx = bottom.x - top.x;
38     const float dy = bottom.y - top.y;
39     return std::atan2(dx, dy) * 180.0F / kPi;
40 }
```

**先讲 `atan2`**：
`std::atan2(y, x)` 返回点 `(x, y)` 与**正 x 轴**的夹角，单位弧度，范围 `(-π, π]`。

**标准用法是 `atan2(dy, dx)`** —— 但第 39 行故意写反了。

**为什么写反**：我们想量的是"灯条与**竖直**方向的夹角"，不是与水平方向。
`atan2(dx, dy)` 等价于把整个坐标系旋转 90°，
基准就从 x 轴变成了 y 轴。逐个验证：

| 灯条姿态 | dx | dy | `atan2(dx, dy)` | 对不对 |
|---|---:|---:|---|---|
| 竖直 | 0 | 正 | 0° | ✓ 竖直就是 0° |
| 下端偏右 30° | 正 | 正 | +30° | ✓ 正角 |
| 下端偏左 30° | 负 | 正 | −30° | ✓ 负角 |

**第 36 行那句注释是设计理由的核心**：
约定 `top.y <= bottom.y` 保证 `dy >= 0`，
于是 `atan2` 的结果落在 `(-90°, 90°)` 开区间内，**永远不会跳到 ±180°**。

如果 dy 可能是负的，一根接近竖直的灯条在
"上端略偏左"和"上端略偏右"两种情况下会给出 `+179°` 和 `-179°` 这种差得极远的读数，
判据 3（倾角差）就会误判。**选这个约定就是为了躲开这个。**

**第 39 行的换算**：`* 180.0F / kPi` 是弧度转角度。
`180 / π ≈ 57.2958`，所以 1 弧度 ≈ 57.3 度。

### 第 46-56 行：有向面积

```cpp
46 float quadSignedArea(const std::array<cv::Point2f, 4>& corners) {
47     // 鞋带公式。图像坐标 y 向下，所以顺时针顺序会得到正值：
48     // 左上→右上→右下→左下 恰好是屏幕上的顺时针。
49     float twice_area = 0.0F;
50     for (int i = 0; i < 4; ++i) {
51         const cv::Point2f& current = corners[i];
52         const cv::Point2f& next = corners[(i + 1) % 4];
53         twice_area += current.x * next.y - next.x * current.y;
54     }
55     return twice_area * 0.5F;
56 }
```

**鞋带公式（Shoelace formula）**：
对多边形的顶点 `(x₀,y₀), (x₁,y₁), ..., (xₙ₋₁,yₙ₋₁)` 按顺序排列，

```
2A = Σ ( xᵢ · yᵢ₊₁ − xᵢ₊₁ · yᵢ )        i 从 0 到 n−1，下标对 n 取模
```

普通的面积公式外面有个绝对值：`A = ½ |2A|`。

**第 55 行故意不取绝对值** —— 因为**符号本身就是信息**：
- 正 = 一种绕向
- 负 = 另一种绕向
取绝对值就把这个信息扔了。

**第 50 行**：`++i` 和 `i++` 在这里完全等价（结果没被使用），
但 `++i` 是习惯写法，因为对复杂类型它可能少做一次复制。

**第 52 行 `(i + 1) % 4`**：这是"首尾相连"的常用手法。
- `i = 0` → next 下标 1
- `i = 1` → 2
- `i = 2` → 3
- `i = 3` → `4 % 4 = 0` ← 绕回第一个

**第 51-52 行的 `const cv::Point2f&`**：引用，避免复制。
`Point2f` 只有 8 字节，复制也不贵，但引用同时表达了"我只是看看，不改"。

**第 47-48 行说的"y 向下所以顺时针是正"，怎么验证**：
取一个 10×10 的正方形，按"左上→右上→右下→左下"：
```
(0,0) → (10,0) → (10,10) → (0,10)
```
代进公式：
```
i=0: 0×0   − 10×0  = 0
i=1: 10×10 − 10×0  = 100
i=2: 10×10 − 0×10  = 100
i=3: 0×0   − 0×10  = 0
                     ─────
              2A =    200  →  A = 100  正数 ✓
```
`10×10 = 100` 正好是真实面积，说明公式算对了。

**换成逆时针** `(0,0) → (0,10) → (10,10) → (10,0)`：
```
i=0: 0×10  − 0×0   = 0
i=1: 0×10  − 10×10 = −100
i=2: 10×0  − 10×10 = −100
i=3: 10×0  − 0×0   = 0
                     ─────
              2A =   −200  →  A = −100  负数 ✓
```

**为什么在数学坐标系里逆时针是正，到图像里就反了**：
数学坐标系 y 轴向上，图像坐标系 y 轴**向下**。
y 轴翻转 = 平面做了一次镜像，绕向正好全部反过来。
所以数学里的"逆时针为正"在图像里变成"顺时针为正"。


**第 62 行**：`bool` 类型，`<=` 返回真/假。
注意用的是 `center().x`（**中心**的 x），不是 `top.x`。
用中心是因为中心是"这根灯条整体在哪"，不受两端谁高谁低影响。

**第 63-64 行**：三元运算符。
`const LightBar& l` 是**引用** —— 只是给 `left` 或 `right` 起个别名，
**不复制**。如果写成 `const LightBar l = ...`，就会复制一份(16 字节)，
虽然不贵，但引用是更准确的表达。

**第 66 行 `corners{}` 后面的 `{}` 是保命的**：
`std::array` 是聚合类型，不初始化的话里面是栈内存的垃圾值。
如果下面漏填了 `corners[3]`，它会是一个随机的 `(x, y)`，
一路传到 PnP，解出来的位姿是**完全错误的** —— 但**不报错**。
加上 `{}` 至少让漏填的角点变成 `(0,0)`，一个明显异常的值。

**第 67-70 行的顺序是全项目最硬的一条约定**：

```

corners[1] = 右上 = 右灯条的上端点
corners[2] = 右下 = 右灯条的下端点
corners[3] = 左下 = 左灯条的下端点
```

顺着读 0→1→2→3，在屏幕上画出来是一个**顺时针**的四边形。
这个顺序必须和后面 `armor_solve` 里建三维点时的顺序**完全一致**，
否则 PnP 会解出镜像的位姿。

### 第 89-106 行：大小板分类

**第 89-90 行注意**：定义里**没有** `= kGapRatioSplit`。

**第 91-92 行**：先把两根长度都算出来存着。

**第 98-100 行 —— 这个保护的位置是踩过坑的**：

**这根一根 0、一根 60 的情况拦不住** —— 平均值是 30，不为零，
保护不触发，然后 `132 / 30 = 4.4 ≥ 3.0`，判成**大装甲板**。

问题是：一根长度为零的"灯条"根本不是灯条，
拿它算出来的比值没有任何意义，而错误的方向是"把垃圾放大成大目标"。

改成"分别检查两根的长度"，才真正拦住。

```
NaN < 1.8     → false
```

- 两根灯条长度都是 0，且

- 判据 2：`0 / 0 = NaN` → 放行
- 判据 3：`atan2(0,0) = 0`，差 `0` → 放行
- 判据 4：`0 / 0 = NaN` → 放行

- 判据 6：`center().x` 相等 → `emplace_back`

间距比算出来是 `gap / 0 = +inf`，
而 `inf > 6.0` 是 **true** → 被判据 4 拦下了。
所以必须**两根都退化且重合**才能触发 NaN。

# 四、答辩问答

## 4.1 灯条为什么用「上下两个端点」描述，不用 `cv::RotatedRect`？

`RotatedRect::angle` 的语义在 OpenCV 4.5 变了：
3.x 取值区间 `[-90, 0)`，4.5 改成 `[0, 90)`，符号含义也跟着变。
靠 `angle` 判断"哪根朝上"会踩坑，而且这个坑是**静默的**（不报错，只是算错）。

两个端点自身就带方向，没有歧义，也不依赖 OpenCV 版本。

## 4.2 `quadSignedArea` 为什么是正数才代表顺序正确？

鞋带公式算的是**有向**面积。**图像坐标 y 轴向下**，
所以"左上→右上→右下→左下"在屏幕上走的其实是顺时针，
鞋带公式给出正值。得到负值说明走的是逆时针，即左右被镜像了。

验证：`(0,0),(10,0),(10,10),(0,10)` 代进公式得 `2A = 200`，`A = 100`，
正好是 10×10 正方形的面积。

这个判据在 PnP 里是致命的：角点顺序一镜像，解出来的位姿也跟着镜像，
现象是"车在动但角度反的"。

## 4.3 `buildCorners` 里那道"面积为负就交换"的防御，真的会触发吗？

**不会。它是死代码，我实测过。**

在"按 `center.x` 定序"和"约定 `top.y <= bottom.y`"这两条同时成立时，
生成的顺序必然给出正面积。我用 5000 万组任意倾角的随机灯条采样，
负面积出现 **0 次**，最小面积 `6e-4`（趋近 0 但不变负）。

代码里保留了它，并在注释里写明不可达。理由：它只花一次乘加，
且如果将来有人把定序依据从 `center.x` 改成 `top.x`，它会立刻开始干活。

**这个问题的答法是关键**：能说出"它是死代码、我做过实验证明、我为什么还留着"，
比说"这是一道防御"强得多。后者会被继续追问"那你怎么验证它生效过？"

## 4.4 那退化四边形（四点接近共线）怎么办？

那道防御**挡不住**这个。四点共线时面积趋近 **0** 而不是变负
（测试第 68-70 行验证了：`(0,0),(5,0),(10,0),(15,0)` 的面积是 0），
所以符号检查不会触发。

退化四边形喂给 `warpPerspective` 会出 NaN。必须由调用方
按「面积下限」主动丢弃 —— 这是一个**正的阈值判断**，不是符号判断。
这一步在 M3 的 `detect()` 里做，`quadSignedArea` 已经备好了。

## 4.5 `classifySize` 为什么用「灯条中心距 / 灯条长度」，不用外接矩形长宽比？

外接矩形在装甲板倾斜时会变大，于是长宽比被压低，
**大装甲板会被误判成小装甲板** —— 而且是静默的，不报错。

中心距/灯条长度是**无量纲比值**：分辨率翻倍、距离变远，分子分母同比例变化，
比值不变。测试第 110-114 行就是这个性质的实证（整体放大 3 倍，结论不变）。

## 4.6 分界值 3.0 是怎么定的？

按物理尺寸算：小装甲板 135×57mm → 中心距/灯条长 ≈ **2.37**；
大装甲板 230×57mm → ≈ **4.04**。
取几何平均 `√(2.37 × 4.04) ≈ 3.09`，圆整到 **3.0**。

语义是"**≥** 分界即大板"，用 `>=` 而不是 `>`，并且有专门的边界测试钉住。

## 4.7 判据的阈值是怎么定出来的？

五个数（`PairCriteria` 里的五个默认值）**不是拿真实图像拟合出来的** —— 现场还没有图，
没得拟合。它们能定下来，是因为**全是无量纲量**，而装甲板的物理尺寸给了锚点。
所以它们现在的状态是「**有依据的初值**」，不是「调好的参数」。

锚点（`装甲板尺寸.txt`）：

| | 宽 | 高 | 板宽 ÷ 板高 |
|---|---:|---:|---:|
| 小装甲板 | 135 mm | 57 mm | **2.37** |
| 大装甲板 | 230 mm | 57 mm | **4.04** |

灯条长度 ≈ 板高，两根灯条的中心距 ≈ 板宽。所以「间距比」这个量的两个真实取值
就是 2.37 和 4.04 —— 五个数全围着这两个锚点转。

**判据 4 的下界 `min_gap_ratio = 1.2`：这个数有明确含义。**
板子偏航（绕竖直轴转）时，**画面里宽度按 cos θ 缩短，高度不变**（灯条长度不变），所以

```
间距比 ≈ 2.37 × cos θ        （θ = 偏航角）
```

令它等于 1.2：`cos θ = 0.506` → **θ ≈ 59.6°**。
也就是说 1.2 的含义是「**偏航到 60° 我还认它是一块板**」，再斜就当作没看见。

```
   θ = 0°（正对）                    θ = 60°（偏航）

   ┌─────────────────┐             ┌─────────┐
   │ ▮             ▮ │             │▮       ▮│    宽度缩掉一半
   │ ▮             ▮ │             │▮       ▮│    高度一点没变
   └─────────────────┘             └─────────┘
      比值 2.37                      比值 ≈ 1.19
```

**判据 4 的上界 `max_gap_ratio = 6.0`：纯余量。**
大板才 4.04，6.0 留了约 1.5 倍。老实说这半边拿不出精确推导，
它的作用只是「别把明显离谱的配对放进来」。真正在拦人的是下界。

**判据 2 的 `max_center_y_diff_ratio = 0.6`：约等于「允许歪头 15°」。**
主要来源是板子在画面内旋转（歪头）θ 度：两根灯条中心连线的竖直分量是 `中心距 × sin θ`，于是

```
|Δy| / 灯条长 ≈ (板宽 / 板高) × sin θ = 2.37 × sin θ
```

令它等于 0.6：`sin θ = 0.253` → **θ ≈ 14.7°**。

次要来源是透视：板子偏航时，远端那根灯条在画面里会略微偏上。两者量级差一个数量级左右，
所以 **0.6 主要由「歪头」定，量级是 15°**。

```
   正着放                          歪头 15°
   ▮       ▮                       ▮
   ▮       ▮                        ▮
   ▮       ▮              ────       ▮     右侧那根整体沉下去
   ▮       ▮                       ▮  ▮
   Δy = 0                          Δy ≈ 0.6 × 灯条长
```

**判据 1 的 `max_length_ratio = 1.8`：为「断条」留的，不是为透视留的。**
同一块板的两根灯条在 3D 里等长，画面里不等长只有两个原因。

原因 A 是**透视**（近的那根显得长）。板距 1 m、板宽 0.135 m、偏航 45°：

```
比值 ≈ (1.000 + 0.048) / (1.000 − 0.048) ≈ 1.10
```

凑到 30 cm 的近距也才 **1.38**。**透视最多把比值推到 1.4 左右，够不到 1.8。**

原因 B 是**断条**：过曝或反光把一根灯条切掉一截，只检出 55% 的长度 → 比值就到了 1.8 上下（1 ÷ 0.55 ≈ 1.82）。

所以 1.8 是为「一根灯条被切断」留的。这个区分有意义 —— 它说明这条判据的实际职责是
抗光照不均，虽然 4.8 的概述里我把它简化成了「抗遮挡」。

**判据 3 的 `max_tilt_diff_deg = 15`：「多斜的视角我还认」。**
一块板的两根灯条在 3D 里是平行的。但**透视投影下，平行的 3D 直线在画面里会朝消失点
收敛**，并不平行 —— 板面相对相机越斜，倾角差越大。所以 15° 的含义是「板子斜到这个
程度，我都还认它是一对」。

要注意的是：**板子在画面里整体旋转（滚转）不会产生倾角差** —— 两根灯条一起转，差还是 0。
产生倾角差的是「板面相对相机变斜」，车体俯仰/偏航会把板面变斜，所以这条确实在挡车体
倾斜；纯粹绕光轴的滚转则不是它管的。

**`kGapRatioSplit = 3.0`** 见 4.6：`√(2.37 × 4.04) ≈ 3.09` → 3.0。取几何平均而不是
算术平均，是因为这两个数差的是**倍数**（4.04 ÷ 2.37 = 1.70），对数意义上的中点才是
3.09；算术平均 3.21 会把边界推离小板。

**合起来看**：判据 2 的 15° 和判据 3 的 15° 都指向「板子歪 15°」，这不是巧合 ——
两条在描述同一件事的两个侧面：一根灯条自己歪多少（判据 3），
两根灯条因为歪而错开多少（判据 2）。

**这五个数该怎么被校准**：不是继续拍脑袋调，而是拿真实帧跑一遍配对，
把配对分成「真配对 / 假配对」两堆，量出五个量在两堆里的**分布**，
把阈值放在两个分布**之间的空隙**里。这也是 `PairCriteria` 写成一个 `struct`
（而不是五个散落的 `constexpr`）的原因 —— 校准出来的新值可以整体替换，
`pairLightBars` 的第二个参数就是它，不用改代码。

## 4.8 五条配对判据里哪条最可靠？为什么？

**判据 4「间距比」**（灯条中心距 / 平均灯条长度，落在 `[1.2, 6.0]`）。

理由同 4.5：量纲相消。灯条长度本身随距离缩放，
所以这个比值对**分辨率和距离都不敏感**，不用为不同分辨率重新调参。

其余几条的作用：
- 判据 1（长度比 ≤ 1.8）：抗光照不均导致的断条、遮挡
- 判据 2（y 中心差 ≤ 0.6）：抗透视变形
- 判据 3（倾角差 ≤ 15°）：抗车体倾斜
- 判据 5（中间不许夹第三根灯条）：无阈值，是结构判据 —— 抗"跨两块板的假配对"
- 判据 6（左右定序）：保证对下游的契约

## 4.9 `pairLightBars` 是 O(n²)，为什么不优化？

灯条数量通常个位数到十几根，`n < 30` 时总枚举次数不到 450 次，
暴力枚举的开销可以忽略。换来的是**每条判据都能单独调试、单独注释、单独测**。

真要优化也不该在这里 —— 瓶颈在灯条提取的形态学运算和数字分类上。
**先测再优化，别凭感觉优化。**

## 4.10 三根等距灯条为什么会配出 3 对？

因为本函数只做「这两根灯条能不能构成一块板」的**局部**判断，不做全局去重。

三根灯条 左/中/右：左中、中右、左右，三对在局部都合法。
所以后面**必须做 NMS**，否则 `armor_count` 会虚高，
而且 `detections.front()` 可能选到歪框。

这条已经写成断言钉在测试里（第 168-172 行）——
它不是 bug，是**已知行为**，用它提醒自己 NMS 不能省。

## 4.11 为什么专门测"两根退化灯条中心重合"？

因为 **NaN 与任何数比较都是 `false`** —— 既不大于也不小于。

两根长度都为 0、且中心重合时：
长度比 `0/0 = NaN`、间距比 `0/0 = NaN`，
六条判据的 `if (x > 上限) continue;` 全部不成立，于是**全部放行**，
配出一块四个角点全是假的"装甲板"，一路传到 PnP 才爆炸。

有意思的是：只要两根退化灯条**不重合**，间距比会算成 `+inf`，
反而被 `inf > 6.0` 挡下了。所以只放一根退化灯条是测不出来的。

实现上的修法：在算任何比值**之前**，先检查两根灯条**各自**的长度是否 > 0，
而不是检查它们的**平均值** ——
一根 0 一根 60 时平均值是 30，保护根本不触发。

## 5.1 `extractDigitPatch` 为什么要两级变换，不能直接映射到 20×28？

**因为装甲板和补丁的纵横比是反的，而且反得很厉害。**

| | 物理/像素比例 | 方向 |
|---|---|---|
| 小装甲板 | 135 : 57 ≈ **2.37** | 横的 |
| 大装甲板 | 230 : 57 ≈ **4.04** | 横的 |
| 数据集补丁 | 20 : 28 ≈ **0.71** | 竖的 |

四个角点一步 `getPerspectiveTransform` 到 20×28，等于把一块横着的板子
硬塞进一个竖着的框：数字会被**横向压扁约 3 倍**（2.37 ÷ 0.71 ≈ 3.3）。

要命的是**这不会报任何错**：warp 正常返回、图正常生成、分类器正常给出答案，
只是准确率悄悄掉下去。所以我在 `test_armor_detect.cpp` 里放了一条
专门挡它的断言：在板子正中画一个**正方形**亮块，抠出来的补丁里它必须**仍然是方的**
（宽高差 ≤ 3 像素）。上面那个错误写法会让宽度压成 ≈3、高度还是 ≈10，差值 7，立刻红。

正确的做法分两级：

```
角点 + size
  │ 第一级：正射到"保物理比例的规范板"
  │   小板 135×57mm、大板 230×57mm，每毫米画 px_per_mm 个像素
  │   这一级顺带把透视畸变也去掉了：斜着看板子也能得到端正的数字
  ▼
规范板（横向，比例正确）
  │ 第二级：从**中央**裁数字框
  │   框高 = 整块板高 57mm
  │   框宽 = 57 × 20/28 ≈ 40.7mm   ← 不是拍脑袋，是算出来的
  ▼
40.7 × 57mm → resize 到 20×28 → Otsu 二值化
```

框宽为什么是 40.7 而不是"大概 40"：框高已经被"取整个板高"定死了，
纵横比又被"必须等于数据集补丁的 20:28"定死了，**框宽就没有自由度了**——
`57 × 20/28 = 40.7`。两个约束各自来自实测，不是两个可以随便调的旋钮。

三个细节都有实测依据，不是猜的：

1. **为什么从中央裁**：统计每类 400~500 张补丁，白像素质心的 x 坐标
   落在 0.42~0.54 倍宽度之间 —— 数字确实是水平居中的。
2. **为什么不把框压到字形大小**：实测墨迹高度只占补丁高的
   0.68~0.95 倍，**不是 1**。说明数据集补丁本身就上下留了余量，
   我们按字形去裁会得到一个比训练数据更紧的裁剪，分布对不上。
3. **为什么必须先 resize 再阈值**：反过来的话 `INTER_AREA` 会把 0 和 255
   平均成中间灰度，输出就不再是数据集那种 {0,255} 二值图 ——
   还是不报错。测试里有一条遍历 20×28 每个像素、断言取值只能 ∈ {0,255}。

**必须承认这是假设**：数据集是别人裁好的，我没有它的裁剪代码。
"居中 + 全板高 + 40.7mm 宽"是三条实测线索推出来的假设。
所以留了一个机械的验证手段：拿到真实帧后跑一遍，把补丁落盘成 PNG，
算它的逐列/逐行白占比剖面，和同类数据集补丁的剖面求相关系数。
相关系数高就说明假设成立；低就调 `px_per_mm` 或裁剪宽度重算。
**不需要人眼判断，也不需要标注，只需要一张真实帧。**

## 5.2 HOG 参数怎么选的？

先说结论：**参数不是我调的，是被两个约束定死的**，只有一个数字是实验选的。

```
winSize(20,28) —— 就是补丁尺寸，等于整幅图，没有自由度
cellSize(5,7)  —— 20/5 = 4 列，28/7 = 4 行 → 4×4 个 cell
blockSize(10,14)   —— 2×2 个 cell
blockStride(5,7)   —— 步进恰好 1 个 cell
bins = 9
```
block 能放的位置 = `(4-2+1) × (4-2+1) = 3×3 = 9` 个。
特征维度 = `9 block × 4 cell × 9 bin = 324`。

这个 324 我手算过，也让 OpenCV 报过一次（`getDescriptorSize()` 返回 324），
两边一致 —— 它必须被钉死，因为**特征长度一改，训练好的模型就废了**
（维度对不上直接抛异常）。测试第一行就是 `assert(kFeatureSize == 324)`。

**唯一真正的选择是"用不用 HOG"**，这个我做了实验，不是凭偏好：
在真正的数据集上，把 HOG 特征和"直接用中心 16×24 的原始像素（384 维）"
放在同一个分层划分上比 —— HOG 略好，而且 HOG 对光照的鲁棒性是有理论依据的
（它本身就是梯度方向直方图，对整体亮度偏移不敏感）。
原始像素那 384 维没有任何光照不变性，现场换个曝光就完蛋。
所以我选了 HOG，理由是"实测不差 + 原理上更稳"。

## 5.3 为什么训练程序是 C++，不是 Python？

**不是"不能用 Python"，是"特征代码只能有一份"。**

"训练 99%、现场 30%"这类事故的根因，几乎都是训练时用的特征
和推理时用的特征是**两份代码**：Python 那边 `cv2.resize` 用 `INTER_LINEAR`，
C++ 这边用 `INTER_AREA`；或者一边做了归一化另一边忘了。
两边的差异通常小到看不出来，但足以让分类器在现场全错。

我的做法是让 `tools/train_digit_svm.cpp` 和推理程序
**编译同一个 `student/src/DigitClassifier.cpp`**，调的是同一个
`DigitClassifier::describe()` 函数。这样两边在物理上不可能分叉 ——
改了特征，训练和推理一起变；跑 `test_digit_classifier` 用的是同一份代码。

代价是 `DigitClassifier.hpp` 只能依赖 `<opencv2/core.hpp>` 和标准库，
不能依赖 `AutoAimTypes.hpp` / `ArmorDetector.hpp`。这是有意为之：
训练机上不一定有串口设备，链了 `training_core` 会把 `serialPort` 拖进来。
CMake 里两个训练工具**故意不链 `training_core`**，只链 OpenCV。

顺带一个好处：评分表红线是"依赖联网下载模型或资源才能现场运行"。
模型是自己训出来、提交进仓库的 XML，现场机器上不需要 Python 环境、
不需要 pip、不需要联网。

## 5.4 置信度为什么不是概率？——以及我在这里踩的一个大坑

**先说结论**：契约（`AutoAimTypes.hpp`）要求 `confidence ∈ [0,1]`。
我给的是"冠军类在所有 one-vs-one 对局里的**最小间隔**，过一道 sigmoid"。
它是单调映射，**不是标定概率**：0.9 不等于"有 90% 的概率是这个数字"。
原因是 C++ 版的 `cv::ml::SVM` **没有** `setProbability`/`getProbability`
（我 grep 过 `opencv2/ml.hpp`，零命中；那是 Python 版才有的），
拿不到 Platt 标定之后的概率，就只能老实说这是间隔。

**下面是这一节真正值得讲的东西。**

我最初按计划写的是 `1/(1+exp(-|d|))`，`d` 取
`predict(..., RAW_OUTPUT)` 的返回值。跑到留出集上，置信度区间是
`[0.5, 0.5]` —— **180 张全部是 0.5**。

两个独立的错叠在一起：

1. **`predict` 的返回值不能用。** OpenCV 的实现里返回值是一个
   初始化为 0 的局部 `float`，只有当调用方**没传** results 输出参数时，
   它才会被别名到那个局部变量上。我传了 `raw`，结果写进了 `raw`，
   返回值恒为 0 ⇒ `|d| = 0` ⇒ 置信度恒为 0.5。
2. **改成从 `raw` 里取之后，`raw` 的取值恰好是 `0.0, 1.0, 2.0, …, 8.0`** ——
   它就是**类别序号**。9 类 SVM 内部是 one-vs-one，多类情况下
   `RAW_OUTPUT` 根本不返回决策函数值，返回的是投票出来的类别标签。

第二个错特别阴：改完之后置信度**看起来完全正常** ——
类"1"的 0.5、类"2"的 0.73、类"9neg"的 0.9997，全都落在 [0,1] 里、
全都不报错、准确率照样 100%。但它其实只是"预测出哪个数字"的纯函数，
跟输入图像没有任何关系，而且还会显示成"数字越大越可信"。
这种东西拿去做阈值判断，等于没做。

**抓住它的是一条提前写好的断言**。我在写变异测试时列了一个变异体
"置信度恒为 1"，为了抓它，加了一条 `assert(置信度最大值 − 最小值 > 1e-6)`。
这条断言在真实代码上**第一次跑就红了** —— 我本来以为它只是防变异体，
结果它先抓住了我自己的 bug。这就是"先写会失败的检查"的价值。

**正确的做法**：线性核下，OpenCV 把 one-vs-one 的每个二分类器压缩成
"一个原始权重向量 + 一个偏置"，`getSupportVectors()` 的每一行就是一个权重，
`getDecisionFunction(p, alpha, svidx)` 给出偏置。实测验证（1440 个
「样本 × 它自己参与的每一对」）：

```
dfval = w · x − rho    →  符号符合"pair.first 胜"的比例 100%
dfval = w · x + rho    →  只有 81.39%          ← 这里也踩过，符号是减不是加
```

于是置信度 = `sigmoid(min over 冠军参与的对局 of ±dfval)`
（符号取成"冠军胜为正"）。
取 **min** 而不是平均值：只要有一个对手没被明显压住，就不该报高置信度 ——
这正是"这个数字和某个易混数字之间只差一点"的样子。
落在 (0,1) 且以 0.5 为界：**> 0.5 表示冠军正面赢过每一个对手；
< 0.5 表示它是靠投票数赢的，至少输给过某个对手**，那是实打实的没把握。

留出集上的实测区间 `[0.731, 0.851]`，180 张里 179 个不同取值，不饱和。
测试里也把符号约定钉住了：判对的那张，冠军必须正面赢过每个对手（置信度 > 0.5）。

## 5.5 怎么回答"你这 99.9% 是不是假的？"

这是最该提前准备好的一问。三条，都拿数字说话：

**第一条：先自己给准确率加限定词。** 我报的 99.9% 是
**同源留出集**上的数字 —— 留出集和训练集来自同一批采集，连杂讯都同分布。
它**不等于**现场准确率，而且**在原理上就检测不出域偏移**。
所有材料里我一律写"同源留出集 99.9%"，不写"识别准确率 99.9%"。

**第二条：做诊断，看模型到底学的是不是字形。** 训练程序每次运行都会打印这张表：

| 诊断 | 做法 | 实测 | 判读 |
|---|---|---|---|
| 完整补丁 | 常规 | **99.91%** | 主指标 |
| 只留中心 | 最外 2 像素涂黑 | **99.94%** | 去掉边缘不掉反升 |
| 只留最外2px框 | 中心 16×24 涂黑 | **85.90%** | 边缘单独训也能到 85% ← 看着吓人 |
| **完整模型 → 只留中心** | 用完整模型，喂边缘被涂掉的输入 | **99.40%** | **← 决定性的这一行** |
| 完整模型 → 只留最外2px框 | 用完整模型，喂只剩边缘的输入 | 34.06% | 完整模型确实不看边缘 |
| 只留中心模型 → 完整补丁 | 反过来 | 99.74% | |

那 85.90% 看着像"模型在靠边缘杂讯分类"，但它测的是**"边缘信息够不够用"**，
不是**"完整模型有没有在用边缘"**。这两件事完全不同。真正关系到现场风险的
是第四行：**完整模型喂进"边缘被涂掉"的输入，还有 99.40%** ——
外圈丢了也不影响判字，模型的依据是字形，边缘那 85% 是数据集自己的伪线索
（不同类别的采集光照/裁剪习惯差异），与部署风险无关。
第五行反向印证：只给边缘，完整模型掉到 34%，说明它真的不看那里。

**第三条：变异测试。** 把 21 个"看起来对、其实是错的"改动逐个注入源码，
重编、跑测试，看测试抓不抓得住。**20 个被抓住，1 个逃逸**（下面写了是哪个）。
这说明断言不是摆设。

## 5.6 已知的三个缺口（被问到要老实说）

**一、留出集不能替你验证"域匹配"。** 上面那张诊断表全是同源数据上的，
证明不了"现场抠出来的补丁和数据集补丁像不像"。这个只能拿真实帧验，
方法见 5.1 末尾的剖面相关系数法。**只要一张帧就能做，相机一到手就做。**

**二、极性。** 数据集是"白数字 + 黑底"。若现场抠出来是反的（黑字白底），
HOG 特征会变成"补集"，准确率**静默崩塌**，而且不报任何错。
这个只能靠那张落盘 PNG 的剖面来看（白占比会整体翻转，一眼能看出来）——
**没有开关能替你发现问题**，所以没做开关。
真发现是反的，就把 `extractDigitPatch` 里那句 `THRESH_OTSU` 后面的
`cv::THRESH_BINARY` 改成 `cv::THRESH_BINARY_INV`（源码里那句注释写明了位置）。
一行的事，但**前提是你先看见了**。

**三、一个逃逸的变异体。** 变异测试里"把最小间隔改成第一个间隔（不取 min）"
逃逸了：因为留出集上每个样本的冠军对**第一个**对手的间隔恰好都是正的，
测试只断言了"置信度 > 0.5"，没断言"取的是最小值"。
后果是置信度会偏高（不够保守），不影响分类正确性。
要抓住它需要暴露内部的对局结构，代价大于收益，所以记录在这里而不是硬凑一条断言。

## 5.7 一个数据泄漏的坑（也可以当故事讲）

留出集的做法是：每类按固定种子洗牌后抽 20 张，共 180 张，
连同 `manifest.txt` 提交进仓库。训练程序读这份清单，**清单里的每一个都跳过**。
测试程序读**同一份**清单来评估 —— 两边共用一份，不可能出现"训练用了又拿去测"。

为什么必须是清单、不能是"训练程序自己排除某个目录"：训练集里见过的图拿去测，
准确率会虚高，而且**看不出任何异常**。

我在这里真的踩了：`manifest.txt` 第一行是注释（`#` 开头），
而我最初的读法是 `while (in >> rel >> label)`。
`>>` 会把 `#` 读进路径，接着拿说明文字去读 `int`，流状态一失败循环立刻结束 ——
**整个清单读成 0 条，一声不吭**，180 张留出图全部混进了训练集。
准确率只会变好，没有任何异常。

修法是三件事一起上：逐行读并跳过 `#` 开头的行；
读出来是 0 条直接报错退出；清单里的每一个键都必须在数据集里认领到一张图，
对不上也报错退出。**第一版跑出来打印的是"留出清单 0 条"**，
这个数字本身就是证据 —— 如果当时没打印它，这个坑会一直带到答辩。

教训：**"防数据泄漏"这件事不能靠记得，要靠程序在自己漏了的时候喊出来。**

## 5.8 怎么复现全部数字

```bash
# 1. 构建
cmake -S . -B build && cmake --build build -j"$(nproc)"

# 2. 抽留出集（每类 20 张，可复现）
./build/make_digit_holdout ~/workplace/armor_digit_dataset/datasets \
                           tests/fixtures/digit_holdout 20

# 3. 训练（三个参数全必填，缺一报错）
./build/train_digit_svm ~/workplace/armor_digit_dataset/datasets \
                        models/armor_digit_svm.xml \
                        tests/fixtures/digit_holdout/manifest.txt

# 4. 跑测试
ctest --test-dir build --output-on-failure
```

训练程序会打印：每类被排除的留出张数、那张三行诊断表 + 三行交叉诊断、
完整补丁的混淆矩阵、最终模型路径。
**重复跑两次，输出逐字节相同、模型 md5 相同**（分层划分用固定种子 `20261008`，
文件列表用 `glob()` 排序）—— 这是"可复现"的实测证据，不是承诺。
