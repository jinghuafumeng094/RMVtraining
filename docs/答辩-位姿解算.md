# 一、坐标轴方向图

## 1.1 三个坐标系各自怎么定义的

| 坐标系 | 原点 | x | y | z | 右手系 |
|---|---|---|---|---|---|
| **相机系** | 相机光心 | 右 | 下 | 沿光轴向前 | 是 |
| **云台系** | 云台旋转中心（P 轴） | 前 | 左 | 上 | 是 |
| **物体系**（装甲板） | 板心 | 板右 | 板下 | 指向板背 | 是 |

三处都不是随便定的：

- **相机系的 y 向下**是 OpenCV 的约定，不用选。
- **云台系取 前 / 左 / 上**，与 `armor/include/BulletModel.hpp:6` 的弹道系（世界系）
  轴向相同，于是两系之间只剩一个绕竖直轴的偏航角。依据是学长 2026-10-15 的答复
  「云台系和世界系一样」；相位差从数据里也能独立看出来，见 `docs/上车前问题清单.md` 第 1.1 节。
  **代价**是相机系（右 / 下 / 前）与它不同向，旋转外参不再可能是单位阵，见 §1.2。
- **物体系的 y 也取向下**（而不是向上）是**有意的**：跟相机系同向，
  省掉一次 180° 翻转。（`StudentTasks.cpp:44-48` 的注释写了这个取舍。）
  注意云台系的 y 已经改成向**左**，所以「板正对相机时 `armor_yaw = 0`」
  不再是两个系重合的结果，而是板背法向 `(0, 0, 1)` 经那个 90° 置换落到云台系 `+x` 得到的，见 §1.2。
- **物体系 +z 指向板背**：板正对相机时物体系与相机系**完全重合**，
  于是 `plateObjectPoints` 给的四个点（左上 右上 右下 左下）天然和
  `ArmorDetection::corners` 的顺序约定一致，不需要额外换序。

## 1.2 相机系 → 云台系：一个 90° 置换，加一次平移

```
p_云台 = R · p_相机 + t

      [  0   0   1 ]                    [ 0.06711 ]     前 67.11 mm
R  =  [ -1   0   0 ]        t     =     [ 0.0     ] =   横向 0
      [  0  -1   0 ]                    [ 0.0515  ]     上 51.5 mm
```

**R 不是单位阵。** 云台系是 前 / 左 / 上，相机系是 右 / 下 / 前，两系不同向，
必须有一个旋转把两边的轴对上。R 的三列分别是相机三个轴在云台系里的分量：

- 相机 +x（右）= 云台的 −y（右）
- 相机 +y（下）= 云台的 −z（下）
- 相机 +z（前）= 云台的 +x（前）

**这是命名约定，不是标定残差。** R 正交、行列式 +1，`CameraParameters::valid()`
会校验这两条（`src/AutoAimTypes.cpp:41-47`），填成非刚体矩阵会当场返回空，不会悄悄算下去。

**但 `valid()` 拦不住"把 R 填回单位阵"** —— 单位阵同样正交、行列式也 +1，几何上完全合法，
`valid()` 只好放行，而结果会全错（云台系坐标整个错位，重投影误差却仍然是 0）。
拦它的是 `tests/test_armor_solve.cpp`：那个用例逐分量断言
`position_gimbal_m = (前 2.06711, 左 -0.1, 上 0.1015)`，且断言它与 `position_camera_m`
的距离 > 1 m，R 一退化成单位阵这三条同时红。**这里没有第二道防线。**

**t 的三个数按 前 / 左 / 上 读，不是按相机系读。** 同一份材料里还给了
`云台P轴到摩擦轮的向量：74.1, 0.0, 0.0`（`sanlanx/RMVtraining` 提交 `e65402f`）。
枪口必然在俯仰轴正前方，不可能横向偏 74.1 mm，所以那一段的第一个分量是「前」，
相机的三个数读作 **前 67.11 / 横向 0 / 上 51.5**，即相机在俯仰轴的**前上方、横向居中**。
反过来按相机系读会得到「相机与俯仰轴等高、横向偏 6.7 cm」，两种都不像真车。
完整推导见 `docs/上车前问题清单.md` 第 1.1 节。

**旧口径已作废。** 第一阶段交材料时云台系定义成与相机系各轴同向，那时 `R = I`、
`t = (−0.06711, 0, −0.0515)`，图上画的是「相机在云台左后方」。2026-10-15 云台系改取
前 / 左 / 上 之后，那 90° 落在 R 上、t 取正值，本节、图、`config/camera.yaml` 三处已统一。
任务书只说「约定的云台/世界坐标系」，没有规定是哪一套，两套都自洽；
选后一套是因为它与弹道模型（`BulletModel.hpp`）同系，**EKF 与弹道那一步不用再补置换**。

**相机装歪了怎么办：俯仰偏角另立一项，不塞进 R。** 2026-10-26 新车实测相机头向下倾斜 7.5 度。
它是支架装出来的真实物理旋转，与两系怎么命名无关，所以既不进 R，也不改 t
（相机绕光心转，光心在云台系里的位置不变），而是单独记在 `config/camera.yaml` 的
`mount_pitch_deg`，正值表示光轴相对云台 x 轴向下偏。`armor_solve` 里先乘一个俯仰
−7.5 度的旋转，把测到的方向转回「光轴与云台 x 轴平行」的名义相机系，再乘上面那个置换矩阵：

```
R_生效 = R_命名 · R_x(−7.5°)
```

不补偿的后果是目标整体被读高，2 m 处偏高 2 × tan 7.5° = 26 cm。方向是「读高」不是「读低」：
画面中央的板被当成沿云台 x 轴，而它实际在轴下方 7.5 度。这一条只能靠
`tests/test_armor_solve.cpp` 第 8 组钉住：同一帧角点，`mount_pitch_deg` 填 7.5 时解回
云台 x 轴（z < 1 mm），填 0 时 z > 0.2 m；符号填反会偏到 −0.52 m，两种错都过不了。

## 1.3 图 (b) 那两个数怎么来的

图 (b) 是**侧视图**（从车的右侧看），按比例画（1 mm = 3 px），一眼能读出两个数：

- **前 67.11 mm** —— 相机在云台旋转中心（P 轴）的**前方**；
- **上 51.5 mm** —— 相机在 P 轴的**上方**。

横向分量为 0，所以侧视图里看不出来：相机与 P 轴**横向居中**，既不偏左也不偏右。
这两个数加上中间的 0 就是 `translation_camera_to_gimbal`，模长 84.6 mm。

**t 的正负号（2026-10-13 已定，取正）。** 本字段定义是「云台原点 -> 相机原点」，
即 `O_相机 − O_云台`。学长 2026-10-13 答「外参是云台 P 轴到相机光心」，与这个定义同向，
`config/camera.yaml` 据此填正号。`云台外参.md` 正文把同一组数写成「相机光心到云台 P 轴」，
方向与上面相反 —— 但同一段那个枪口向量 `74.1, 0, 0` 只有在「第一个分量是前」时才有物理意义，
所以那一段用的轴序是 前 / 左 / 上，相机的三个数就是「前 67.11 / 横向 0 / 上 51.5」，
**两组数取正号**。学长那句与字段定义、与这组数三者一致。

# 二、大小装甲板三维点

`plateObjectPoints(size)` 按大小给两套点，都是板心为中心、z = 0 平面上的矩形四角：

| 大小 | 宽 | 高 | 四个点（物体系，m） |
|---|---|---|---|
| `Small` | 0.135 m | 0.057 m | (−0.0675, −0.0285, 0) (0.0675, −0.0285, 0) (0.0675, 0.0285, 0) (−0.0675, 0.0285, 0) |
| `Large` | 0.230 m | 0.057 m | 同构，x = ±0.115 |

顺序固定 **左上 → 右上 → 右下 → 左下**，与 `detection.corners` 一一对应。

**一个已经量过的坑**：大小判错时，PnP **不会报错**，而且**距离几乎不动**。
在真实帧 `hik_capture/barscene/hik_00.png` 上实测：
把小板（135）当成大板（230）解，重投影误差 0.82 → 0.97 px（照样过 5 px 的闸），
深度 1.491 → 1.629 m（**只差 9%**），**但 yaw 从 −0.042 rad 甩到 +0.811 rad（+46°）**。
也就是说，解算器把尺寸误差**吸收成了旋转**，不是缩放。
**四道闸一道都拦不住大小判错** —— 所以大小分类的正确性得由检测那一环保证，
不能指望位姿这一环兜底。（数值与推导见 `rm_autoaim_evidence/05-位姿解算/`。）

# 三、PnP 本身

```cpp
cv::solvePnP(object, image, camera_matrix, distortion, rvec, tvec,
             false, cv::SOLVEPNP_ITERATIVE);
```

- 输入：物体系 4 个三维点 + 图像上 4 个像素角点；内参/畸变来自 `config/camera.yaml`
  （本机标定值 fx 1806.7 / fy 1804.4 / cx 743.4 / cy 526.1，畸变 `[-0.0818, 0.1680, 0, 0, −0.0283]`，
  1440×1080，标定重投影 0.0753 px）。
  **2026-10-13 起 `config/camera.yaml` 已换成第二阶段上车相机的内参**
  （fx 1782.6 / fy 1784.3 / cx 749.4 / cy 574.7，畸变 `[-0.0357, -0.1533, 0, 0, 1.1905]`）；
  本节的推导与结论不受影响，换的只是数值来源。
  **2026-10-22 相机在车上倒装**，`HikCamera::grab` 把画面转 180°，主点变为
  cx 689.6 / cy 504.3，见 `config/camera.yaml`。旋转和平移外参不受影响：
  绕光轴转 180° 不挪光心，也不改手性，相机系仍是 x 右、y 下。
  **2026-10-24 换了一支镜头并改为正装**，`grab` 里不再旋转，内参换成
  fx 2433.8 / fy 2437.4 / cx 679.3 / cy 571.8，畸变 `[-0.0129, -0.3517, 0, 0, -0.1536]`，
  平移外参改为 `(0.0708175, 0, 0.0843059)` m。分辨率仍为 1440×1080。
  本节推导与结论不依赖具体数值。
- 输出：`rvec`（物体系 → 相机系的旋转）、`tvec`（**板心在相机系中的位置，单位 m**）。
- `tvec` 直接就是 `position_camera_m`，不需要再换算。

**必须知道的一件事**：`solvePnP` 对**几乎所有坏输入都返回成功**。
角点缩到 2% 时它给出 100 m 的距离，角点摆成蝶形时它给过 z = 5e11，
角点顺序反了它给出一个**镜像解** —— 这三种情况下 `solvePnP` 的返回值都是 `true`，
重投影误差都是 0。**所以返回值不能当校验用**（`StudentTasks.cpp:129-132` 的注释写了这句）。

# 四、四道闸（异常观测拒绝）

任务书 §3.5 最后一句要求对「PnP 失败、深度非法、误差异常」拒绝。
实现上是**四道**，因为「PnP 不失败但解是错的」这种情况必须单独挡：

| # | 闸 | 条件 | 挡的是什么 | 位置 |
|---|---|---|---|---|
| 0 | 未标定 | `!camera.valid()` → 整体返回空 | 拿占位参数硬算（距离看着正常、实际全错） | `:95-97` |
| 1 | 角点退化 | `quadSignedArea(corners) < 1.0` → 丢这一条 | 四点重合/共线（面积 ≈ 0）；**顺序反了（面积为负）** | `:114` |
| 2 | 深度非法 | `!isfinite(depth) \|\| depth < 0.05 \|\| depth > 30` | 缩爆/拉爆角点解出来的假位姿（5e11、100 m） | `:134` |
| 3 | 误差异常 | `!isfinite(error_px) \|\| error_px > 5.0` | 角点形状自相矛盾 | `:152` |

第 1 道闸**故意不取绝对值**：取绝对值就等于把「顺序反了」当成正常输入放行，
而顺序反了的输入 PnP 会给出一个**位置正确、法向翻转**的解，重投影误差**仍然是 0** ——
误差和深度都拦不住，只有符号能拦。

第 2 道的两端都有物理含义：5 cm 时板已经贴在镜头上，30 m 超过 RM 场地长度（28 m）。

第 3 道的阈值 5 px 依据实测（合成探针 5 px ≈ 某个角点错了 20 px 量级；
真实帧角点抖动 ≤ 1.41 px、重投影 0.70~0.79 px，余量 6.4 倍）。
**但它拦不住"跨板配对"和"大小判错"**：实测一个跨车假对的重投影误差是 2.28 px，
照样过闸。详见 `rm_autoaim_evidence/05-位姿解算/`。

# 五、算出来的四个量

| 量 | 怎么算的 | 位置 |
|---|---|---|
| **距离** | `‖position_gimbal_m‖`，板心到相机光心；平移是刚体变换，模长不变 | `main.cpp:538` |
| **相机系位置** | `position_camera_m = tvec` | `:159` |
| **云台系位置** | `position_gimbal_m = R·tvec + t`（全函数唯一用到外参的地方，R 是那个 90° 置换） | `:180-181` |
| **`armor_yaw`** | 物体系 +z（板背法向）-> 相机系 -> 云台系，取 `atan2(-y, x)`；正对时为 0 | `:183-192` |
| **重投影误差** | `projectPoints` 回来和原角点比 | `:142-154` |

⚠ **`armor_yaw` 的定义存疑**：这里实现的是「板面**法向**在云台系中的方位角」。
但任务书三处措辞（§3.5「目标 yaw/pitch」、`target_yaw`、
`PredictionResult::target_yaw`「最终云台指令」）都指向**板心方位角**。
两者在板正对时相等，板斜了就不等。**待拍板，没定之前不翻。**

pitch 不在 `armor_solve` 里：它由下游从 `position_gimbal_m` 现算
（`main.cpp` 的 `pnp_pitch_rad`），因为 pitch 是「云台要抬多少」，
跟云台当前姿态有关，不属于单帧解算的输出。
