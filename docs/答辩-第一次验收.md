## 2.1 依赖清单

| 依赖 | 版本 | 用途 | 怎么找到的 |
|---|---|---|---|
| GCC / G++ | 支持 C++17 | 编译器 | `CMAKE_CXX_STANDARD 17` |

| OpenCV | 4.x | 图像与 PnP | `find_package(OpenCV 4 REQUIRED COMPONENTS ...)` |

| 海康 MVS SDK | 装在 `/opt/MVS` | 相机取流 | `find_path` / `find_library`，见 2.3 |

OpenCV 的组件列表是逐个列出来的，不是笼统要 `OpenCV`：

```cmake
find_package(OpenCV 4 REQUIRED COMPONENTS
    core imgproc calib3d objdetect ml imgcodecs)
```

- `core` 是 `cv::Mat` 等基础类型；
- `imgproc` 给 `cvtColor` / `resize` / `warpPerspective`；
- `calib3d` 给 `solvePnP`；
- `objdetect` 给 `cv::HOGDescriptor`，`ml` 给 `cv::ml::SVM` —— 这两个是数字分类要的；
- `imgcodecs` 给离线工具的 `imread` / `imwrite`；
- **没有 `videoio`**：取流走 MVS SDK，不用 `cv::VideoCapture`。全仓已经没有任何 `videoio` 符号。

把 `objdetect` 和 `ml` 写进组件列表是必需的：不写的话 `cv::HOGDescriptor` 和 `cv::ml::SVM`
的头文件能找到、链接会失败。

## 2.2 构建产物分四层

`CMakeLists.txt` 一共建了四类目标，分层是为了**让不必要的东西不互相拖**：

| 目标 | 类型 | 内容 |
|---|---|---|
| `serialPort` | 库 | 给的串口类 |
| `web_debug` | 库 | 给的 Web Debug |
| `algorithm_support` | 静态库 | `armor/` 里的参考算法，链 Eigen |
| `training_core` | 静态库 | `AutoAimTypes.cpp` + `AppSupport.cpp` + **我写的四个 .cpp** |
| `rmv_training` | 可执行 | `main.cpp`，链上面全部 |

`hik_mvs` 是 `INTERFACE` 库，只为把 MVS 的头文件路径和库传给使用者。

**`train_digit_svm` 和 `make_digit_holdout` 故意不链 `training_core`**（`CMakeLists.txt:116-134`），
它们只把 `student/src/DigitClassifier.cpp` 这一份源码编进去。原因有两条：

1. 训练机和现场机不是同一台，训练时没有必要要求它也有串口设备和相机；
2. 更重要的是**训练和推理必须用同一个 `describe()`**。同一个 `.cpp` 编进两个程序，
   物理上不可能分叉；如果两边各写一份特征提取，就会出现"训练 99%、现场 30%"那种事故，
   而且**不会报任何错**。

## 2.3 MVS SDK 的查找与 rpath

SDK 不自带 CMake 配置文件，所以没有 `find_package` 可找，只能按路径找：

```cmake
set(MVS_ROOT "/opt/MVS" CACHE PATH "海康 MVS SDK 安装根目录")
find_path(MVS_INCLUDE_DIR MvCameraControl.h PATHS "${MVS_ROOT}/include" NO_DEFAULT_PATH)
find_library(MVS_LIBRARY MvCameraControl PATHS "${MVS_ROOT}/lib/64" NO_DEFAULT_PATH)
if(NOT MVS_INCLUDE_DIR OR NOT MVS_LIBRARY)
    message(FATAL_ERROR "找不到海康 MVS SDK。... 用 -DMVS_ROOT=<安装根目录> 重新 configure。")
endif()
```

找不到时直接 `FATAL_ERROR` 并打印找过哪两个目录、当前值是什么、怎么改 —— 报错要能直接照着做。

**把库目录烤进 rpath，而不是靠环境变量**：

```cmake
get_filename_component(MVS_LIB_DIR "${MVS_LIBRARY}" DIRECTORY)
target_link_options(hik_mvs INTERFACE "-Wl,-rpath,${MVS_LIB_DIR}")
```

MVS 官方 Sample 的 Makefile 也这么干。跳过这一步就得靠 `MVCAM_COMMON_RUNENV` 等环境变量，
而那四个只在 `~/.bashrc` 里，本机登录 shell 是 zsh，干净终端里它们是空的 ——
靠环境变量等于靠运气。烤进 rpath 之后，**跑自己的程序完全不依赖任何 MVS 环境变量**。

# 三、串口与双线程（10 分）

对应必验场景 2 与 8。

## 3.1 64 字节结构体一字节没改，而且有编译期保证

通信结构在 `serialPort/include/Communication.hpp`。三件硬约束：

```cpp
inline constexpr std::uint8_t kFrameHead = 0x71;
inline constexpr std::uint8_t kFrameTail = 0x4C;
inline constexpr std::size_t kCommunicationFrameSize = 64;
#pragma pack(push, 1)
struct MessData_AutoAim { ... };
#pragma pack(pop)
```

`#pragma pack(1)` 是因为**这是串口线上的布局，不是普通内存模型**。不加的话编译器会插填充字节，
帧长就不再是 64。任务书 §3.2 第一条就是"不修改字段、类型、顺序和 64 字节总长度"。

保证方式不是"我记得没改"，而是**一串编译期断言**（`Communication.hpp:50-76`）：

```cpp
static_assert(sizeof(MessData_AutoAim) == 64, "...");
static_assert(sizeof(Translator) == 64, "...");
static_assert(std::is_standard_layout_v<MessData_AutoAim>);
static_assert(std::is_trivially_copyable_v<MessData_AutoAim>);
static_assert(offsetof(MessData_AutoAim, head)  == 0);
static_assert(offsetof(MessData_AutoAim, yaw)   == 1);
static_assert(offsetof(MessData_AutoAim, pitch) == 5);
... 一直到 tail == 63
```

**二十个字段的偏移量逐个钉死。** 谁挪了一个字段的顺序、改了一个字段的类型、或者编译器换了一套
对齐规则，都会在**编译阶段**报错，而不是等现场对不上帧。这比人工核对可靠，也是这张表存在的意义。

同一组 64 字节既能按字段访问、也能当缓冲区用，靠的是联合体：

```cpp
union Translator {
    MessData_AutoAim message;
    char data[kCommunicationFrameSize];
};
```

## 3.2 双线程分工

保留了参考工程的结构：`main` 负责初始化，然后起两个 pthread。

| 线程 | 函数 | 只做一件事 |
|---|---|---|
| 读线程 | `ReadFunction` `main.cpp:280` | 从串口收完整帧，更新共享的 `temp` |
| 操作线程 | `OperationFunction` `main.cpp:332` | 取流 -> 检测 -> PnP -> EKF -> 写回结构体 -> 串口 Write |

**读线程额外维护一个滑动缓冲**（`main.cpp:289-327`）。`SerialPort::Read` 本身已经负责短读缓存，
但那是按"请求多少字节"的语义来的；如果程序从一个半帧的位置启动、或者线上混进了一个干扰字节，
就会一直错位。滑动缓冲的做法是：把收到的字节追加进 `std::vector`，然后从当前位置开始
逐字节找 `0x71 ... 0x4C`，找到才认一帧，找不到就往后挪一个字节。这样**任何时刻都能重新同步**。

`length == 0` 是超时，不是错误，睡 10 ms 继续等；`length < 0` 才是真错误，置退出标志。

## 3.3 共享数据怎么保护的

共享的只有三个变量，都用同一把锁保护（`main.cpp:47-49`）：

```cpp
std::mutex message_mutex;
bool message_available = false;
std::chrono::steady_clock::time_point message_received_at{};
Translator temp;        // 读线程写，操作线程读
Translator translator;  // 只属于操作线程，不需要锁
```

关键在两点：

1. **写和读都在锁里，而且读是"整体复制出来"**（`copyLatestFrame`，`main.cpp:125-134`）。
   不在锁里逐字段读，避免读到半新半旧的一帧。
2. **时间戳和数据在同一把锁里更新**（`publishFrame`，`main.cpp:118-123`）。
   如果时间戳单独维护，会出现"数据是新的、时间戳是旧的"这种撕裂，直接影响到下面的过期判断。

C++ 里只要有一个线程写、另一个线程读同一个对象，就必须同步，否则是未定义行为 ——
不是"偶尔会错"，是编译器有权假设它不会发生并据此优化。所以这把锁不是保险，是必需的。

## 3.4 数据过期怎么处理

```cpp
constexpr auto kMessageMaxAge = std::chrono::milliseconds(500);
```

操作线程每轮先检查三件事（`main.cpp:358`）：

```cpp
if (!frameIsFresh(received_at) || !isAutoAimStatus(translator.message.status) ||
    !hasFiniteControlInput(translator.message)) {
    setSafeOutput(translator);   // 无目标、不许可开火
    writeFrame(*serialPort, translator);
    std::this_thread::sleep_for(kIdleDelay);   // 防止无休止高速回包
    continue;
}
```

- `frameIsFresh` 挡的是"控制器已经 500 ms 没更新了"。这时算法算出来的东西是**基于过期姿态**的，
  继续下发指令是危险的，必须降级。
- `isAutoAimStatus` 只接受状态 0（我方红）和 5（我方蓝），其它模式不进入算法。
- `hasFiniteControlInput` 挡 NaN / Inf。控制器掉线或数据损坏时可能收到非有限值，
  拿它去算旋转会污染整条链路。

**过期时不是"跳过不回包"，而是回一个确定的安全帧**：控制器那边必须持续收到东西，
不然它会以为视觉死机了。所以是 `setSafeOutput` + `writeFrame` 之后才 `continue`。

## 3.5 `crc` 是 EKF 状态，不是校验和

任务书 §3.2 最后一条明确：`crc` 字段表示 EKF 状态，不实现 CRC 算法。
所以代码里**没有任何校验和计算**，写的是：

```cpp
message.crc = static_cast<std::uint16_t>(prediction.state);   // AppSupport.cpp:94
```

`TrackingState` 的三个值和任务书 §3.6 对齐：`NoTarget = 0`、`Stable = 1`、`Unstable = 2`。
`AutoAimTypes.hpp:20-25` 的注释里特意写了"数值直接对应历史通信字段 crc"，就是为了防止
有人看到字段名叫 `crc` 就去写一个校验和。

## 3.6 正常退出的完整路径

```
Ctrl-C
  -> 信号处理函数 request_shutdown()：只置一个原子标志，不做任何清理
  -> 两个线程各自在循环条件里看到标志，退出循环
  -> 操作线程退出前 STOP_WEB_SERVER()
  -> main 先 pthread_join(操作线程)
  -> main 置标志、再 pthread_join(读线程)
  -> main delete serialPort
  -> 进程退出阶段：atexit 钩子释放相机（见第四节）
```

信号处理函数**只置标志**是有意的。在信号处理函数里做任何清理都不安全 ——
它可能在任意一行代码处被打断，那时候锁、堆、SDK 的内部状态都可能是中间态。
让线程自己正常收尾，才能保证清理顺序是对的。


函数内 `static` 从 C++11 起**初始化是线程安全的**，所以"进程内只开一次相机"这件事
由语言保证，不需要手写 double-checked locking。失败一律返回 `false`，不往上抛也不终止进程 ——
上层就靠这个 `false` 走"空帧继续安全回包"的分支。

## 4.2 相机参数

```cpp
constexpr float    kExposureUs     = 5000.0F;   // 曝光 5000 us
constexpr float    kGainDb         = 0.0F;      // 增益 0 dB
constexpr unsigned kGrabTimeoutMs  = 1000;      // 单帧等待上限 1 s
constexpr int      kFailStreakLimit = 5;        // 连败 5 次重开相机
```

**曝光和增益都手动，不用自动。** 自动曝光的目标亮度由相机自己定，画面里灯的亮度一变，
整幅图的灰度就跟着变，下游那一堆**固定**的颜色阈值会被直接拖垮。
白平衡同理关掉：AWB 在 Continuous 模式下会把红色往橙色推。

**顺序不能反**（`HikCamera.cpp:131-141`）：

```cpp
MV_CC_SetEnumValue(handle_, "ExposureAuto", 0);       // 先关自动
MV_CC_SetFloatValue(handle_, "ExposureTime", kExposureUs);   // 再写值
MV_CC_SetEnumValue(handle_, "GainAuto", 0);
MV_CC_SetFloatValue(handle_, "Gain", kGainDb);
MV_CC_SetEnumValue(handle_, "BalanceWhiteAuto", 0);
```

`ExposureAuto` 还开着的时候写 `ExposureTime` 会被自动曝光立刻覆盖回去，**而且不报错**，
只看到"设了没用"。这个顺序问题在标定阶段真的踩过：第一批图就是 AE 顶格 + AWB 还在 Continuous 时拍的。

参数是可以审计的：MVS SDK 每次 `MV_CC_OpenDevice` 都会往
`/var/log/MVS/MvSdkLog/SDK_*.log` 写一行 CSV，记录进程名、PID 和读到的
`ExposureAuto` / `ExposureTime` / `GainAuto` / `Gain`。所以"某次跑的相机参数是多少"
可以直接翻日志，不用复现。

## 4.3 那个退出钩子的坑

这是本轮踩得最深的一个坑，值得单独讲。现象是：程序退出时**时崩时不崩**，
栈顶落在 MVS 自己的线程里，不像我这一层的错。

原因在 `atexit` 的执行顺序。**`atexit` 注册的处理器按注册的逆序执行**：
注册得越晚，跑得越早。MVS 在 `MV_CC_Initialize` / `OpenDevice` 那一串调用里自己注册了退出清理，
而我的注册点在它之后才写上去 —— 但如果注册点放在 `StartGrabbing` 之前，就变成
**我注册得更早、跑得更晚**，轮到我清理时设备已经被它释放了。实测那个时序下：

```
MV_CC_StopGrabbing  -> 0x80000000（MV_E_HANDLE，无效句柄）
MV_CC_DestroyHandle -> 在已释放的内存上再释放一次，段错误
```

解法是把注册点推到 `StartGrabbing` **之后**，这样注册得比 SDK 晚、跑得比它早，
清理时设备还活着。实测四个调用全部返回 0x0。

所以 `HikCamera.cpp:153-159` 那一行 `std::atexit(&releaseCameraAtExit);` 的位置是**有意义的**，
注释里写着"别往上挪"。每次成功开流都注册一次也是故意的：重开相机之后要重新注册，
才能继续压过 SDK 新注册的那一份。重复注册无害，`releaseAll()` 是幂等的。

## 4.4 像素格式转换交给 SDK，不用 `cv::cvtColor`

（`HikCamera.cpp:200-232`）

MVS 的 `"BayerRG8"` 与 OpenCV 的 `COLOR_BayerRG` **是不是同一个相位，官方没说**。
猜错了 R/B 会对调 —— **而且不报错**，只会让红蓝队判反，是最难查的那种错误。
所以直接把转换交给 SDK 的 `MV_CC_ConvertPixelTypeEx`，目标格式 `PixelType_Gvsp_BGR8_Packed`，
从源头上不给自己猜的机会。

配套两个细节：

- **行列数用 `nExtendWidth` / `nExtendHeight`，不用 `nWidth` / `nHeight`**。前者是"真正的行宽"，
  Bayer 图可能有对齐填充。本机 1440 恰好是 4 的倍数，现在两者数值相同 ——
  **但这个巧合不能写进代码**。
- **`MV_CC_FreeImageBuffer` 无论转换成功还是失败都要调**（`HikCamera.cpp:220`）。
  `MV_CC_GetImageBuffer` 拿的是 SDK 缓冲池里的缓冲，不还的话几十帧就把池子耗干净，
  之后再也取不到图。

最后 `clone()` 是必需的：转换结果是栈上的临时 `std::vector`，出了函数就没了。

## 4.5 取流失败的处理

```cpp
if (nRet != MV_OK) {
    ++failStreak_;
    std::cerr << "[camera] 取帧失败 ... 连续 " << failStreak_ << " 次\n";
    if (failStreak_ >= kFailStreakLimit) { close(); }   // 连败 5 次就重开
    return false;
}
```

- 单次失败只是**计数并返回 `false`**，不关相机也不退出。
- 连着失败 5 次，`close()` 把句柄整个放掉，下一帧 `grab()` 里 `openOnce()` 会重新枚举、重开。
  相机掉线再插上，程序能自己恢复。
- 捕获到帧就 `failStreak_ = 0`。

上层还有一层：`main.cpp:373-395` 里连续空帧超过 3 次会结束操作线程。
分层的好处是"相机重连成功"和"相机彻底没了"是两种不同的处理，不会混在一起。

## 4.6 标定结果

标定用 MATLAB R2024b 的 `cameraCalibrator`，99 张棋盘格（9×12 方块、25 mm/格），
结果写在 `config/camera.yaml`：

| 项 | 值 |
|---|---|
| 分辨率 | 1440 × 1080 |
| 内参 | fx 1806.7 / fy 1804.4 / cx 743.4 / cy 526.1 |
| 畸变 | `[-0.0818, 0.1680, 0, 0, -0.0283]`，顺序 `[k1, k2, p1, p2, k3]` |
| 平均重投影误差 | 0.0753 px |
| 旋转外参 | `R = I`（单位阵） |
| 平移外参 | `t = (−0.06711, 0, −0.0515)` m |

**判据不是重投影误差，而是画面四角的径向缩放因子** `1 + k1r² + k2r⁴ + k3r⁶`。
第一轮结果重投影误差同样是 0.0753 px，但四角缩到了 0.66 —— 明显不对。
原因不是标定算法，是**采样**：第一轮棋盘格只覆盖到画面 44% 半径，高阶畸变系数在没有任何约束的
区域外推。第二轮补拍后四角缩放均为 0.9896，正常镜头落在 0.98~1.02。

**所以这一条要记住：低重投影误差 ≠ 标定正确。** 重投影误差只反映"棋盘格覆盖到的那块区域"拟合得怎么样。

`p1 = p2 = 0` 是 MATLAB 默认不估计切向畸变（`EstimateTangentialDistortion = false`）导致的，
不是配置错误；切向填 0 在 OpenCV 针孔模型里是完全合法的取值。

## 4.7 外参：这是坐标系约定，不是缺省值

`rotation_camera_to_gimbal` 取单位阵，依据是学长 2026-10-10 的答复：
「相机系和云台系只有平移、没有旋转」。把云台系**定义成与相机系各轴同向、原点取云台旋转中心**，
两个系的三个轴就一一平行，旋转外参就确实是单位阵 —— 这是那个约定下的**真值**，不是占位符。

**另有一套同样自洽的约定**是枪管系（x 前 / y 左 / z 上，见 `armor/include/BulletModel.hpp:6`），
那时 `R` 是一个 90° 置换矩阵。任务书只要求"说明两个坐标系各轴方向"，没有规定用哪一套。
两套都对，本工程选了前一套，轴向约定写在 `config/camera.yaml` 头部。

代价是：`position_gimbal_m` 活在"x 右 / y 下 / z 前"里，而 `BulletModel.hpp` 假设
"前 x / 左 y / 上 z"、串口 yaw/pitch 符号也未定 —— 接 EKF 与弹道那一步要补一个置换。
这不影响 §3.5 的解算本身。

> ⚠ `t` 的正负号**尚未与学长复核**。`config/camera.yaml` 里这个字段的定义是
> 「云台原点 -> 相机原点」= `O_相机 − O_云台`；handout 给的三个数按「相机光心 -> 云台 P 轴」
> = `O_P − O_相机` 写，两者方向相反，所以按字段定义取了负号。确认后如果反过来，
> 改配置里那三个数即可，代码和图都不用动。

## 4.8 配置校验：非法就明确报错退出，不硬算

`main.cpp:211-215` 在起线程之前就检查标定文件：

```cpp
if (!loadCameraParameters(options.camera_config, camera, camera_error)) {
    std::cerr << camera_error << '\n';
    return EXIT_FAILURE;
}
```

`loadCameraParameters()`（`src/AutoAimTypes.cpp:50-92`）读完之后调 `CameraParameters::valid()`，
`valid()` 检查的是一整套：

| 检查 | 挡的是什么 |
|---|---|
| `calibrated == 1` | 忘了把模板标志改成 1 |
| `image_width/height > 0` | 占位的 0 |
| 四个矩阵的**类型与维度**（`CV_64F`、3×3 / 3×1 / 1×n） | 复制粘贴时行列填错 |
| `cv::checkRange` 四个矩阵 | NaN / Inf |
| `mean_reprojection_error_px >= 0` 且有限 | 模板里的 −1 |
| `fx > 0`、`fy > 0` | 全零占位矩阵 |
| `det(R) ≈ +1`（容差 1e-2） | 不是刚体旋转 |
| `‖RᵀR − I‖∞ < 1e-2` | 旋转矩阵不正交 |

**为什么不"检查失败就警告一下继续跑"**：用占位参数解出来的距离看着完全正常、实际全错，
比"没有结果"难查得多。任务书 §3.3 也明确要求"缺失或非法时明确报错退出"。
`armor_solve` 里还有第二道（`StudentTasks.cpp:89-95`）：`!camera.valid()` 时直接返回空，
而不是拿占位参数硬算。

`config/camera.yaml.example` 是纯模板，里面所有矩阵都是全零，注释里写着"不可用于运行"。

## 5.2 ① 颜色掩膜

```cpp
cv::subtract(main, other, diff);      // 主通道 − 副通道，带符号
cv::threshold(diff, strong, 60, 255, cv::THRESH_BINARY);   // 通道差够大
cv::threshold(main, bright, 100, 255, cv::THRESH_BINARY);  // 主通道本身够亮
cv::bitwise_and(strong, bright, mask);
```

**本函数唯一但致命的坑：差值必须是带符号的。** 蓝队找 B > R，红队找 R > B。
换成 `cv::absdiff` 就是 |B − R|，红队和蓝队会看到**一模一样**的结果，对面队伍的车全变成目标 ——
而且不报任何错。`cv::subtract` 对 `CV_8U` 是饱和减法，负数截成 0，正好等价于 `max(B−R, 0)`。

**两条判据是"与"关系，缺一不可**：
- 只用差值：一个通道差 70 的暗灰蓝像素（比如 80/60/10）也会进来；
- 只用亮度：白光（255/255/255）差值只有 0 倒是不进，可**偏色的高光**会漏进来。

阈值 60 / 100 是从海康那 69 张整图上量出来的，不是拍的：

| 统计 | 值 |
|---|---|
| \|B−R\| < 20 的像素 | 99.78%（背景、场地、地板全在这里） |
| \|B−R\| ≥ 120 的像素 | 0.13%（灯条本体） |
| 用 >60 且主通道 >100 之后，一帧剩下的斑块 | 0~8 个，69 帧平均 2.6 |

60 落在"背景极密、灯条极疏"中间的空档里，**两边都有近 5 倍余量**，
所以在 60 附近挪动不会突然崩 —— 这一点对现场调参很重要。

## 5.3 ② 灯条提取

```cpp
cv::findContours(mask, contours, cv::RETR_EXTERNAL, cv::CHAIN_APPROX_SIMPLE);
```

**`RETR_EXTERNAL` 是有意的**：只要最外层轮廓。灯条过曝时中间会烧成白、边缘反而偏暗，
用 `RETR_LIST` / `RETR_TREE` 会把同一根灯条拆成里外两三个轮廓，每一圈都被当成独立灯条去配对，
于是同一块板配出一堆假目标 —— 而且看起来"检测很灵"。

三道形状门槛，管三个**互相正交**的量：

| 门槛 | 量纲 | 管什么 |
|---|---|---|
| `min_aspect` 1.5 | 比值 | 形状像不像灯条 |
| `min_area` 30 px² | 长度² | 粗不粗 |
| `min_long_side` 20 px | 长度 | 长不长，也是唯一决定"最远能看多远"的 |

正交性有实测（69 帧各一例）：一根 29.3×1.8 的细丝，面积只有 16 被 `min_area` 挡，
可它长边 29 够长、长宽比 16 也在 [1.5, 20] 内 —— **撤掉 `min_area`，形状门槛一个都拦不住它**。

**`min_long_side` 的下限不是"灯条看起来够不够大"，而是"端点定得准所需要的像素数"。**
端点量化是 1 像素的阶跃，而配对判据里每一项都**除以灯条长度**，于是误差按 1/长边 放大：

```
间距比的相对误差 ≈ 1 / 长边
tiltDegrees 的误差 ≈ 57 / 长边 度
```

实测：长边 22 -> 4.3%，16 -> 5.9%，11 -> 8.3%，9 -> 10%（与 1/长边 吻合）。
长边掉到 9 附近时，两根灯的倾角差误差最坏可达 ~12°，而判据 3 的预算只有 15°，判据被噪声吃掉。
取 20 的理由：比值相对误差 5%、倾角 2.9°，都只有判据预算的五分之一上下。

**不用 `cv::RotatedRect::angle` 判断哪条边是长边**：OpenCV 4.5 起 `angle` 的取值区间和符号语义
都改过（3.x 是 [−90,0)，4.5 是 [0,90)），靠它判断会随版本变。直接比四条边的长度，没有任何歧义。

## 5.4 ③ 灯条配对：六条判据

`pairLightBars`（`ArmorDetector.cpp:136`）对每一对灯条做 O(n²) 判断，**只做局部判断**：
"这两根灯条能不能构成一块板"。返回的每一对都保证 first 在左、second 在右。

| # | 判据 | 阈值 |
|---|---|---|
| 1 | 两根灯条长度比 | ≤ 1.8 |
| 2 | 中心高度差 / 平均长度 | ≤ 0.6 |
| 3 | 倾角差 | ≤ 15° |
| 4 | 中心距 / 平均长度 | ∈ [1.2, 6.0] |
| 5 | 两根之间不能夹着第三根灯条 | — |
| 6 | 左右定序 | — |

**判据 5 是本轮新增的、也是最有价值的一条。** 真实装甲板中间不会竖着第三根灯条；
夹着的那一对是**跨了两块板**。光靠间距比挡不住它：在实测的某一帧上，跨板那对的间距比是 5.05，
**正好落在合法区间 [1.2, 6.0] 里，五条判据全过**。而它的外接矩形最大，NMS 按面积取大正好留它下车 ——
结果裁剪框落到了中间那根灯条上，"数字补丁"其实是灯条本身。加上判据 5 之后三根等距灯条只产生 2 对。

判据 5 的纵向范围只在两根灯条**共同覆盖的高度带**内判，避免把背景里远处、纵向错开的目标误判成夹在中间。

**`pairLightBars` 不保证一根灯条只出现一次**，这是故意的。四根灯条同框时会给出三对
`(b0,b1)(b1,b2)(b2,b3)`，b1 和 b2 各被两对用到。局部判据不该假装知道全局的事，
"一根灯条只用一次"交给下一步。

## 5.5 ③' 一对一选择：`choosePairs`

这是本轮修的另一个大 bug。之前四根灯条会被拆成三个框（同一块板被报多次）。
判据 5 和 NMS 都挡不住"相邻两对共用灯条"。

`choosePairs`（`ArmorDetector.cpp:258`）的做法是贪心：按分数从高到低，能放就放
（两端灯条都还没被占），用一张 `used[]` 表记账。返回按分数降序，最好的排最前面；
分数打平时按候选顺序定先后 —— **结果必须是确定的**，否则同一帧隔一次跑给出不同的框，现场没法复现。

分数三个来源，前提都是候选已经过了全部六条判据：

| 来源 | 量程 | 说明 |
|---|---|---|
| 几何自洽度 | −3 ~ 0 | 三根判据各自归一化成"预算用掉了几成"，量纲无关、可加 |
| 板面对比度 | 0 ~ +1 | `min(对比度−1, 1)`，封顶是免得它一家独大盖过几何 |
| 数字奖励 | 0 或 +2 | 读出 1~8 **且这一对确实有板面**才加 |

数字奖励从 10 降到 2 是有实测依据的：真板的板面项封顶只有 +1，所以奖励只要 > 1，
**一个误报的数字就必然压过一块板面看得清清楚楚的真板**。现场实测的跨车假对正是这种情形。
而且加了"必须真有板面"这个前提 —— 数字是印在牌面上的，牌面都没有的地方读出数字本身就是错的。

**没有竞争时，分数多低的一对都会返回。** 下游要靠"角点有效但 target_id = 0"
把"检测坏了"和"分类坏了"分开，这里筛掉就把两种故障混成一种了。

## 5.6 ④ 角点 与 ⑤ 大小分类

`buildCorners`（`ArmorDetector.cpp:93`）的顺序是**硬约定**，全链路都依赖：

```
c[0] 左上 = 左灯条 top      c[1] 右上 = 右灯条 top
c[2] 右下 = 右灯条 bottom   c[3] 左下 = 左灯条 bottom
```

内部有防御：万一调用方把左右传反了，按 `center().x` 自动交换后再生成 ——
交给"谁在左边"这个客观量判断，不依赖调用方的自觉。

`classifySize`（`ArmorDetector.cpp:117`）用"灯条中心距 / 灯条长度"判大小，
分界值 `kGapRatioSplit = 3.0`：

```
小装甲板 135×57 = 宽高比 2.37     大装甲板 230×57 = 宽高比 4.04
取几何平均 √(2.37×4.04) ≈ 3.09，圆整到 3.0
```

**为什么不看角点外接矩形的长宽比**：板子一倾斜外接矩形就变大，比值被压低，大板会被误判成小板。
而"中心距 / 灯条长度"在透视下稳定得多。

大小判错有多严重：在真实帧上实测，把小板当成大板解，重投影误差 0.82 -> 0.97 px（照样过 5 px 的闸），
深度 1.491 -> 1.629 m（**只差 9%**），但 **yaw 从 −0.042 rad 甩到 +0.811 rad（+46°）**。
解算器把尺寸误差**吸收成了旋转**，不是缩放。**四道闸一道都拦不住大小判错** ——
所以大小分类的正确性必须由检测这一环保证。细节见 `docs/答辩-位姿解算.md` 第二节。

## 5.7 ⑥ 数字分类

完整逐行解析见 `docs/答辩-数字分类代码.md`，这里只给结论与关键设计。

**方案**：`cv::HOGDescriptor` 提特征 + `cv::ml::SVM` 线性核分类，离线训练好、随仓库提交。
数据集 17787 张、9 类（`1 2 3 4 5 6outpost 7guard 8base 9neg`），全部 28 高 × 20 宽、
**只有 {0, 255} 两个灰度级**（已是二值图）。

**两级变换**（`extractDigitPatch`，`ArmorDetector.cpp:328`）是最容易写错的一处：

```
角点 + 大小
   │ 第一级：正射到"保物理比例的规范板"（小板 135×57，大板 230×57）
   ▼
规范板
   │ 第二级：从中央裁出数字框。框高 = 整板高，框宽由"保持 20:28"定出 ≈ 40.7 mm
   ▼
resize 到 20×28 + THRESH_OTSU 二值化
```

**错法是四个角点直接 `getPerspectiveTransform` 到 20×28**：装甲板物理 135:57 ≈ 2.37（横的），
数据集补丁 20:28 ≈ 0.71（竖的），一步到位会把数字**横向压扁约 3 倍**，而且不报错，只是准确率掉下来。

**必须 `THRESH_OTSU`**：数据集是 0/255，喂灰度模糊图会让 HOG 的梯度分布完全不同。
这是**静默错误**，所以测试里钉住了"输出值域 ⊆ {0, 255}"。

**置信度是决策函数值的单调映射，不是标定概率**：

```cpp
const float d = svm->predict(desc, cv::noArray(), cv::ml::StatModel::RAW_OUTPUT);
const float confidence = 1.0F / (1.0F + std::exp(-std::fabs(d)));
```

C++ 的 `cv::ml::SVM` **没有 `setProbability`**（`opencv2/ml.hpp` 零命中），拿不到标定概率。
这里有一个必须知道的坑：多类情况下 `predict(..., RAW_OUTPUT)` **返回的是类别标签本身**，
不是决策函数值（实测：类 1 的样本 raw 恒为 0.0，类 2 恒为 1.0，…… 类 9neg 恒为 8.0）。
拿它当 margin，置信度就变成"预测出哪个数字"的纯函数、跟输入图像毫无关系，而且看起来还挺像回事。
所以自己从 `getSupportVectors()` 里取出 36 个 one-vs-one 二分类器的原始权重，
算 `dfval = w·x − rho`，取**冠军类在所有对局里的最小间隔**再过 sigmoid ——
`> 0.5` 表示冠军正面赢过了每一个对手，`< 0.5` 表示它是靠投票数赢的。

**诚实说明**：报告和答辩材料里这个数一律写成"同源留出集上的准确率"，不写成"识别准确率"。
留出集和训练集来自同一批采集，连杂讯都同分布，**它在原理上就检测不出域偏移**。
这个话题在下面的问答里展开。

## 5.8 目标丢失处理（评分表明确列的一项）

`DigitClassifier` 的类别表里，`9neg` 的含义是"这块 ROI 里**没有数字**"，映射到 `target_id = 0`：

```cpp
constexpr int kTargetIds[] = {1, 2, 3, 4, 5, 6, 7, 8, 0};
//                             1  2  3  4  5  6out 7g  8b  9neg
```

这正好对上 `AutoAimTypes.hpp:54` 里"0 保留给未知目标/无目标"的约定。

**关键设计：板子检测到了、但中间没有数字时，这块板仍然返回**（角点有效，PnP 能用），
只是 `target_id = 0`。下游 `applyPrediction` 用 `target_id != 0` 把开火闸住
（`AppSupport.cpp:15`）。

**为什么不整块丢掉**：反过来的做法会让"检测坏了"（`armor_count == 0`）和"分类坏了"
（`armor_count > 0` 但 `detection_id == 0`）在 Web Debug 上长得一模一样，两种故障没法区分。
这条也写进了 `detectArmors` 的注释。同一原则也用在抠补丁失败时：**不 `continue`**，
角点是对的、PnP 还能用，证据保持默认值。

外部灯条遮住数字时，该帧不会被当成"干净"，也不会凭空多出一块板 —— 就是 `target_id = 0` 的一块板。

## 5.9 ⑦ 去重

`suppressOverlaps`（`ArmorDetector.cpp:661`）按外接矩形面积从大到小贪心保留互不重叠的，`nms_iou = 0.3`。

**为什么按面积排序而不是按置信度**：面积大说明离得近、像素多，数字本来就更好读；
而置信度回答的是"有多确定是某个数字"，跟"这是不是一块真板"是两回事 ——
板子上什么都没有时，分类器会很有把握地说"这是 9neg"，置信度一样可以很高。

NMS 现在是**第二道保险**：同一块板被拆成多个框的主要来源（一根灯条被两个候选共用）
已经在 `choosePairs` 那里按一对一拍死了。NMS 只管"两块真板挨得太近、外接矩形确实叠上了"这一种。

一个细节：`cv::boundingRect` 对**点集**用的是含两端的约定（宽 = x_max − x_min + 1），
所以四点跨 200 像素时给出的宽是 201，不是一个笔误。后果是这里的 IoU 会比按坐标区间手算略大一点点，
对 NMS 这种只要相对大小的判据没有影响。

## 5.10 现场稳定性

| 场景 | 处理 |
|---|---|
| 无目标 / 空图 | `detectArmors` 入口就拒绝，返回空 vector，不假定每帧一定有目标 |
| 灰度图 / RGBA | 入口统一归一化一次；其它类型明确返回空，不猜通道顺序 |
| 四点退化 | `min_quad_area_px = 100` 提前丢，避免在退化角点上白跑一次透视变换 |
| 相机掉线 | `grab()` 连败 5 次重开；上层连续空帧超 3 次结束操作线程 |
| 参数与分辨率 | 三类参数分清楚，换分辨率只调像素量那一类 |

# 六、位姿解算（15 分）

**完整的逐条材料在 `docs/答辩-位姿解算.md`**（含坐标轴方向图、三维点表、四道闸表）。
这里只列提纲，细节一律以那份为准。

| 任务书 §3.5 要求 | 落在哪 |
|---|---|
| 按尺寸建大小装甲板三维点 | `plateObjectPoints()` `StudentTasks.cpp:45` |
| 用标定内参做 PnP | `cv::solvePnP(..., SOLVEPNP_ITERATIVE)` `StudentTasks.cpp:120` |
| 转到约定云台系 + 报告里画坐标轴 | 变换 `:158-162`；图见 `答辩-位姿解算.md` 第一节 |
| 算距离 / yaw / pitch / 重投影误差 + 拒绝异常观测 | 四道闸见下 |

**四道闸**（比任务书要求的三类多一道）：

| # | 闸 | 条件 | 挡的是什么 |
|---|---|---|---|
| 0 | 未标定 | `!camera.valid()` | 拿占位参数硬算 |
| 1 | 角点退化 | `quadSignedArea(corners) < 1.0F` | 四点重合/共线；**顺序反了（面积为负）** |
| 2 | 深度非法 | `depth < 0.05 \|\| depth > 30` | 缩爆/拉爆角点解出来的假位姿 |
| 3 | 误差异常 | `error_px > 5.0` | 角点形状自相矛盾 |

**第 1 道闸刻意不取绝对值**，这是这一节最容易被追问的一点：取绝对值就等于把"顺序反了"
当成正常输入放行。而顺序反了的输入 PnP 会给出一个**位置正确、法向翻转**的镜像解，
重投影误差**仍然是 0** —— 误差和深度都拦不住，只有符号能拦。

**必须知道的一件事**：`solvePnP` 对**几乎所有坏输入都返回成功**。角点缩到 2% 时它给出 100 m 的距离，
角点摆成蝶形时给过 z = 5e11，角点顺序反了它给镜像解 —— 这三种情况的返回值都是 `true`，
重投影误差都是 0。**所以返回值不能当校验用**，必须自己按物理范围兜。

另外两条已经量过的结论：

- **大小判错会变成旋转误差**（前面 5.6 节），四道闸拦不住，只能靠检测保证；
- **跨板配对的观测能过闸**：实测一个跨车假对的重投影误差是 2.28 px，照样过 5 px 的闸。
  所以判据 5 和 `choosePairs` 必须在检测那一环挡住它。

**⚠ 一个还没定的定义**：`armor_yaw` 实现的是"板面**法向**在云台系中的方位角"，
但任务书三处措辞（§3.5「目标 yaw/pitch」、`target_yaw`、`PredictionResult::target_yaw`「最终云台指令」）
都指向**板心方位角**。两者在板正对时相等，板斜了就不等。

# 七、Web Debug（5 分）

对应必验场景 7：页面持续显示关键曲线，**页面刷新不影响视觉处理**。

## 7.1 接口

`web_debug/include/WebLogger.hpp` 给三个宏：

```cpp
#define START_WEB_SERVER(port)   WebLogger::getInstance().start(port)
#define STOP_WEB_SERVER()        WebLogger::getInstance().stop()
#define WEB_LOG(key, value)      WebLogger::getInstance().log((key), (value))
```

关闭调试时它们变成空操作，并且**不求值传入的参数** ——
所以 `WEB_LOG("fps", expensive())` 在关闭时不会调用 `expensive()`。

`WebLogger` 是单例，内部一个 10000 条的环形缓冲 + 一把锁 + 一个后台 HTTP 线程。
`log()` 只往缓冲里塞一条样本、**不等网页读**，所以内存占用有上界、页面卡住也不会拖慢算法。
网页通过 SSE 拉数据，每个客户端各自记录序号，所以**刷新页面不影响视觉处理**。

## 7.2 记录了哪些量

任务书 §3.7 要求四组，`main.cpp` 里全部都有：

| §3.7 要求 | key |
|---|---|
| 相机帧率与单帧处理耗时 | `camera_fps`、`process_time_ms`、`frame_dt_ms` |
| 检测数量、目标编号、置信度 | `armor_count`、`detection_id`、`detection_confidence`、`target_x_px`、`target_y_px` |
| PnP 距离、yaw/pitch、重投影误差 | `pnp_distance_m`、`pnp_yaw_rad`、`pnp_pitch_rad`、`pnp_reprojection_error` |
| EKF 车体中心、速度、yaw、角速度、半径、状态 | `ekf_x_m`、`ekf_y_m`、`ekf_vx_m_s`、`ekf_vy_m_s`、`ekf_yaw_rad`、`ekf_yaw_rate_rad_s`、`ekf_radius_1_m`、`ekf_radius_2_m`、`ekf_state`、`target_found` |

外加两个排查用的：`empty_frame`（连续空帧计数）、`target_id` / `target_yaw` / `target_pitch` / `target_distance`。

**两处刻意的设计**：

1. **没有观测时把这一帧显式标成无效**，写 `pnp_reprojection_error = -1.0`、`pnp_yaw_rad = -1.0`、
   `pnp_pitch_rad = -1.0`（`main.cpp:445-451`）。不这么做的话，网页会一直显示上一帧的旧值，
   看着像"还在跟踪"，其实早就丢了目标 —— 这种假象在现场最难识破。
2. **`pnp_*` 和 `target_*` 是两套量，不能混看**：`pnp_yaw_rad` / `pnp_pitch_rad` 是**单帧 PnP 的原始观测**
   （`main.cpp:434-444`，`atan2(x, z)` / `−atan2(y, hypot(x, z))`，右正 / 上正），
   而 `target_yaw` / `target_pitch` 是 **EKF 滤波后的云台指令**。
   本轮 EKF 没做，所以 `target_*` 恒为 0，页面上真正有数的是 `pnp_*` 那一组。

pitch 不在 `armor_solve` 里，而是在 `main.cpp` 里从 `position_gimbal_m` 现算：
pitch 是"云台要抬多少"，跟云台当前姿态有关，不属于单帧解算的输出。

# 八、可能问的问题与回答

## 8.1「从干净目录怎么构建？」

```bash
rm -rf /tmp/rmbuild
cmake -S . -B /tmp/rmbuild
cmake --build /tmp/rmbuild -j$(nproc)
ctest --test-dir /tmp/rmbuild --output-on-failure    # 6/6
```

唯一需要外部条件的是海康 MVS SDK 装在 `/opt/MVS`；装在别处就用 `-DMVS_ROOT=<安装根目录>`。
SDK 没有 CMake 配置文件，所以用 `find_path` / `find_library` 手动找，找不到直接 `FATAL_ERROR`
并把"找过哪两个目录"打出来。

## 8.2「为什么把 MVS 的库目录烤进 rpath，而不是设环境变量？」

官方 Sample 的 Makefile 就是这么做的（`-Wl,-rpath=$(MVCAM_COMMON_RUNENV)/64`）。
MVS 的四个环境变量只写在 `~/.bashrc` 里，而本机登录 shell 是 zsh，干净终端里它们是空的 ——
靠环境变量就等于靠运气。烤进 rpath 之后跑自己的程序完全不依赖任何 MVS 环境变量。

## 8.3「通信结构体你改了吗？怎么证明？」

一字节没改，而且不是靠记忆：`Communication.hpp:50-76` 有一串 `static_assert`，
把 64 字节的总长、`Translator` 联合体的大小、以及**二十个字段的偏移量逐个**钉死。
谁挪了字段顺序、改了类型或编译器换了对齐规则，都会在编译阶段报错。
`#pragma pack(1)` 是因为这是线上布局而不是内存模型，不加编译器会插填充字节。

## 8.4「两个线程共享什么数据？怎么保护的？」

共享的只有读线程写、操作线程读的 `temp` 和时间戳，加一个"有没有数据"的标志，
三个都用同一把 `message_mutex` 保护。关键是**读的时候在锁里整体复制出来**，不逐字段读，
避免读到半新半旧的一帧；**时间戳和数据在同一把锁里更新**，否则会出现"数据是新的、
时间戳是旧的"这种撕裂，直接影响过期判断。

`translator` 和 `pic` 只属于操作线程，不需要锁。

## 8.5「`crc` 是什么？你实现 CRC 了吗？」

没有，一个校验和都没算。任务书 §3.2 明确 `crc` 表示 **EKF 状态**，不是通信校验和。
写进去的是 `TrackingState`：0 无目标、1 预测稳定、2 有目标但不稳定，
和任务书 §3.6 的定义一致。`AutoAimTypes.hpp` 里那句注释就是防止有人看到字段名叫 `crc`
就去写一个校验和。

## 8.6「相机参数在哪设？为什么要有顺序？」

`HikCamera.cpp:131-141`。曝光 5000 us、增益 0 dB、自动曝光/自动增益/自动白平衡全关。

**顺序是先关自动、再写值**。`ExposureAuto` 还开着的时候写 `ExposureTime` 会被自动曝光立刻覆盖，
**而且不报错**，只看到"设了没用"。白平衡必须关：AWB 在 Continuous 模式下会把红色往橙色推，
直接影响红蓝判色。

不用自动曝光是因为它的目标亮度由相机自己定，画面里灯一亮整幅图的灰度就变，
下游那些固定颜色阈值会被拖垮。第一批标定图就是这么废掉的。

## 8.7「你退出程序的时候崩过吗？」

崩过，而且时崩时不崩，栈顶还落在 MVS 自己的线程里。根因是 `atexit` 的执行顺序：
**按注册的逆序执行**。MVS 在 `Initialize` / `OpenDevice` 那一串里自己注册了退出清理；
我的注册点如果放在 `StartGrabbing` 之前，就变成"我注册得更早、跑得更晚"，
轮到我清理时设备已经被它释放了 —— `StopGrabbing` 报 0x80000000（无效句柄），
`DestroyHandle` 在已释放的内存上再释放一次，段错误。

解法是把注册点推到 `StartGrabbing` **之后**，比 SDK 注册得晚、于是跑在它前面，清理时设备还活着。
实测四个调用全部返回 0x0。所以那一行 `std::atexit` 的位置是有意义的，注释里写了"别往上挪"。

## 8.8「像素格式转换为什么不用 `cv::cvtColor`？」

MVS 的 `"BayerRG8"` 与 OpenCV 的 `COLOR_BayerRG` 是不是同一个相位，官方没说。
猜错了 R/B 会对调 —— **而且不报错**，只会让红蓝队判反。所以直接交给 SDK 转成
`PixelType_Gvsp_BGR8_Packed`，从源头不给自己猜的机会。

顺带两个必须做的：行列数用 `nExtendWidth` / `nExtendHeight` 而不是 `nWidth` / `nHeight`
（Bayer 图可能有对齐填充，本机 1440 恰好是 4 的倍数、现在两者数值相同，但这是巧合）；
`MV_CC_FreeImageBuffer` 无论转换成功还是失败都要调，不还的话几十帧就把 SDK 的缓冲池耗干净。

## 8.9「相机掉线怎么办？」

两级。`HikCamera` 里单次失败只计数并返回 `false`；连着失败 5 次就 `close()` 放掉句柄，
下一帧自动重新枚举、重开 —— 相机拔了再插能自己恢复。上层 `main.cpp` 里连续空帧超过 3 次
才结束操作线程。分开的好处是"重连成功"和"彻底没了"是两种不同的处理。

## 8.10「标定怎么做的？你怎么知道标定是对的？」

MATLAB R2024b 的 `cameraCalibrator`，99 张棋盘格（9×12 方块、25 mm/格），
结果写进 `config/camera.yaml`：fx 1806.7 / fy 1804.4 / cx 743.4 / cy 526.1，
畸变 `[-0.0818, 0.1680, 0, 0, -0.0283]`，平均重投影误差 0.0753 px。

**判据不是重投影误差，而是画面四角的径向缩放因子 `1 + k1r² + k2r⁴ + k3r⁶`。**
第一轮重投影误差同样是 0.0753 px，但四角缩到了 0.66；原因是第一轮的棋盘格只覆盖到画面 44% 半径，
高阶畸变系数在无约束区域外推。第二轮补拍后四角都是 0.9896，正常镜头落在 0.98~1.02。

这条要背熟：**低重投影误差 ≠ 标定正确**，它只反映棋盘格覆盖到的那块区域拟合得怎么样。

## 8.11「外参 R 为什么是单位阵？是占位值吗？」

不是占位值，是那个约定下的真值。学长答复"相机系和云台系只有平移、没有旋转"，
把云台系定义成与相机系各轴同向、原点取云台旋转中心，两个系的三个轴就一一平行，旋转就是单位阵。

另一套同样自洽的约定是枪管系（x 前 / y 左 / z 上，`armor/include/BulletModel.hpp:6`），
那时 R 是 90° 置换矩阵。任务书只要求"说明各轴方向"，没规定用哪一套，两套都对。
代价是接 EKF 和弹道那一步要补一个置换。

**要主动说明的一点**：相机支架如果本身有安装偏角，那是一个**真实的物理旋转**，
与坐标系怎么命名无关，需要另行标定（固定棋盘格 + 云台扫位姿 + `cv::calibrateHandEye`）。
`R = I` 只覆盖"命名"这一层。

**另外 `t` 的正负号还没和学长复核**，两种定义方向相反，配置里按字段定义取了负号；
确认后如果反过来只改那三个数，代码和图都不用动。

## 8.12「配置写错了会怎样？」

`main` 在起线程之前就检查，不合法直接打印原因并 `EXIT_FAILURE`，不会带着错参数跑。
检查项包括：`calibrated == 1`、图像尺寸 > 0、四个矩阵的类型与维度、`cv::checkRange`
（NaN / Inf）、重投影误差 ≥ 0、`fx > 0` 且 `fy > 0`、`det(R) ≈ +1`、`‖RᵀR − I‖ < 1e-2`。

**为什么不警告一下继续跑**：拿占位参数解出来的距离看着完全正常、实际全错，比"没有结果"难查得多，
任务书 §3.3 也要求"缺失或非法时明确报错退出"。`armor_solve` 里还有第二道兜底。

## 8.13「识别管线有哪几步？在哪？」

颜色掩膜 -> 灯条提取 -> 灯条配对 -> 一对一选择 -> 角点 -> 大小分类 -> 数字分类 -> NMS。
函数和行号见第五节开头的表。`armor_detect` 本身只做转发，算法都在 `ArmorDetector` 里，
这样能脱离相机单独测。完整逐行解析另有两份：`docs/答辩-检测管线.md`（①②⑥⑦）、
`docs/答辩-数字分类代码.md`（⑥）。

## 8.14「颜色阈值 60 / 100 是怎么定的？」

从海康那 69 张整图上量出来的。`|B−R| < 20` 的像素占 99.78%（背景、场地、地板全在这里），
`|B−R| ≥ 120` 的只占 0.13%（灯条本体）。加上主通道 > 100 之后，一帧只剩 0~8 个斑块，
69 帧平均 2.6 个。

60 落在"背景极密、灯条极疏"中间的空档里，两边都有近 5 倍余量，所以在 60 附近挪动不会突然崩。
顺带说明**为什么必须是带符号的差**：用 `|B−R|` 红蓝两队会看到一模一样的结果，
对面队伍的车全变成目标，而且不报任何错。

## 8.15「四根灯条为什么只出一块板？」

这是本轮修的一个大 bug。之前四根灯条会被拆成三个框。判据 5（中间不能夹第三根灯条）
和 NMS 都挡不住"相邻两对共用一根灯条"。

修法是新增 `choosePairs`：按分数贪心、一根灯条只用一次，用 `used[]` 表记账。
判据 5 和 NMS 都保留着 —— 判据 5 管"这一对中间有没有夹东西"，
`choosePairs` 管"全局上一根灯条被谁用了"，NMS 管"两块真板挨太近、外接矩形真的叠了"，
三件事互不代替。

同时把数字奖励从 10 降到 2，并加上"必须真有板面"的前提：真板的板面项封顶只有 +1，
奖励只要 > 1，一个误报的数字就必然压过一块板面看得清清楚楚的真板。

## 8.16「数字分类准确率多少？这个数字能信吗？」

**同源留出集上 99.97%**（3557/3559，LINEAR 核 C=1），每类 recall 都 ≥ 99.9%。
但报告里一律写成"同源留出集"而不是"识别准确率"，因为这个数字有明确的适用范围：
留出集和训练集来自同一批采集，连杂讯都同分布，**它在原理上就检测不出域偏移**。

所以另有一套能真正检验"分类器学的是不是字形"的三个诊断，每次训练都打印：
只留边缘（把补丁中心挖空重训）、去掉边缘（裁到 16×24 重训）、同源留出。
如果"只留边缘"就能超过 90%，说明模型在靠边缘杂讯分类、字形没学到 —— 那是危险信号。

**要主动承认的**：数据集是别人裁好的，我没有它的裁剪代码。"居中 + 全板高 + 40.7 mm 宽"
是三条实测线索推出的**假设**，不是已知。所以留了一个机械化的验证手段：
拿真实帧跑 `extractDigitPatch` 把补丁落盘成 PNG，算逐列/逐行白占比剖面，
和数据集同类剖面求相关系数。相关系数高就说明裁剪假设成立。这一步不需要人眼判断、也不需要标注。

## 8.17「目标丢失怎么处理？」

分两层。检测层面：板子检测到了但中间没有数字时，这块板**仍然返回**（角点有效、PnP 能用），
只是 `target_id = 0`，下游 `applyPrediction` 用 `target_id != 0` 把开火闸住。
不做成"整块丢掉"，是因为那样会让"检测坏了"和"分类坏了"在 Web Debug 上长得一模一样
（`armor_count` 都是 0），两种故障没法区分。

帧层面：`detectArmors` 入口就接受空图和各种异常输入，**不假定每帧一定有目标**；
`main.cpp` 里连续空帧会用黑帧走完流程但最终强制输出无目标；控制器数据超过 500 ms 没更新，
直接降级成安全帧。

## 8.18「PnP 的解怎么保证是可信的？」

四道闸：未标定、角点退化（有向面积 < 1，**不取绝对值**）、深度非法（< 0.05 m 或 > 30 m）、
误差异常（> 5 px）。

**必须先说清楚一件事**：`solvePnP` 对几乎所有坏输入都返回成功。角点缩到 2% 时它给出 100 m，
角点摆成蝶形时给过 z = 5e11，角点顺序反了它给镜像解 —— 这三种的返回值都是 `true`、
重投影误差都是 0。所以返回值不能当校验用，必须自己按物理范围兜。

第 1 道闸不取绝对值这一点单独说：顺序反了的输入会得到"位置正确、法向翻转"的镜像解，
重投影误差**仍然是 0**，误差和深度都拦不住，只有符号能拦。

**同时要说清楚四道闸拦不住什么**：大小判错（会变成 46° 的旋转误差，而重投影误差照样过闸）、
跨板配对（实测一个跨车假对的重投影误差 2.28 px，照样过闸）。这两类只能靠检测那一环保证。

## 8.19「Web Debug 上的 `target_yaw` 为什么一直是 0？」

因为 `target_*` 那一组是 **EKF 滤波后的云台指令**，而本轮没做 EKF，`ekf_predict` 返回空，
框架走 `setSafeOutput` 的安全帧，所以 `target_*` 恒为 0。页面上真正有数的是 `pnp_*` 那一组：
`pnp_yaw_rad` / `pnp_pitch_rad` 是**单帧 PnP 的原始观测**，`pnp_distance_m`、
`pnp_reprojection_error` 也是。这两组量是两回事，不能混看，`main.cpp:434-439` 的注释写了这一点。

另外没有观测时会显式写 −1，不会让网页停在上一帧的旧值上假装"还在跟踪"。

## 8.20「Eigen 和 Ceres 用在哪？」

**Eigen**：只出现在 `armor/` 的参考代码里 —— `KalmanFilter`（13 维状态的 EKF）和
`Planner`（`Planner.cpp:253-255` 有被注释掉的 `Eigen::AngleAxisf` 旋转，改成手展开的三角式）。
**`student/` 八个文件里一处 Eigen 都没有**，因为 Eigen 在这套流程里唯一的用处就是 EKF，
而那属于下一轮。

**Ceres**：本工程没有使用。它是第二次培训作业（`vision_training`）里拟合正弦角速度曲线用的，
在这条自瞄流程里没有对应的位置 —— 不是替代 EKF 的东西。

`CMakeLists.txt` 里虽然链了 Eigen（`target_link_libraries(algorithm_support PUBLIC Eigen3::Eigen)`），
那是给 `armor/` 的参考代码用的。

## 8.21「EKF 为什么没做？」

本轮范围是六个评分项、80 分，EKF 是独立的 20 分项，任务书把它列成 §3.6 的单独一节。
现在 `ekf_predict` 返回空，框架会走安全回包分支，**所以整条链路在没有 EKF 的情况下仍然跑得通
且不会误开火**。下一轮的计划是复用 `armor/include/KalmanFilter.hpp`（13 维状态的通用 EKF）
加上任务书 §3.6 要求的装甲板关联、切换和离群点拒绝。

## 8.22「本次踩的最大的坑是什么？」

两个，都是"不报错的错误"这一类：

1. **相机退出时序**（8.7 节）。`atexit` 逆序导致 double free，时崩时不崩，栈顶还落在 SDK 的线程里。
2. **标定的假正确**（8.10 节）。第一轮重投影误差 0.0753 px 很漂亮，实际四角缩到 0.66，
   根因是采样覆盖不足而不是算法。

第三个值得说但没造成事故的是**跨板配对**（8.15 节）：跨板那对的间距比 5.05 落在合法区间内、
五条判据全过、NMS 还按面积把它留了下来，最后裁剪框落到了中间那根灯条上。

这三个的共同点是：**都不会报错**。所以现在的做法是每个都留了能自动抓的检查 ——
编译期断言、四角缩放因子、判据 5 加一对一选择，而不是靠人记得。
