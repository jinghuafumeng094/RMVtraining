# EKF 初始化调整方案

日期：2026-10-13
适用：`student/src/ArmorEkf.cpp:436-447` 的初始化段
前一版结论：`docs/上车前问题清单.md` §2.7、`rm_autoaim_evidence/06-EKF跟踪与预测/20261013-ekf-fix-trials-候选修法全试过.md`

**一句话**：初始化的方位角方向取反了 180°。代码假设观测到的板**背对**相机，
而能被检出的板必然**面朝**相机。改一行（`atan2(y,x)` 换成 `atan2(-y,-x)`）之后，
实测初始中心误差 0.50 m 变 0.02 m、收敛后 0.188 m 变 0.003 m，
半径从负数回到 0.248/0.252，而且不再 21 帧就报 `Stable`。

**状态（2026-10-13 晚）**：第七节 ①②③④ 已实施并提交 `d3a7ff3`，
`ctest` 7/7 通过。第五节（可观测性门）还没做，见改动后的第五、七、八节。

## 一、根因

初始化段（`ArmorEkf.cpp:436-447`，下面引的是修复前的式子）把**板心相对世界原点**的方位角，
当成了**板心相对旋转中心**的方位角：

```cpp
x_[Yaw] = wrapToPi(std::atan2(init_mean_.y(), init_mean_.x()));
x_[Px] = init_mean_.x() - config_.initial_radius_m * std::cos(x_[Yaw]);
x_[Py] = init_mean_.y() - config_.initial_radius_m * std::sin(x_[Yaw]);
```

`x_[Yaw]` 这个量在模型里的含义是槽位 0 的 `psi`，也就是**中心指向板心的径向方位**。
代码给它的取值是**原点指向板心的视线方位**。两者只有在车心恰在世界原点时才相等。

换成向量的说法更清楚。记

- `r_hat`：中心指向板心的单位径向（板装在外侧，板面法向就是它）
- `p_hat`：原点（相机）指向板心的单位视线
- `delta`：`r_hat` 与 `-p_hat` 的夹角，也就是这块板被看到的**斜角**

代码隐含假设 `r_hat = p_hat`。但检测条件是"板面法向与指向相机的方向夹角小于锥角"，
即 `angle(r_hat, -p_hat) = delta < 锥角`，所以真实关系是 **`r_hat` 约等于 `-p_hat`**。
假设方向整整反了 180°。

初始中心误差就是两个假设向量之差乘以半径：

| 假设 | 中心误差 | `delta` 在可见范围 `[0°, 80°)` 内的取值 |
|---|---|---|
| 现状 `r_hat = p_hat` | `2r·cos(delta/2)` | `(0.383, 0.50]` m |
| 取反 `r_hat = -p_hat` | `2r·sin(delta/2)` | `[0, 0.321)` m |

取 `r = 0.25` m。正对相机时 `delta = 0`：现状偏 0.50 m，取反偏 0；
掠射到锥角边缘 `delta = 80°`：现状偏 0.383 m，取反偏 0.321 m。
在 `delta < 90°` 的整个范围内 `sin(delta/2) < cos(delta/2)`，
所以**凡是能被检出的姿态，取反都严格优于现状**。这不是调参，是把一个符号改回来。

（`delta > 90°` 也就是板在车的远侧、面朝外背离相机的那半边，现状反而是对的。
但那半边根本检不出来，实车数据里不会出现。测试夹具里会出现，见第四节。）

## 三、为什么前面三份证据没到这一层

前面把根因归到"半径自由度"再归到"初始化窗口"，那一层是**下游**：
初始化偏了，滤波器才挪用半径去拟合。这一层是初始化的**输入方向**本身错了。

`ekf_trace` 的合成观测由 `ArmorEkf::observationModel` 生成，
只喂**可见的那些板**（`visiblePlates`，锥角 80°），与真实检测口径一致，
所以它能复现。而下面的测试夹具口径不一致，所以它复现不出来。

## 四、配套必改：测试夹具（已完成，提交 `d3a7ff3`）

`tests/test_ekf_predict.cpp` 的 `feedFrame` 原来**无条件**发 `plate_count` 块板：

```cpp
for (int index = 0; index < config.plate_count; ++index) {   // 旧
```

对一辆四板车、车心在 (4, 0.3, 0.6) m，这等于每帧发两块**背对相机**的板。
真实检测器永远不会输出这种配置。夹具把错误方向当成了正确方向，
这正是这条 bug 能在测试全绿的情况下活下来的原因。

改后加了与 `testrig/ekf_trace` 的 `visiblePlates` 同源的 80 度锥角判据，
只发那时真实可见的一到两块。板高表从 `{0, 0, 0.15, 0}` 改回出厂默认全零——
那个抬高原本是想在断言里唯一确定 `theta_c`，实测它把真实可见性下的收敛拖到几千帧，
改成在断言里避开等价关系（板位按集合比，`worstPlateMatch`）。

### 旧夹具把结论反过来这件事，比"不真实"更严重

`var_fix_四块全喂前12帧.txt` 是**改对的那一版**在旧口径下的前 12 帧：
第 2 帧完成初始化用的是那块背对相机的板，方向反了 `2r`；同一帧剩下的三条观测又在这个
偏离 `2r` 的状态上做最近槽位关联，被拽到错的槽位，500 帧里拒绝 1728 次、
偏航以 4.8 rad/s 自转、半径塌到 0.05。

反过来，**写反的那一版**在旧口径下第一块板是背对相机的，它的视线方位恰好等于径向方位，
初始化反而对了。旧口径不是"少验证了一件事"，它会主动把初始化方向的错判反过来。
所以初始化相关的一切判断都必须在可见性口径下做。

## 五、第二层：可观测性门（还没做，先留证据）

理由与取反正交：取反修的是"初始化偏在哪个方向"，
它不改变"只看见一块板时旋转中心根本不可观测"这件事。
取反在这条轨迹上之所以晚报 Stable，是因为误差小、协方差收得慢，
属于**涌现行为，不是保证**。换一条轨迹（比如卡在锥角边缘的掠射姿态）就可能又 21 帧报 Stable。

**扫过 `omega` × 初始朝向 `theta0` 的实测（1500 帧，车心 (4, 0, 0.5)，半径 0.28/0.22）**，
记录首次进 `Stable` 那一刻的中心误差，原始输出 `var_fix_初始朝向扫描.txt` /
`var_base_初始朝向扫描.txt`：

- 改后：**最差 0.108 m**（`omega = 2.0`、`theta0 = 60` 度），之后修到 0.0000；
  半径全程在 0.21~0.31 之间，没有负值。
- 旧版：最差 **0.582 m**，末态半径多次是负的（`-0.302/0.187`、`-0.060/0.349`），错解的指纹。
- `theta0 = 40/50/60` 度、`omega = 0.4` 那几行两个变体数字逐位相同：这两支规范等价
  （错开一格、`theta_c` 差 pi、半径互换），可观量一样，不能当"旧版也对"的证据。

### 门到底值不值：实测推翻了本节原来的理由（2026-10-13 晚）

原来写的是"门能把这条缝收掉"。为定这件事又扫了一遍：在夹具层面记录每帧可见板的
**槽位奇偶**（这些跑拒绝次数近似为零，可见约等于被接受），算出门最早哪一帧允许报
Stable，与现在的实现哪一帧报 Stable 对比。27 行 × 两个变体，
原始输出 `var_fix_门的代价扫描.txt` / `var_base_门的代价扫描.txt`。

1. **门是免费的。** 改后 23/27 行、旧版 25/27 行报过 Stable，这些行里**没有一行**门推迟过
   首帧（门开帧总是不晚于首帧）。决定何时报 Stable 的是协方差与 `hit_streak`，
   它们比"车转过 90 度"慢得多。
2. **但门也堵不住这条缝，原来的理由是错的。** 首帧误差最大的 9 行（0.084~0.108 m）
   **门开帧全是 0**：相机一开始就同时看得见两个奇偶的板。门的用处是防半径简并
   （差 180° 的两块板同奇偶），不是防中心误差。

⇒ 要收那条缝，杠杆在协方差阈值，不在门。门仍然可以加（确实免费），但别指望它解决这件事。
（这里数的是可见而不是被接受，拒绝多时真实的门只会更晚开，所以"免费"这条对真实实现是乐观侧，
"堵不住"这条不受影响。）

做法（若要做）：在 `advanceStateMachine`（`ArmorEkf.cpp:623`）的 Unstable 转 Stable 条件里加一条

```
去过偶数槽位的观测 && 去过奇数槽位的观测
```

- 用**槽位奇偶**而不是"见过几块板"，因为 `radiusIndex`（`:166`）按奇偶分 `r1`/`r2`：
  两块相差 180° 的板落在**同奇偶**槽位，打破不了半径简并，只数块数是错的。
- 判据只在"观测被接受"时置位（过了三道闸的才算）。
- 代价：车若恰好不自转（`omega = 0`），可见的永远是同一个槽位，门会一直挡住。

### 顺带量到的一处稳态残差

上面那条扫描里 `omega = 2.0`、`theta0 = 50/60 度` 的 0.10 m 是**暂时**的，接着掉到 0.0000。
但同一张表上慢转那几行是稳态偏差：

| omega | theta0 | 首帧误差 | 末帧误差 | 末帧半径 | 真值半径 |
|---|---|---|---|---|---|
| 0.4 | 40~60 度 | 0.080 m | **0.052 m** | 0.309 / 0.177 | 0.28 / 0.22 |
| 2.0 | 50~60 度 | 0.103~0.108 m | 0.0000 m | 0.280 / 0.220 | 0.28 / 0.22 |

0.4 rad/s 跑 1500 帧（约 9 s）收敛到的是偏差 0.052 m、半径分成 0.309/0.177 的解，
半径和 0.486 对 0.50 还勉强，末态仍在报 Stable。这是"车转得慢 + 每次只看一块板"
下这套模型的真实精度上限，不是 bug，但报告里不该省。

### 另一条实测限制：完全不转的目标永远不报 Stable

`omega` 恰为 0 时偏航的规范自由度永远不收缩，`covarianceIsStable()` 的 `yaw_std < 0.10`
永远过不去（改后在 3000 帧里始终没进 Stable，静止车与云台扫两种场景都是）。
门要不要连带处理这件事，和"静止车该怎么处置"是同一个问题，先记在这里。

## 九、复现

```bash
cd /tmp/rm_ekf_fix
echo 'x_[Yaw] = wrapToPi(std::atan2(-init_mean_.y(), -init_mean_.x()));'   # 取反那一行
bash build.sh ArmorEkf_base.cpp ekf_base ekf_trace.cpp
bash build.sh ArmorEkf_G.cpp    ekf_G    ekf_trace.cpp
./ekf_base --direct > var_base_direct.txt
./ekf_G    --direct > var_G_direct.txt
```

`--direct` 才打内部 `x_`，负半径只在内部看得见（`:912-913` 上报前已经 `std::max(0.0, ...)`）。
没有 `--fast`：必须真睡够帧间隔，否则 `ekf_predict` 内部量到的 latency 会被截到 0.2 s。
