# 一、为什么必须是六个文件

不是把代码拆碎了好看，是**每一刀都切在一个真实存在的风险上**。

## 1.1 为什么要一个**离线训练**程序，而不是在运行时学

SVM 训练是凸二次规划，**没有 epoch、没有学习率、没有反向传播、不用 GPU**。
但它要几千张图、要划分训练/测试、要算混淆矩阵 —— 这些都不该在实时循环里做。

所以切成：离线训一次 → 存成 XML → 现场只做推理。

## 1.2 为什么特征代码**只有一份**（这是最关键的一刀）

训练程序 `tools/train_digit_svm.cpp` 和推理程序 `DigitClassifier.cpp`
**调的是同一个 `DigitClassifier::describe()` 函数** —— 同一个 `.cpp` 被编进了
两个不同的可执行文件：

```cmake
# CMakeLists.txt:76-84 —— 训练程序只借 DigitClassifier.cpp 一份源码
add_executable(train_digit_svm
    tools/train_digit_svm.cpp
    student/src/DigitClassifier.cpp)
target_link_libraries(train_digit_svm PRIVATE ${OpenCV_LIBS})   # 只链 OpenCV
```

`CMakeLists.txt:71-75` 的注释把理由写死了：

> 这两个**故意不链 `training_core`**：只借 `DigitClassifier.cpp` 一份源码，
> 链 OpenCV 就够了。链了 `training_core` 会把 `serialPort`、相机那套全拖进来。

**为什么这条最重要**：如果训练和推理各自实现一遍 HOG（比如训练用 Python、
推理用 C++），两边的 cell 大小、block 步长、gamma 归一化只要有**一个参数**不一致，
就会变成"训练 99%、现场 30%"—— 而且**训练侧的指标一切正常，什么都看不出来**。
用同一份源码，这件事从物理上不可能发生。

## 1.3 为什么 `DigitClassifier.hpp` 只依赖 `opencv2/core.hpp`

```cpp
// DigitClassifier.hpp:10-12
// 这个头文件只依赖 OpenCV 的 core 和标准库，故意不依赖 ArmorDetector.hpp /
// AutoAimTypes.hpp。原因是训练程序也要用它 ——
// 训练程序只需要 OpenCV，不该被迫拖进相机、串口那一堆依赖。
```

这是 1.2 得以成立的前提：头文件不干净，训练程序就链不进来。

## 1.4 为什么类别表只定义一份

```cpp
// DigitClassifier.cpp:19-23
constexpr const char* kClassNames[] = {
    "1", "2", "3", "4", "5", "6outpost", "7guard", "8base", "9neg"};
// label → target_id。9neg 是"这块 ROI 里没有数字"，所以给 0。
constexpr int kTargetIds[] = {1, 2, 3, 4, 5, 6, 7, 8, 0};
```

训练程序用 `DigitClassifier::className(label)` 拼数据集目录名，
推理程序用 `targetIdForLabel(label)` 转编号 —— **同一张表，两处都用它**。
表本身对不上会怎样？见 4.6。

# 二、这一段新用到的语法

只列前面文档里没出现过的。

## 2.1 `cv::HOGDescriptor` —— 构造参数**就是**特征的定义

```cpp
// DigitClassifier.cpp:33-38
cv::HOGDescriptor& hog() {
    static cv::HOGDescriptor instance(
        cv::Size(DigitClassifier::kPatchWidth, DigitClassifier::kPatchHeight),  // winSize (20,28)
        cv::Size(10, 14),   // blockSize
        cv::Size(5, 7),     // blockStride
        cv::Size(5, 7),     // cellSize
        9);                 // nbins
    return instance;
}
```

这五个数不是"超参数"，它们**唯一确定了特征是什么**。算一遍：

```
win 20x28, cell 5x7      → 20/5 = 4 列，28/7 = 4 行，共 4x4 = 16 个 cell
block 10x14 = 2x2 cell   → 每块 4 个 cell
blockStride 5x7 = 1 个cell → block 排 3 列 x 3 行 = 9 个
每个 cell 9 个 bin        → 9 block x 4 cell x 9 bin = 324 维
```

手算 324，`getDescriptorSize()` 实测也是 **324**（这一条有断言钉住：
`test_digit_classifier.cpp:74`）。所以 `kFeatureSize = 324` 不是抄来的，
是算出来又验过的。

## 2.2 函数内的 `static` —— 只初始化一次，而且线程安全

上面 `hog()` 里那个 `static cv::HOGDescriptor instance(...)`：

- **为什么要 static**：`HOGDescriptor` 构造时要算一堆内部查找表。每秒 60 帧
  各造一个，是纯浪费。
- **为什么线程安全**：C++11 起，函数内静态变量的初始化由编译器保证
  **只执行一次**，且多线程并发调用也安全。所以不需要额外加锁 —— 代码注释
  里把这句写出来了（`DigitClassifier.cpp:31-32`）。

## 2.3 `std::lock_guard` —— RAII 的锁

```cpp
// DigitClassifier.cpp:242
std::lock_guard<std::mutex> lock(modelMutex());
```

构造函数里加锁、析构函数里解锁。好处是**中途 `return` 或抛异常都会自动解锁**
（`tryLoadLocked` 里真的会抛 `cv::Exception`，见 3.4）。

`modelMutex()` 和 `model()` 都是"函数内 static 单例"的老套路：

```cpp
std::mutex& modelMutex() { static std::mutex instance; return instance; }
Model& model() { static Model instance; return instance; }
```

**单线程程序为什么要加锁**：主循环是单线程，但 Web Debug 那边有别的线程在读。
注释说得很直白：「加锁的成本远低于一个偶发数据竞争带来的调试成本」
（`DigitClassifier.cpp:69-71`）。

## 2.4 `cv::Mat::row()` 是**不连续**的行视图

```cpp
// DigitClassifier.cpp:243-245
// clone：row() 是不连续的行视图，clone 成一块连续内存再喂给 predict，
// 免得踩到 OpenCV 对"一行样本"的内存假设。
svm.predict(features.row(index).clone(), out);
```

`features` 是一个 `N x 324` 的矩阵，`row(i)` 拿到的是第 i 行，但它的内存
**不是连续的** —— 步长还是整行的宽度。大多数 OpenCV 函数能处理这种情况，
但"单行样本"这种边界输入不保证。`clone()` 一次，把风险消掉。

## 2.5 参数默认实参 `= {}`

```cpp
// ArmorDetector.hpp:117
bool extractDigitPatch(const cv::Mat& image, const std::array<cv::Point2f, 4>& corners,
                       ArmorSize size, cv::Mat& patch, const PatchParams& params = {});
```

`= {}` 的意思是"不传就用 `PatchParams` 自己的默认值"（即 `PatchParams{}`）。
好处是测试和现场可以只写四行：

```cpp
extractDigitPatch(img, corners, size, patch);          // 用默认参数
extractDigitPatch(img, corners, size, patch, tuned);   // 现场换一组
```

这个写法在 `ArmorDetector.hpp` 里有四处（`:117` `:143` `:200` `:247`），
四个参数结构体各一处。

## 2.6 `glob()` 而不是 `std::filesystem`

两个离线工具都用 POSIX 的 `glob()` 遍历数据集目录：

```cpp
// train_digit_svm.cpp:66-77
// glob 默认按文件名排序，顺序确定 —— 可复现性的一部分。
std::vector<std::string> globFiles(const std::string& pattern) { ... }
```

**为什么不用 `std::filesystem`**：`glob` 保证**按字典序返回**，这是可复现性的
一部分。同一份数据集换台机器跑，样本顺序一样 → 划分结果一样 → 训练出的模型
逐位一样。这条在 5.2 的"复现"里是要兑现的。

（顺便：`std::filesystem` 在 GCC 8 上还得额外链 `stdc++fs`，`glob` 没这问题。）

# 三、逐行讲解

## 3.1 `extractDigitPatch`（`ArmorDetector.cpp:229-320`）—— 角点 → 28×20 补丁

这是**推理链路上最容易写错的一步**，也是唯一一步"写错了还会正常跑"。

### 第 234 行：先清空输出

```cpp
patch.release();
```

无论成功还是失败，调用方拿到的都是干净状态 —— 和 `get_pic` 同一个约定。
否则调用方可能误用上一帧的补丁，而**上一帧的补丁是能通过所有格式检查的**
（28×20、CV_8UC1、{0,255}），一路错到底都不报错。

### 第 236-242 行：两道提前返回

```cpp
if (image.empty() || params.px_per_mm <= 0.0F || params.out_width <= 0 ||
    params.out_height <= 0 || params.patch_quad_scale <= 0.0F) {
    return false;
}
if (std::fabs(quadSignedArea(corners)) < kMinQuadAreaPx) {   // kMinQuadAreaPx = 1.0F
    return false;
}
```

- 第一道拦**参数非法**：除零、负尺寸、撑大倍数非正。
- 第二道拦**四点退化**：面积趋近 0 的四边形没有透视变换的解。

注意这里的 `kMinQuadAreaPx = 1.0F`（`ArmorDetector.cpp:210`）和
`DetectParams::min_quad_area_px = 100.0F` **是两个常数**。
`detectArmors` 在 `:540` 用 100 那道拦过一遍了，这里 1.0 是
"这个函数被单独调用时"的兜底 —— 它是个**自卫检查**，不是业务判据。

### 第 244-247 行：转灰度

```cpp
cv::Mat gray;
if (!toGray(image, gray)) { return false; }
```

`toGray` 只接受 `CV_8UC1` 和 `CV_8UC3`，别的返回 `false`（不猜通道顺序）。
和 `buildColorMask` 同一个态度：**宁可不做，也不猜**。

### 第 253-284 行：**第一级变换** —— 先把四边形撑大，再正射到"保物理比例的规范板"

```cpp
const float plate_width_mm = (size == ArmorSize::Large)
                                 ? params.large_width_mm    // 230mm
                                 : params.small_width_mm;   // 135mm
const int canonical_w = std::max(1, (int)std::lround(plate_width_mm * params.px_per_mm));
const int canonical_h = std::max(1, (int)std::lround(params.plate_height_mm * params.px_per_mm));
```

`px_per_mm = 2.0`、`plate_height_mm = 57` → `canonical_h = 114`；
小板 `canonical_w = 270`，大板 `canonical_w = 460`。

#### 但正射之前要先做一件事：把四边形撑大（`:262-274`）

检测出的四边形**只框住两根灯条**，而牌面上那幅图案（数字或哨兵图标）**比灯条高一截**
—— 实拍量下来约 **1.7 倍**。照着原四边形裁，第二级取出的窗只能覆盖图案中间一条
竖窄带，分类器拿到的基本是噪声。所以先把四边形**绕中心等比撑大** `patch_quad_scale` 倍
（默认 **2.0**）：

```cpp
const cv::Point2f quad_center =
    (corners[0] + corners[1] + corners[2] + corners[3]) * 0.25F;
const std::vector<cv::Point2f> source{
    quad_center + (corners[0] - quad_center) * params.patch_quad_scale,
    quad_center + (corners[1] - quad_center) * params.patch_quad_scale,
    quad_center + (corners[2] - quad_center) * params.patch_quad_scale,
    quad_center + (corners[3] - quad_center) * params.patch_quad_scale};
```

两点必须讲清，答辩很可能追问：

- **撑大的只是这里的局部副本。** `corners` 是 `const` 引用，检测输出的角点、
  要喂给 PnP 的那四个点**一个都没变**。是"抠数字时借一个更大的框"，
  不是"把检测框改大" —— 后者会让位姿解算跟着错。
- **必须在原图上撑开再正射。** 反过来"先正射、再在规范板里取大窗"没用 ——
  四边形外面没有真实像素，取到的只是边缘拉丝。已实测：那样做置信度只有 0.64 且不收敛。

实测（三张实拍帧、同一份 `armor_digit_svm.xml`、同一套未改的检测管线）：

| `patch_quad_scale` | 直播帧 | 队里 10-08 A | 队里 10-08 B |
|---|---|---|---|
| **1.0（旧行为）** | 0 (0.57) | 0 (0.56) | **4 (0.35)** ← 三帧三个不同答案 |
| 1.6 | 7 (0.70) | 7 (0.71) | 7 (0.70) |
| **2.0（默认）** | **7 (0.74)** | **7 (0.74)** | **7 (0.75)** |

`1.0` 时三帧给出三个**不同**答案，说明输入里没有判别信息、只剩噪声；`≥1.6` 时三帧
一致收敛。峰值在 2.0~2.2——**这不是真值，是标定值**，换镜头/机型/板子都要重标。

**为什么不能一步到位映射到 20×28** —— 这是整段的核心：

```
装甲板物理尺寸   135 : 57  ≈ 2.37   （横的）
数据集补丁        20 : 28  ≈ 0.71   （竖的）
                    ↓ 直接映射
               数字被横向压扁约 3.3 倍
```

**而且不会报任何错**，只会准确率掉下来。所以必须两级：
先把四边形正射成**保持物理比例**的规范板，再从规范板里裁数字框。

这一段还顺手做了一件好事：`cv::warpPerspective` 把**透视畸变也一起去掉了**。
四边形被拉成矩形，所以**斜着看板子也能得到端正的数字** —— 不需要额外处理。

```cpp
const std::vector<cv::Point2f> destination{
    {0.0F, 0.0F},
    {(float)(canonical_w - 1), 0.0F},
    {(float)(canonical_w - 1), (float)(canonical_h - 1)},
    {0.0F, (float)(canonical_h - 1)}};
```

目标点的顺序必须和 `corners` 的约定一致（左上、右上、右下、左下）。
**顺序错了会得到旋转或镜像的补丁** —— 又是一个静默错误。

### 第 286-303 行：**第二级变换** —— 从规范板中央裁出数字框

```cpp
const int box_h = canonical_h;                      // 框高 = 撑大后四边形的整高（114）
const int box_w = std::max(1, (int)std::lround(box_h * params.digit_aspect));
const int safe_w = std::min(box_w, canonical_w);    // 绝不越界
const int box_x = (canonical_w - safe_w) / 2;       // 居中
const cv::Mat box = canonical(cv::Rect(box_x, 0, safe_w, box_h));
```

**为什么框高取"整个四边形高"而不是"字形高度"**（`ArmorDetector.cpp:287-289`）：

> 数据集里量过，墨迹高度只占补丁高的 **0.68~0.95** 倍，说明人家裁的时候就留了余量。
> 我们按字形裁会得到一个比训练数据更紧的裁剪，分布对不上。

注意这个"整个四边形高"是**撑大后**的四边形：`box_h = canonical_h = 114px`，
而撑大 2 倍后规范板是 1 像素 = 1mm，所以窗高 = **114mm** —— 图案的上下缘都进来了。

**为什么框宽不是独立参数**（`:291-294`）：

> 框宽不是独立参数：它和框高、纵横比三者只有两个自由度。
> 纵横比定成 20:28（= 数据集补丁的比例），框宽就唯一确定了。
> 默认下框高 114px = 114mm，框宽 = **114 × 20/28 ≈ 81mm**。

这是一处**很值得讲的推理**：三个量（框宽、框高、纵横比）里只有两个自由度，
所以"框高 = 撑大后四边形整高"和"纵横比 = 20:28"两条一交代，框宽就唯一了。
**它不是一个可以随便调的参数** —— 调它等于破坏"和数据集同比例"这条前提。

> **修订（2026-10-10）**：这里原来写的是 **57 × 20/28 ≈ 40.7mm** —— 那是
> `patch_quad_scale` 加进来**之前**的口径。四边形撑大 2 倍后，规范板每像素代表的
> 毫米数从 0.5mm 变成 1mm，窗跟着变成 81mm。推理链（两个自由度定框宽）完全不变，
> 只是代入的数换了。

### 第 305-319 行：缩放 + 二值化 —— **顺序不能反**

```cpp
// 顺序很重要：必须"先缩放、再阈值"。
cv::resize(box, resized, cv::Size(params.out_width, params.out_height), 0.0, 0.0,
           cv::INTER_AREA);
cv::threshold(resized, patch, 0.0, 255.0, cv::THRESH_BINARY | cv::THRESH_OTSU);
```

**为什么不能反过来**：`INTER_AREA` 是**取平均**的缩放。如果先阈值再缩放，
它会把 0 和 255 平均成中间灰度 —— 输出就不再是数据集那种 `{0, 255}` 二值图。
**不报错，只是准确率悄悄掉**。

**为什么用 Otsu**：阈值由这张小图自己的直方图算出来，不用手调，
所以对现场的光照变化比固定阈值皮实。

**为什么是 `THRESH_BINARY` 而非 `_INV`**：数据集是**白数字 + 黑底**。
万一现场抠出来极性相反，把常量换成 `THRESH_BINARY_INV` 即可 ——
但**换之前得先知道极性错了**，见 4.1。

**返回值契约**：成功时 `patch` 是 28 行 × 20 列、`CV_8UC1`、取值只可能是
`{0, 255}`。三条都有断言逐像素钉住（`tests/test_armor_detect.cpp:255-266`）。

这一段还有两个**很强**的用例，值得单独讲，因为它们钉住的正是本节说的那两个坑：

**用例一：纵横比**（`test_armor_detect.cpp:268-280`）——在 20mm 的白方块上量
补丁里的白框尺寸，然后断言：

```cpp
// ↓ 这一条是关键。把四个角点一步 getPerspectiveTransform 到 20x28 的
//   实现，会让宽度压成 ≈3、高度还是 ≈10，宽高差 7 > 3，立刻红。
assert(std::abs(box[0] - box[1]) <= 3);
```

也就是说，**"两步变换"这个设计是被一条具体的断言保护的**：
只要有人图省事改成一步到位，这条立刻变红。下一个断言还拿大板（230mm）
再量一遍，同时钉住"`size` 参数真的被用上了"。

**用例二：Otsu vs 固定阈值**（`test_armor_detect.cpp:297-320`）——
构造一张低对比度图（背景 30、亮块 100）：

```cpp
// Otsu 会自己从直方图里找刀口（≈65），固定阈值 128 会把整幅判成黑，
// 数字直接丢干净。少了这一条，"把 Otsu 换成固定阈值"这种改动
// 在两个 0/255 的极端之间看不出任何差别，测试抓不住。
```

这解释了**为什么测试要造低对比度输入**：只在 0/255 的干净图上测，
`THRESH_OTSU` 和固定阈值 128 的结果**一模一样**，测不出区别。

## 3.2 `DigitClassifier::describe`（`DigitClassifier.cpp:177-187`）—— 补丁 → 324 维

```cpp
std::vector<float> DigitClassifier::describe(const cv::Mat& patch) {
    std::vector<float> descriptor;
    // 三个条件缺一不可。尺寸判断要写 cols/rows 而不是 rows/cols ——
    // 20 和 28 反了的话，HOG 会算出完全不同的特征，而且一声不吭。
    if (patch.empty() || patch.type() != CV_8UC1 ||
        patch.cols != kPatchWidth || patch.rows != kPatchHeight) {
        return descriptor;      // 空 vector = 特征不可用
    }
    hog().compute(patch, descriptor);
    return descriptor;
}
```

三个检查缺一不可：

| 检查 | 挡的是什么 |
|---|---|
| `patch.empty()` | 上一级扣图失败 |
| `type() != CV_8UC1` | 喂了彩色图或浮点图 → HOG 算出完全不同的东西 |
| `cols != 20 \|\| rows != 28` | **长宽写反** → 特征完全不同，**一声不吭** |

**为什么失败时返回空 vector 而不是抛异常**：调用方（`classify`）用
`descriptor.empty()` 判断，走降级路径。现场掉文件、喂错图，都该降级而不是崩。

> 注意 `cols` 对应的是**宽 20**，`rows` 对应的是**高 28**。
> 这一行写反是这段最隐蔽的 bug 之一：`HOGDescriptor` 的 winSize 是 `(20, 28)`
> = `(宽, 高)`，和 `cv::Mat` 的 `(rows, cols)` 顺序**正好相反**。
> 两个 API 的约定不同，写在一起就是陷阱。

## 3.3 `DigitClassifier::ready` + `tryLoadLocked` —— 懒加载与严格准入

### 3.3.1 `ready()`（`:189-217`）：三态，而不是两态

```cpp
bool DigitClassifier::ready() {
    std::lock_guard<std::mutex> lock(modelMutex());
    Model& state = model();
    if (state.loaded) { return true; }
    if (state.attempted) { return false; }   // ← 关键：失败过就不再试
    state.attempted = true;
    ... 先试编进二进制的绝对路径，再试相对路径 ...
}
```

`Model` 里有两个 bool（`:61-67`）：

```cpp
bool loaded{false};     // 当前真的有可用模型
bool attempted{false};  // 已经试过加载（含失败），不要再自动重试
```

**为什么要两态**：只有 `loaded` 一个的话，加载失败后**每帧都会再去开一次文件**。
`ready()` 每帧被调一次，60fps 就是每秒 60 次失败的文件打开 ——
白白消耗 I/O，还可能把日志刷爆。

**路径的两级回退**：

1. 先试 `ARMOR_SVM_PATH` —— 编译期宏，**绝对路径**，不依赖工作目录：

```cmake
# CMakeLists.txt:53-54
target_compile_definitions(training_core PRIVATE
    ARMOR_SVM_PATH="${CMAKE_CURRENT_SOURCE_DIR}/models/armor_digit_svm.xml")
```

2. 再试 `models/armor_digit_svm.xml` —— 相对路径兜底，从仓库根目录运行时能命中。

**为什么首选绝对路径**：现场可能从任何目录启动程序。相对路径会**静默失效**
（模型加载不上 → 所有 `target_id` 都返回 0 → 看起来像"检测不到数字"）。

### 3.3.2 `tryLoadLocked`（`:97-159`）：只接受一种模型

```cpp
if (svm->getKernelType() != cv::ml::SVM::LINEAR ||
    weights.rows != pair_count || weights.cols != DigitClassifier::kFeatureSize) {
    std::cerr << "[digit] 模型 " << path
              << " 不可用：需要线性核、且能取到 one-vs-one 原始权重。\n";
    return false;
}
```

**为什么只收线性核 + 压缩形式**：置信度要靠每个二分类器的**原始权重向量**算
（见 3.5）。RBF 核取不到这个 —— 每对的 "支持向量" 有很多个，不是单个权重。
与其让置信度退化成常数，**不如在加载阶段就明确拒绝**，让问题暴露在这里
而不是答辩现场。

```cpp
// 压缩形式：每对只有一个"支持向量"，就是那个原始权重。
if (alpha.total() != 1 || svidx.total() != 1) {
    std::cerr << "[digit] 决策函数 " << p << " 不是压缩形式…\n";
    return false;
}
Pair pair;
pair.weight_row = svidx.at<int>(0);   // 权重在 getSupportVectors() 里的行号
pair.rho = rho;                       // 偏置
```

这个 `Pair` 结构（`:54-59`）是后面置信度计算的全部依据：

```cpp
struct Pair {
    int first;        // 这对里的类别 A
    int second;       // 类别 B，first < second
    int weight_row;   // 权重在 getSupportVectors() 里的行号
    float rho;        // 偏置
};
```

**枚举顺序必须和 OpenCV 内部一致**：`(0,1) (0,2) … (0,8) (1,2) …`，
就是下面这个双层循环（`:126-128`）：

```cpp
for (int i = 0; i < class_count; ++i)
    for (int j = i + 1; j < class_count; ++j, ++p)
```

顺序错了会怎样？`getDecisionFunction(p, ...)` 拿到的 `rho` 和
`getSupportVectors()` 的行号会对不上 —— **置信度全错、标签可能还是对的**。
这种错在准确率上完全看不出来（准确率只用标签），只在置信度上烂掉。

### 3.3.3 加载失败绝不崩

```cpp
} catch (const cv::Exception& error) {
    std::cerr << "[digit] 加载模型失败 " << path << "：" << error.what() << std::endl;
    return false;
}
```

`SVM::load` 在文件不存在时会**抛 `cv::Exception`**，所以必须接住。
模型丢了是要**降级运行**，不是要让整个程序挂掉。

降级的形态是：`ready()` 返回 false → `classify()` 返回 `{target_id=0, confidence=0}`
→ 但 `armor_detect` **仍然返回有效的角点**（见 0 节那 7 行，抠补丁/分类失败
**不 `continue`**）。于是 Web Debug 上能把两种故障分开：

| 现象 | 含义 |
|---|---|
| `armor_count == 0` | **检测**坏了（掩膜/灯条/配对） |
| `armor_count > 0` 但 `detection_id == 0` | **分类**坏了（模型没加载 / 补丁抠失败） |

这就是评分表「目标丢失处理」和「关键数据可观测」要的东西。

## 3.4 `DigitClassifier::classify`（`:231-301`）—— 推理 + 置信度

### 第 233-240 行：先 `ready()`，再取特征

```cpp
DigitResult result;              // 默认 {target_id = 0, confidence = 0}
if (!ready()) { return result; }
const std::vector<float> descriptor = describe(patch);
if (descriptor.empty()) { return result; }
```

**注意顺序**：`ready()` 会加锁，`describe()` 不加锁。所以 `ready()` 返回后
锁已经释放了，中间可以安全地做耗时较多的特征计算。之后真正要用 `model()` 时
**再重新加锁**（`:242`）并**重新检查 `state.loaded`**（`:244`）：

```cpp
std::lock_guard<std::mutex> lock(modelMutex());
Model& state = model();
if (!state.loaded || state.svm.empty()) { return result; }   // 期间被别人换掉了
```

这个"加锁—放开—重算—再加锁—再检查"的模式叫**双重检查**。少了第二次检查，
就可能拿着已经 `release()` 掉的 `svm` 去 `predict`。

### 第 250-258 行：零拷贝包一个样本矩阵

```cpp
const cv::Mat sample(1, (int)descriptor.size(), CV_32F,
                     const_cast<float*>(descriptor.data()));
```

`cv::Mat` 可以用"外部内存"构造 —— 不拷贝，直接包住 `descriptor` 的连续内存。
`descriptor` 在本次调用结束前一直活着，所以安全。
`const_cast` 是因为 `cv::Mat` 的构造函数只收非 const 指针，但这里只是读。

**不用 `cv::Mat(descriptor)`** 是因为那样会得到一个 `324 x 1` 的列向量，
而 `predict` 要的是 `1 x 324` 的一行样本。

### 第 261-299 行：置信度 —— 冠军在所有对局里的**最小**间隔

这是整段最需要讲清楚的地方。

```cpp
bool have_margin = false;
float worst = 0.0F;
for (const Pair& pair : state.pairs) {
    int sign = 0;
    if (pair.first == label) { sign = 1; }
    else if (pair.second == label) { sign = -1; }
    else { continue; }               // 跟冠军无关的对局，不影响结论

    const float dfval =
        (float)state.weights.row(pair.weight_row).dot(sample) - pair.rho;
    const float signed_margin = dfval * (float)sign;
    if (!have_margin || signed_margin < worst) {
        worst = signed_margin;
        have_margin = true;
    }
}
result.confidence = 1.0F / (1.0F + std::exp(-worst));
```

**逐步拆解**：

1. **只关心冠军参与的那 8 场对局**。9 类里，冠军 `label` 每次都在其中——
   作为 `first` 还是 `second` 决定符号（`sign`）。其余 28 场与它无关。
2. **每场的间隔是 `w · x - rho`**。线性核下，OpenCV 把每个二分类器压缩成
   "一个原始权重向量 + 一个偏置 rho"。**符号约定：`> 0` 表示 `pair.first` 胜**
   （`:52-53` 的注释：实测 1440 个"样本 × 它自己参与的每一对"，符号符合率 100%；
   写成 `+ rho` 只有 81%，是错的）。
3. **乘上 `sign` 变成"以冠军为正"的有符号间隔**：`> 0` = 冠军赢了这个对手。
4. **取最小值，不取平均**。只要有一个对手没被明显压住，就不该报高置信度——
   这正是"这个数字和某个易混数字之间只差一点"的样子。
5. **过一道 sigmoid**：把 `(-∞, +∞)` 压到 `(0, 1)`，且以 **0.5 为界**。
   低于 0.5 意味着"预测出的这个类，至少输给过某个对手"，是实打实的没把握。

**为什么不能直接用 `predict(..., RAW_OUTPUT)`**（`:41-53` 的注释，这段值得背下来）：

> 多类情况下 `predict(..., RAW_OUTPUT)` **返回的是类别标签本身**，不是决策函数值
> （实测：类 1 的样本 raw 恒为 0.0，类 2 恒为 1.0，…… 类 9neg 恒为 8.0）。
> 拿它当 margin ⇒ 置信度变成"预测出哪个数字"的纯函数，跟输入图像毫无关系，
> 而且看起来还挺像回事（数字越大越"可信"）—— 这是最难发现的那种错。

**诚实说明**（`:293-298`，答辩要主动说）：

> C++ 版的 `cv::ml::SVM` 没有 `setProbability`/`getProbability`（Python 版才有），
> 所以拿不到**标定概率**。这里给的是"最小间隔经过 sigmoid"的**单调映射** ——
> 它只保证"离分界面越远越大"，**不是**"有 92% 的概率是这个数字"。
> 用它排序、显示、卡阈值都可以，但当概率解释会错。

测试里 `test_digit_classifier.cpp:157-161` 钉住了一条强的：**判对的那一张，
置信度必须 > 0.5**（冠军确实正面赢过每个对手）。这条能抓住符号写反 ——
符号错了值会整体掉到 0.5 以下，但**数值照样在 [0,1] 里、照样随输入变化**，
只有这一条抓得住。

### 3.6.2 `readManifest`（`:86-105`）—— 一个真实的血案


修正后的写法是**逐行读、跳过 `#` 开头**：

```cpp

    if (first == std::string::npos || line[first] == '#') { continue; }
    std::istringstream stream(line);
    std::string relative; int label = 0;
    if (stream >> relative >> label) { keys.insert(relative); }
}
```

而且 `main` 里还有两道拦截：

第二道的意思是：**清单里的每一个键都必须真的在数据集里认领到一张图**。
认不到就说明路径拼法对不上（目录名写错、数据集换版本……），
后果是那张图照旧进训练集 —— **又是静默泄漏**。所以这里直接拦死。

> **这个坑的教训**：数据泄漏不会让指标变难看，只会让它**变好看**。
> 所以防它的代码必须"宁可跑不起来，也不许悄悄跑过去"。

### 3.6.4 `stratifiedSplit`（`:182-200`）—— 为什么必须分层


### 3.6.5 三种输入变体 —— 回答"模型学的是不是字形"

```cpp
enum class Mode { Full, CenterOnly, BorderOnly };
```

```cpp
// train_digit_svm.cpp:107-125  applyMode
// CenterOnly：把最外 2 像素的框涂黑，只留中心
// BorderOnly：反过来，把中心涂黑，只留最外 2 像素的框
```

用**同一套 HOG 参数**处理三种输入，所以比较的是"**信息在哪里**"，
而不是"参数变了"。

`main` 里先各自训一个、各自测（`:366-371`），再做**交叉诊断**（`:383-389`）：

```cpp
printReport("完整模型 → 只留中心",   evaluate(*svm_full, features_center, ...));
printReport("完整模型 → 只留最外2px框", evaluate(*svm_full, features_border, ...));
```

**交叉诊断这几行才是决定性的**（`:375-382` 的注释）：

> "只留最外 2px 框"那 80% 看着吓人，但它测的是"边缘信息够不够用"，
> 不是"完整模型有没有在用边缘"。这两件事完全不同。
> 真正关系到现场风险的是第一行：完整模型喂进"边缘被涂掉"的输入
> （模拟现场补丁的外圈和数据集对不上），准确率掉不掉。
> **不掉 → 模型靠的是字形**，边缘那 80% 是数据集的伪线索，与部署风险无关。
> **掉 → 模型确实在依赖外圈**，现场就有得受了。

这正是 `docs/答辩问答.md` 5.5「你这 99.9% 是不是假的？」的**代码级答案**。

### 3.6.6 最终模型用**全部**非留出图训练

```cpp
// train_digit_svm.cpp:396-403
const cv::Ptr<cv::ml::SVM> final_svm = trainSvm(features, samples, all_indices);
final_svm->save(model_out);
```

上面报的准确率是 80/20 划分上的**估计值**（比最终模型略悲观，这是正常的）；
真正提交的模型用**全部**非留出图训练 —— 样本更多，只会更强。
**留出集（180 张）从头到尾没参与训练**，留给 `test_digit_classifier` 评估。

## 3.7 `tools/make_digit_holdout.cpp` —— 抽留出集

### 3.7.1 固定种子洗牌，不是"取前 N 张"

```cpp
// 抽法是"每类固定种子洗牌后取前 N 张"，不是"取前 N 张"：
// 数据集很可能是按采集顺序排的，取前 N 张会让留出集全来自同一段时间、
// 同一种光照，测出来的数字会偏乐观。
std::mt19937 rng(1000U + static_cast<unsigned>(label));
std::shuffle(files.begin(), files.end(), rng);
```

种子带上 `label`，所以各类抽的是**不同的位置**，但每次都一样 →
换台机器、换次答辩，抽出来的是同一批图。

### 3.7.2 清单是训练和测试**共用**的同一份文件

```cpp
manifest << name << "/" << file_name << " " << label << "\n";
```

- 训练时 `train_digit_svm` 按它**排除**；
- 测试时 `test_digit_classifier` 按它**评估**。

同一份文件，所以**不可能出现"训练用了又拿去测"**。

## 3.8 `CMakeLists.txt` 里的三个 target

```cmake
# :36-54 主库，把 DigitClassifier.cpp 编进去，并注入模型绝对路径
add_library(training_core STATIC ... student/src/DigitClassifier.cpp)
target_compile_definitions(training_core PRIVATE
    ARMOR_SVM_PATH="${CMAKE_CURRENT_SOURCE_DIR}/models/armor_digit_svm.xml")

# :107-113 测试：注进留出集目录，注册到 ctest

```

**两个宏的区别**：

> 链 OpenCV 就够了。链了 `training_core` 会把 `serialPort`、相机那套全拖进来。

# 四、这一段埋着的静默错误

**"静默错误"= 不报错、不崩、看起来正常，只是结果悄悄变差。**
这一段有 7 个，全部写在代码注释里。答辩被问"你怎么保证实现对"，
这一张表就是答案。

| # | 错误 | 后果 | 在哪被挡 |
|---|---|---|---|
| 1 | **极性反了**：`THRESH_BINARY` / `_INV` 选错 | HOG 特征变成"补集"，准确率崩塌 | 只能靠**实拍验证**（见 5.3）；代码里留了注释指路 |
| 2 | **顺序反了**：先阈值再缩放 | `INTER_AREA` 把 0/255 平均成灰，不再是二值 | 代码注释 `ArmorDetector.cpp:293-296`；`patch` 值域 ⊆ {0,255} 有断言 |
| 3 | **`rows`/`cols` 写反**（20 ↔ 28） | HOG 算出完全不同的 324 维 | `describe` 里的尺寸检查 + 断言 `:84` |
| 4 | **`winSize` 写反** `(20,28)` ↔ `(28,20)` | 同上 | `getDescriptorSize() == 324` 断言 |
| 5 | **置信度用了 `RAW_OUTPUT`** | 置信度变成"预测出哪个数字"的纯函数，与图像无关 | `test_digit_classifier.cpp:181`（"置信度是常数"断死） |
| 6 | **间隔符号写 `+rho`** | 置信度整体掉到 0.5 以下 | `:157-161`（判对的必须 > 0.5） |
| 7 | **类别表两边不一致** | 准确率正常显示，但每个数字指向错的板 | 表只有一份（1.4）；`className`/`targetIdForLabel` 都有断言 |

外加一个不属于"静默"但同样致命的 —— **数据泄漏**（3.6.2），
它会让指标**变好看**而不是变难看，挡它的是清单 + 两道硬拦截。

> **这 7 条的共同点**：它们的实现**完全满足接口契约**
> （返回 28×20 的 `CV_8UC1`、置信度在 [0,1] 内、类型全对），
> 编译通过、测试的"形状类"断言也全过。**只有端到端准确率会掉。**
> 所以这段的测试重点不是"形状对不对"，而是"数值有没有信息量"——
> 比如 `confidence_max - confidence_min > 1e-6`（恒返回 1.0 的实现在 [0,1]
> 契约下完全合法，只有这一条能抓住）。

## 5.2 预期输出

训练程序会打印三组东西：

**第一组 —— 三种输入各自训、各自测**（回答"信息在哪里"）：

| 行 | 预期 |
|---|---|
| `完整补丁` | ≈ **99.9%** |
| `只留中心（外圈涂黑）` | 略低，但不塌 |
| `只留最外2px框` | 明显低（若 > 90% → **特征方案有问题，要回头改设计**） |

**第二组 —— 交叉诊断**（回答"模型有没有在用边缘"）：
`完整模型 → 只留中心` 若**接近**"完整补丁"那一行，说明外圈丢了也不影响判字，
模型的依据是**字形**。

**第三组 —— 混淆矩阵**，以及最终模型落盘。

**测试侧**：`ctest` 应该是 **5/5**：

| 测试名 | 覆盖 |
|---|---|
| `scaffold_safety` | 通信结构体 64 字节不变、字段映射（红线） |
| `armor_detect_geometry` | ③④⑤ + **⑥ 补丁契约/纵横比/Otsu** |
| `armor_detect_pipeline` | ①②⑥串联⑦（掩膜、灯条、配对、NMS） |
| `digit_classifier` | 特征维度、类别表、留出集准确率、置信度 |
| `cli_help` | `rmv_training --help` 能正常退出 |

`digit_classifier` 会打印留出集准确率（阈值 0.95 / 每类 0.85）和置信度区间。

> 阈值为什么定 0.95 而不是 0.99（`test_digit_classifier.cpp:187-189`）：
> 留出集只有每类 20 张，**一张就是 5%**。定到 99% 会让阈值本身比噪声还细 ——
> 那是自欺。

**重复跑两次，准确率必须逐位相同**（固定种子）。做不到就说明有非确定性来源。

## 5.3 拿到真实帧后补的两步（2026-10-10 已做）

这两步都只需要**一张真实帧**，相机一到手就能做。**2026-10-10 相机到手后已做，而且
第一步真的抓到了一个 bug**：

1. **域匹配**：真实帧跑 `armor_detect` → `extractDigitPatch` → 把补丁落盘成 PNG →
   算**逐列/逐行白占比剖面** → 和数据集里同类别的剖面求**相关系数**。
   低就调 `px_per_mm` / 裁剪宽度 / 是否居中。
   （做法在 `docs/答辩问答.md` 5.1；数据集剖面数据也在那里。）

   **结果：问题不在 `px_per_mm`，也不在裁剪宽度，而是窗从一开始就太窄。**
   量下来灯条四边形只有 90px 高，而牌面上的图案有 ~150px 高（≈1.7 倍）——
   照着原四边形裁只能覆盖图案中间一条竖窄带。修法是先把四边形**绕中心撑大**
   （`patch_quad_scale`，默认 2.0，见 3.1），三帧随即一致判出 `7guard`。
   证据：`rm_autoaim_evidence/04-装甲板识别/数字补丁-裁框诊断/`。
2. **极性**：数据集是**白数字 + 黑底**。若现场抠出来是反的，准确率会**静默崩塌**。
   同一张落盘 PNG 里一起看就行 —— 极性反了，白占比会整体翻转。

   **结果：极性正确**。修好后补丁是白图案 + 黑底（白像素占比 ~29%），与数据集同向，
   不需要把 `THRESH_BINARY` 换成 `THRESH_BINARY_INV`。

> 这两步**不需要标注、不需要人眼判断**，只有"一张真实帧"这一个前提。

# 六、这一段的缺口（被问到要老实说）

和 `docs/答辩问答.md` 5.6 是同一份清单，这里只补**代码层面**的两条：

1. **`px_per_mm = 2.0` 仍是"起步值"。**
   注释说"再大只是让中间那张图更贵、再小会让 114 像素高的板降到 57 开始丢笔画"——
   这是**推理**。2026-10-10 的实拍验证（5.3）证明**它够用**：修好裁框后三帧都能
   稳定判出结果，说明 2.0 这个中间分辨率没有丢掉判别信息。但"2.0 是不是最优"没测过，
   也不必测 —— 它只影响中间那张图的分辨率，对最终 20×28 没有增益。

2. **`patch_quad_scale = 2.0` 是标定值，不是真值；"编号对不对"还没闭环。**
   这个数来自三帧同型目标的实测（见 3.1 的表），换镜头 / 换机型 / 换板子都要重标。
   更要紧的一条：`digit_aspect = 20/28` 与"框高 = 撑大后四边形整高"这条链现在
   **在实拍上能跑通、三帧一致**，但**没有真值标注**证明板上那个编号就是对的那一类。
   现场确认板子编号之后，这条才算真正闭环 —— 被问到要这么说。
