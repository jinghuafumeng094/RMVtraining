# 零、全景：数据怎么流过这几百行

一帧的数据流：

```
相机 -> 检测 -> PnP  ->  observations: vector<ArmorPose>   云台系板心
                        gimbal: GimbalState                电控下发的当前姿态
                                    |
                        ekf_predict(observations, gimbal, timestamp_seconds)
                                    |
        predict(dt) -> update(每条观测) -> advanceStateMachine(ts) -> buildPrediction(gimbal, latency)
                                    |
                            PredictionResult
                                    |
                    applyPrediction -> 64 字节串口帧
                    logPrediction   -> Web Debug 曲线
```

四个方法每帧按这个顺序各调一次，这是整个类唯一的入口约定（`ArmorEkf.hpp:138-146`）。

`ArmorEkf` 只依赖 Eigen 和标准库，不依赖 OpenCV。所以它可以独立构造，单测直接测类，不走适配器。

# 一、坐标系：为什么非要一个世界系

见 `ArmorEkf.hpp:20-29`。

云台是会转的。同一辆静止的敌车，在云台系里每帧坐标都在变。运动模型如果建在云台系里，滤波器会把**云台的转动**当成**目标的运动**，估出来的速度是废的。所以分成两系：

| 记号 | 各轴 | 谁在用 |
|---|---|---|
| **W 世界系** | x 前、y 左、z 上 | 车体位置、速度、yaw、半径全部住在这里；`armor/include/BulletModel.hpp:6` 的弹道模型也在这个系 |
| **G 云台系** | x 前、y 左、z 上 | `ArmorPose::position_gimbal_m` 在这里 |

## 1.1 原点在哪，为什么两系只差一个旋转矩阵

**两系共用一个原点，就是云台的 P 轴原点。** 这也是外参平移那一项的起点：`config/camera.yaml` 写着「云台 P 轴 -> 相机光心 = (67.11, 0, 51.5) mm」。所以 W 既不是场地原点，也不是车心，它随车一起平移。

**这条是定义，不是观测**，要讲清楚它是怎么来的，别答辩时被当成实测结论。

唯一直接的依据是变换函数里**没有平移项**（`:113-121`）。两系原点若不同，那里必须写成 `p_W = M · p_G + t`，多一个三维平移。代码没有这一项，所以「两系同原点」与「变换是纯旋转」是同一件事的两种说法，不是两条独立结论。

**也必须这么定，因为原点不同的世界系造不出来。** 要建一个原点另有所指的世界系，得知道我们自己在那个系里的位置。整条链路没有任何自定位：`GimbalState`（`AutoAimTypes.hpp:27-33`）只有 `yaw` / `pitch` / `roll` / `prediction_bias_s` 四个角和一个时间，一个位置量都没有；`PredictionResult` 报的是目标中心在 W 里的坐标，不是我们的位姿。没有场地位置、没有里程计。所以不是不想建，是建它需要的三个数拿不到，同原点是唯一能算的选择。

**handout 里没有这句话。** `云台外参.md` 只管云台系：正式部分写「相机原点在云台坐标系中的位置，即从云台原点指向相机原点的 3x1 平移向量」，正文写「相机光心到云台 P 轴的向量」，两句合起来只说明**云台原点 = 云台 P 轴**，即外参平移的起点，对世界系一个字没提。本文档目录下那张坐标系图里的「原点 = 云台旋转中心（P 轴）」也是我们自己标的，不是 handout 原话。

**还隐含一个小假设**：纯旋转等价于假设偏航轴正好穿过这个原点。云台原点是俯仰轴上的一个点，若那个参考点沿俯仰轴偏离了两轴交点 `d`，云台偏航时它会扫出半径 `d` 的圆，严格变换应多一个平移项，量级 `2d·sin(θg/2)`：`d = 1 cm` 转 90 度时约 1.4 cm，`d = 5 cm` 时约 7.1 cm。现在按 `d = 0` 处理，这是默认值，没有实测。要确认得问学长「P 轴那个参考点是不是俯仰轴与偏航轴的交点」。

### 为什么不把原点挪到我们自己的车心

「车心」有两种读法，这里先说我们自己的，目标车心另起一节。

**能挪。** 云台原点到我们自己车心是一个常向量：两点都在自己车上，而 W 不随云台 yaw 转，所以这个偏移在 W 里不随时间变。改原点就是 `p_W = p_W_原 - t`，整个状态平移一下，EKF 的估计一个字不用改。

**但没好处，代价却不小。**

一是**这个向量手上没有**。已知的只有两组：相机光心到云台 P 轴 (67.11, 0, 51.5) mm、云台 P 轴到摩擦轮 (74.1, 0, 0) mm，都出自 `云台外参.md`。云台 P 轴到车心，仓库里、handout 里、`config/` 里一处都没有。

二是**这个偏移永远估不出来，只能靠人给**。把它放进模型，会与目标中心位置完全共线：PnP 观测约束的是相对几何，`t` 偏多少、目标中心就跟着偏多少，两者在任何一帧里都分不开，不可观测。

三是**喂错了直接进瞄准角**。瞄准角是从原点指向瞄准点的方向，原点横移 δ 会让它偏大约 `δ / R`：

| 原点偏差 δ | 5 m 处的角度偏差 | 对照开火容差 |
|---|---|---|
| 5 cm | 0.010 rad = 0.57 度 | `fire_yaw_tolerance_rad = 0.02 rad` |
| 10 cm | 0.020 rad = 1.15 度 | 刚好吃光 |

重投影、深度、NIS 三个闸门都看不见这种偏差，因为偏差在参照系上，不在观测上。

四来**云台原点本来就是个更好的锚点**：它是三个轴的交点，按定义在俯仰轴上，所以俯仰时它不动；变换又假设偏航轴穿过它，所以偏航时它也不动；roll 同理。它是我们这辆车上唯一在云台任何转动下都不动的点。

**结论**：车心原点的世界系能建但没用。EKF 要的是相对几何，目标相对我们多远、往哪动、转多快，这些量换原点前后一样。换原点唯一改变的是上报的 `center_x/y/z`，一个常数平移。真想让「目标相对车心」更好读，应该在输出那一层减，不在状态里建。

### 更不行：把原点放在目标车心

如果「车心」指的是**目标车的车心**，那不是「划不划算」的问题，是根本立不住。三点。

**一、那个向量不是已知量，它就是状态本身。** 已知的常向量只有云台原点到相机光心（外参）。云台原点到目标车心是**每帧要估的未知量**，就是状态的前三维 `[Px, Py, Pz]`。它是整个系统里最难估的三个数，慢转 0.052 m 稳态残差与 `omega = 0` 不收敛说的都是它。拿它当原点，等于把要测的量定义掉了。

**二、PnP 给的是板心，不是车心。** 观测只有板心，从板心到车心要反解 `platePositionWorld`（`:196-203`）：

```
板心 = 车心 + r * (cos(psi), sin(psi), 0)        psi = theta_c + i * pi/2
```

反求车心要先知道 `theta_c`、`r`、`i` 三个量，而这三个正是滤波器在估的。单帧 3 个测量对 6 个未知，欠定。

**三、目标不转时连多帧都定不出来。** 车心可以绕着这块板滑一圈、同时把半径改掉，观测序列完全一样。这是深版 12.6.2 里 `omega = 0` 一列中心误差不收敛的成因，那条方向上的分量永远学不出来。所以「PnP 知道板的位置和距离，就也应该知道车心」这一步不成立：**板心是读出来的，车心是解出来的，而且解它需要目标在转。**

**四、原点只能放在量具所在的地方。** 观测是 PnP 出的板心，天然相对相机；外参把相机原点挪到云台原点，于是所有观测天然都是相对云台原点的。要让原点是目标车心，得先知道云台原点相对目标车心的位置，而整条链路没有自定位。就算估出来了，那个向量每帧都在变，原点跟着目标跑，车心恒等于零向量，那已经不是世界系而是目标体坐标系。

**要的其实另一样东西。** 如果目的是拿到「目标车心相对云台」这个读数，它现在就有：状态在 W 里，乘一次 `worldToGimbal(gimbal_yaw)` 即到云台系，`buildPrediction` 对瞄准点做的正是这件事（`:682-683`）。上报的 `center_x_m/y_m/z_m`（`:738-740`）是 **W 系口径**，注释里也这么写。想在 Web Debug 上加三个云台系口径的数，在输出层乘一次 `M^T` 即可，与「把原点挪走」不是一回事。

**两系用的是同一套轴的定义**，都是 x 前、y 左、z 上。注意朝左的是 y 不是 x：`theta_c` 用数学约定 `atan2(y, x)` 因此是左正，而 `gimbal.yaw` / `target_yaw` 用 `atan2(-y, x)` 是右正，见 1.3。

这里容易读岔，提前说清：「轴的定义相同」说的是两系对 x、y、z **各指什么东西**叫法一样，**不是任何时刻三根轴都指向同一个方向**。云台转过 `θg` 之后，G 的 x、y 相对 W 的 x、y 各偏了 `θg`，**只有 z 因为本身就是那根转动轴而始终同向**；`θg = 0` 的那一刻两系才完全重合成一套轴。这两层的关系见本节末「那这两个系到底差在哪」。

**只差一个旋转矩阵，两个原因，缺一个都不成立。**

1. **同原点，所以没有平移项。** 云台的 yaw 是绕过原点的竖直轴的纯转动，转完原点还在原地。对照相机系到云台系那一跳：相机光心不在云台原点上，离了前 67.11 mm、上 51.5 mm，所以那里必须带一个 `t`（`StudentTasks.cpp:167-168`）。
2. **只绕 z 转，所以 z 分量原样通过，而且矩阵正交。** 转动轴就是两系共同的 z，`M` 的第三行第三列是 1。正交且 `det = +1`，逆矩阵等于转置，`worldToGimbal` 才敢直接返回 `transpose()`（`:123-125`）。

一句话定义：**W 就是「把 yaw 读成 0」之后的那一帧云台系。** `θg = 0` 时 `M` 是单位阵，两系重合。

### 那这两个系到底差在哪

原点相同，**但轴向并不是「指向相同」**：两系共用的只是 x 前、y 左、z 上这套定义。云台转过 `θg` 之后，G 的 x、y 相对 W 的 x、y 各偏了 `θg`，只有 z 始终同向。所以「两系差在哪」要连着这一条看。

准确说法还是那一句：W 是「把 yaw 读成 0」之后的那一帧 G。两系的差别只有一个自由度，就是偏航角 `θg`，而这个角每帧都在变。`θg = 0` 的那一刻两者完完全全重合，`M` 是单位阵，三根轴也指向同一个方向；云台一转，G 跟着转，W 不转，x 与 y 立刻分开。**两个系是同一个系的两种状态，不是两个不同的系。**

`M` 就是这件差事的具体形式：把一个在某一系里量出来的坐标，改用另一系的轴重新表达。轴方向若真的一样，`M` 就该是单位阵，两系之分也就不必要了。它只混 x 和 y（第三行第三列是 1），正是「只有 x、y 分开、z 没分」的代码痕迹；观测雅可比里 `H.col(Pz) = to_gimbal * (0, 0, 1)` 算出来就是 `(0, 0, 1)`（`:183`），云台转角根本没进 z 那一分量。

看一组数字，`p_W = M(θg) · p_G`，取 `p_G = (5.00, 0, 0)`，也就是「云台正前方 5 m」这个方向：

| 云台 yaw | G 里的坐标 | 换到 W 里 |
|---|---|---|
| 0 | (5.00, 0, 0) | (5.00, 0, 0) |
| 右 30 度 | (5.00, 0, 0) | (4.33, -2.50, 0) |

第二行是重点：**同一组数字，在两个系里指的是两个不同的方向**，夹角正好是云台转过的 30 度。y 为负是右，所以「云台正前方 5 m」这个方向在 W 里看是右前方，因为云台自己已经往右转了 30 度。

反过来问也成立：若是一个**固定不动的目标点**、云台朝它转过去，那它的 W 坐标恒定，G 坐标跟着变。云台往右转 30 度，同一个点从 G 的 (5.00, 0, 0) 变成 (4.33, +2.50, 0)（y 为正是在左边，因为云台右转之后目标落到了视线的左侧）。两种问法算的是同一件事，只是把「谁不动」按在了不同的系上。

再加上第三种情形：目标真动了，G 和 W 会一起动；云台只是自己转、目标没动时，**只有 W 是安静的，G 在乱动**。这正是估计必须建在 W 里的原因。

两个系各自存在的理由，缺一不可：

- **观测只能从 G 进来**。相机固定在云台上，PnP 出的 `position_gimbal_m` 天然是云台系的坐标。
- **估计必须建在 W 里**。状态若直接建在 G 里，云台一转目标坐标就变，滤波器会把「云台在转」当成「目标在动」，估出来的速度是废的。

这和机器人里的 body frame / world frame 是同一个套路：同原点、同轴向定义、只差一个姿态，区别在于谁跟着机体转。答辩问「原点一样轴也一样，那不一样在哪」，答的就是这一句：**差在 G 跟着云台转、W 不跟着。**

### 它不是惯性系

名字比性质好听，两条限制要记住。

**随车平移**：原点在云台上，车一动原点就动。它只是「与云台 yaw 无关」，不是「与世界无关」。

**只去掉 yaw，没去掉 pitch**：`gimbal.pitch` 从头到尾没进过 `gimbalToWorld`，函数签名只收一个 `gimbal_yaw`。所以云台一抬头，整个 W 跟着俯仰一起转，静止目标在 W 里的坐标也会变。所以更准确的说法是「它其实是炮管系」。展开见下一节。

### 云台抬头了会怎样

前面几节讲的两系关系**一个字都不变**：云台抬头 10 度，G 和 W 一起抬 10 度，两系之间仍然只差一个偏航角 `θg`，`M` 仍然只混 x 和 y。变的是 **W 的 z 不再是竖直方向，而是炮管的「上」**。后果按严重程度排四条：

**一、上报的竖直量带上 `d · sin(pitch)` 的台阶。** `center_z_m` / `ekf_z_m` 是当绝对值报的，5 m 处抬头 10 度就差 0.87 m。这就是上车手册要求「读 z 之前先把俯仰归零」的原因。

**二、`vx` / `vz` 会吃到一段假速度。** 云台以 `φ̇` 抬头时，静止目标在 W 里的坐标也以 `d · φ̇` 旋转：5 m 处 30 度每秒就是 2.6 m/s。滤波器分辨不出这段运动是目标在动还是参照系在动，会照单收下。

**三、仰角指令多带一份提前量 `φ̇ · t_pred`。** 这条最要紧，因为它直接进开火判据。目标是静止的、就在正前方时，理想指令是仰角 0。代码把状态在 W 里外推到 `t_pred`，而 W 自身还在以 `φ̇` 转，预测到的仰角因此多出 `φ̇ · t_pred`，加回 `gimbal.pitch` 之后并不归零。30 度每秒、`t_pred` 约 0.22 s（5 m 的飞行时间 0.21 s 为主）时是 0.115 rad = 6.6 度，五倍于 0.02 rad 的容差。**对照 yaw 那一半**：正因为 yaw 被去掉了，同一情形下 `target_yaw = θg + rel_yaw` 精确归零；pitch 没去掉，这笔账就没平。**注意这一条与「不外推时精确抵消」不矛盾**：不外推时 `rel_pitch` 在炮管系里量、加回 `gimbal.pitch` 正好回到世界系仰角，误差为零；误差是外推那一步引进来的，随 `φ̇` 与 `t_pred` 一起长大。

**四、方位角基本不受影响。** 俯仰是绕 y 轴转，`y` 分量不动，而 `rel_yaw = atan2(-y, x)` 只看 `x` 与 `y` 的比例，偏差是 `φ` 的二阶小量。

**改法**：给 `gimbalToWorld` 补一层 `Ry`，`M = Rz(-yaw) · Ry(pitch)`，`p_W = M · p_G`。`worldToGimbal` 照旧返回转置，`:176-178` 那条「不手抄 `M^T`」的规矩正好用上：**只有这一个函数要改**。补完 W 是真水平系，第二、三条消失，第一条的台阶也没了，而 `target_pitch = gimbal.pitch + rel_pitch` 的抵消照旧成立（`rel_pitch` 变成「真世界里还差多少」，加回当前仰角仍回到世界系仰角）。

两个前提得先定：一是 `Ry(∓pitch)` 取哪个符号、串联顺序是不是先 yaw 后 pitch，要问电控；二是**要在上车扫 Q/R 之前改**，否则扫出来的噪声参数会把这份视在运动一并吃进去，等于给一个参照系的毛病配了套参数，之后再改就得重扫。

**上面四条是读代码加推算，没有实测过**，列为已知欠账，见 17.2。最省事的验证：目标不动、只抬云台俯仰，看 `ekf_z_m` 动不动；按现写法**会动**，补完 `Ry` 之后不该动。

## 1.2 唯一的变换函数

两系用的是同一套轴的定义（前 / 左 / 上），所以换系时不用改名、不用换序，方向上的差别只剩一个绕竖直轴（两系的 z）的偏航角 `θg = gimbal.yaw`。于是变换退化成纯旋转，没有基础变换：

```cpp
// ArmorEkf.cpp:113-121
Eigen::Matrix3d ArmorEkf::gimbalToWorld(double gimbal_yaw) {
    const double s = std::sin(gimbal_yaw);
    const double c = std::cos(gimbal_yaw);
    Eigen::Matrix3d m;
    m << c, s, 0.0,
         -s, c, 0.0,
         0.0, 0.0, 1.0;
    return m;
}
```

这个矩阵是整个第二阶段的符号地基，值得自己手验三条：

1. `θg = 0` 时是单位阵，视线朝 `+x`，也就是正前方。
2. 云台向右转 `θg > 0` 后，正前方的东西在世界系里落在 `x > 0`、`y < 0`。y 朝左，所以 y 为负就是右。对。
3. 展开就是 `M(θg) = Rz(-θg)`，行列式 `+1`，是纯旋转不是镜像。

`worldToGimbal` 直接返回它的转置（`:123-125`）。

### `gimbal.yaw` 是标量，矩阵只是它的包装

不要把两者当成一回事。`gimbal.yaw` 是电控给的一个 float，矩阵是拿这个数算出来的：

```cpp
double gimbal_yaw = gimbal.yaw;                  // 一个标量，单位 rad
Eigen::Matrix3d m = gimbalToWorld(gimbal_yaw);   // 由它算出的 3x3
```

9 个元素里只有 `cos` 和 `sin` 两个独立量，而这两个又都由同一个 `θg` 决定。所以矩阵不携带任何 yaw 之外的信息，**自由度只有 1，不是 9**。

包成矩阵的理由是它能直接作用在三维向量上，`p_W = M · p_G` 一句话写完，约定也不用散落到每个调用点。不包也等价：把方位角减掉 `θg`、半径和高度不动，结果一样。

同一个 yaw 在代码里有三处用法，只有一处是矩阵：

```
:682   to_gimbal  = worldToGimbal(gimbal_yaw)        // 包成矩阵
:686   rel_yaw    = gimbalAzimuth(to_gimbal * p_W)   // 从转回来的点里量角度
:751   target_yaw = gimbal_yaw + rel_yaw             // 标量直接相加
```

三行连着读：**先用 yaw 把世界系的点转回云台系，量一个相对角，最后又把同一个 yaw 加回去**。转出去又转回来，是因为 `target_yaw` 要的是世界系里的绝对方位角。最后那一行是标量加法，与矩阵无关；如果 yaw 本身就是矩阵，这里写不出来。

**它也不是「云台的姿态」。** 云台姿态是 3 个自由度，`GimbalState` 里确实有 `yaw` / `pitch` / `roll` 三个角，但 `gimbalToWorld` 只吃 yaw 一个：

| 电控给的角 | EKF 里的去向 |
|---|---|
| `yaw` | 唯一进变换的，`M(θg)` 全部由它决定 |
| `pitch` | 不进变换，只当绝对仰角参照（开火门、弹道回落的基准） |
| `roll` | 一次都没用过，只在 `main.cpp:115` 查有效性、`AppSupport.cpp:56` 透传 |

所以 `M` 是「云台姿态里 yaw 那一份」的矩阵形式，不等于云台姿态。没去掉 pitch，正是 1.1 里那条「它其实是炮管系」。

**这是全代码唯一允许出现坐标系变换的地方**。观测模型、雅可比、选板、输出四处都调这两个函数，谁都不许手抄矩阵元素。理由写在 `:176-178`：手抄等于把同一个约定写两遍，换约定时容易只改一处。

关键推论：**`gimbal.yaw` 是观测模型的输入，不是状态的一部分**。滤波器不需要估云台角，因为电控每帧直接告诉它。

## 1.3 两套 yaw 符号共存，是有意的

`ArmorEkf.hpp:34-38`。

- `theta_c`（状态第 6 维）是 W 系里的方位角，用数学约定 `atan2(y, x)`，而 y 朝左，所以**左为正**。
- `gimbal.yaw`、`target_yaw`、`pnp_yaw_rad` 用 `atan2(-y, x)`，**右为正**。

两者各自只在一个地方用一次，滤波器因此仍然自洽，不需要强行统一。

**但有个连带约束必须记住**：输出是 `target_yaw = gimbal_yaw + rel_yaw`，这要求两个操作数同号。一旦上车确认电控是左正，`ArmorEkf.cpp:44-46` 的 `gimbalAzimuth` 与 `main.cpp:448` 的 `pnp_yaw_rad` **必须一起翻**，只改一处会差两倍角。这条已写进 `docs/上车前问题清单.md` §1.5。

# 二、状态向量：10 维

```cpp
// ArmorEkf.hpp:12-18
//   x = [ px, py, pz, vx, vy, vz, theta_c, omega, r1, r2 ]^T
```

| 分量 | 下标 | 物理量 | 单位 |
|---|---|---|---|
| px py pz | 0 1 2 | 旋转中心在 W 系的位置 | m |
| vx vy vz | 3 4 5 | 旋转中心速度 | m/s |
| theta_c | 6 | 车体偏航角，W 系方位角，左为正 | rad |
| omega | 7 | 车体偏航角速度 | rad/s |
| r1 r2 | 8 9 | 偶数 / 奇数编号装甲板到旋转中心的半径 | m |

下标用枚举（`ArmorEkf.hpp:47-59`），文件里搜不到 `x_[0]` 这种写法。

三条设计理由：

**为什么状态里是「旋转中心」而不是「某一块板」**。车在转，板跟着转，板的坐标随时间摆动。只有中心是不动的。把中心当状态，过程模型就退化成匀速直线，`F` 里只剩 4 个 `dt`。

**两块半径为什么只有两个**。0 / 2 号板共用 r1，1 / 3 号共用 r2。这就是 `PredictionResult::radius_1_m` / `radius_2_m` 对应的东西（`AutoAimTypes.hpp:81-82`）。标准步兵两块板同量级，`r1 ≈ r2`；前哨站是三块交替半径。

**高度 `h_i` 为什么不进状态**（`ArmorEkf.hpp:62-76`）。高度只进一个方程 `z = pz + h_i`，而 `pz` 也只在那一个方程里出现。所以**高度方程和其余九个状态完全解耦**：滤波器把「当前看得见那块板」的真实高度吃进 `pz`，瞄准点照样对。填错的代价只有两个：`center_z_m` 这个上报量偏了，以及两块板同框那几帧的 `±Δh/2`。默认全零表示四块共面，对标准步兵是错的，但它不报错，只是静默偏一点点。

标准步兵与哨兵的真实高度表是「相对两块等高、相邻两块有高差」，也就是 `{h0, h1, h0, h1}`，与 `r1 / r2` 的奇偶配对同一套（`ArmorEkf.hpp:63-68`）。上车量出来按这个形状填。

# 三、主循环四步

```cpp
// ArmorEkf.hpp:138-146
filter.predict(dt);                                  // 1. 外推，x 和 P 都推到当前
for (const ArmorPose& o : observations) {
    filter.update(o, gimbal.yaw);                    // 2. 关联 + 门控 + 更新，每条观测一次
}
filter.advanceStateMachine(timestamp_seconds);       // 3. 状态迁移 + 超时重置
filter.buildPrediction(gimbal, latency_s);           // 4. 生成指令
```

三个必须记住的约定：

- **`predict` 一定先于 `update`**。它把 `F` 从上一帧推到这一帧，再把 `used_indices_`、`updated_this_frame_`、`init_used_this_frame_` 三个每帧标志清掉（`:306-308`）。
- **`advanceStateMachine` 每帧都要调，包括没有观测的帧**。数「连续丢了几帧」的是它，不是 `update`。
- **没有观测时 `update` 一次都不调**，但 `predict` 和 `advanceStateMachine` 照调。这就是「纯预测」的来源。

顺序反了的后果很隐蔽：先 `update` 后 `predict`，等于拿旧状态去关联新观测，滤波器能跑、曲线看着也平滑，只是每一帧都在用上一帧的 `F`。

# 四、预测步：`f`、`F`、`Q`

## 4.1 状态外推 `propagate`（`:209-214`）

```cpp
x[Px] += x[Vx] * dt;
x[Py] += x[Vy] * dt;
x[Pz] += x[Vz] * dt;
x[Yaw] = wrapToPi(x[Yaw] + x[YawRate] * dt);
```

匀速直线加匀角速度，半径不动。`theta_c` 外推后立刻包裹回 `(-π, π]`，这是防止角度跑到 `10π` 之后 `cos / sin` 精度掉光的主防线。

## 4.2 状态转移 `F`（`:216-222`）

```cpp
F.setIdentity();
F(Px, Vx) = dt;  F(Py, Vy) = dt;  F(Pz, Vz) = dt;  F(Yaw, YawRate) = dt;
```

10×10，单位阵加 4 个 `dt`。**和 `propagate` 逐字对应**，这是必须的：`F` 是 `f` 的雅可比，两者不一致时 `P` 长的速度和状态跑的速度对不上，短期看不出来，几秒后 `P` 会被喂爆。

## 4.3 过程噪声 `Q`（`:224-253`）

按**随机加速度模型**离散化。假设每个 `[位置, 速度]` 轴对的加速度是白噪声，功率谱密度 `σ_a²`，则

```
Q_pv = σ_a² · [[ dt^4/4, dt^3/2 ],
               [ dt^3/2, dt^2   ]]
```

```cpp
const double linear = config_.accel_noise_m_s2 * config_.accel_noise_m_s2;
for (const auto& pair : pairs) {
    Q(pair[0], pair[0]) = linear * dt4 / 4.0;
    Q(pair[0], pair[1]) = linear * dt3 / 2.0;
    Q(pair[1], pair[0]) = linear * dt3 / 2.0;
    Q(pair[1], pair[1]) = linear * dt2;
}
```

三个物理量各一份原料：

| 原料 | 默认 | 物理含义 |
|---|---|---|
| `accel_noise_m_s2` | 6.0 m/s² | 中心三轴加速度标准差。RM 步兵 0 到 20 m/s 约 1~2 秒，瞬时机动约 10 m/s²，取一半 |
| `angular_accel_noise_rad_s2` | 12.0 rad/s² | 车体 yaw 角加速度标准差，车能快速起旋停旋 |
| `radius_drift_m` | 0.2 m | 半径随机游走强度，另加地板 `(1 mm)²` 防冻死 |

**`Q` 是每帧现算的矩阵，那三个数是原料，不是「加权和」**。这点答辩最容易被问倒：`dt = 6 ms`（165 fps）时 `dt² = 3.6e-5`，`Q_vv = 6² × 3.6e-5 ≈ 1.3e-3`；`dt = 50 ms` 时涨到 0.09，差 70 倍。所以 `Q` 不能写死成一个常数矩阵。

半径那一行（`:247-252`）：

```cpp
const double radius_variance =
    std::max(config_.radius_drift_m * config_.radius_drift_m * dt2,
             config_.radius_variance_floor_m2);
```

半径物理上几乎不变，但完全给 0 会让滤波器把先验的 0.25 m 冻死、再也学不到真值。加地板是留一点自由度，不是「这里噪声真的这么大」。

# 五、观测模型 `h` 与雅可比 `H`

## 5.1 观测量的选择

**只用板心的三维坐标，不用任何角度**（`ArmorEkf.cpp:9-13`）。

理由：`armor_solve` 输出的 `armor_yaw` 实现成「板面法向的偏航角」，而任务书三处措辞指的是「板心方位角」，两者差 90 度。把它当观测量，符号错了会把整个滤波带偏，而且不会报错。三维板心没有这个歧义。

## 5.2 观测模型（`:153-165`）

```cpp
const int i = armor_index;
const double psi = x[Yaw] + static_cast<double>(i) * plate_spacing_rad;
const double radius = x[radiusIndex(i)];
Eigen::Vector3d u;
u << x[Px] + radius * std::cos(psi),
     x[Py] + radius * std::sin(psi),
     x[Pz] + plate_height_m[i];
return worldToGimbal(gimbal_yaw) * u;
```

三行读完：

1. 第 i 块板在 W 系里的方位角是 `psi_i = theta_c + i * spacing`，`spacing` 默认 90 度。所以 **`theta_c` 是 0 号板的方位角**，其余三块按编号顺序挂上去。
2. 板心 = 旋转中心 + 半径沿这个方位角。
3. 换回云台系，因为观测值本来就在云台系里。**`h` 和 `z` 同系**，不需要把观测搬到世界系；这是「运动模型放在 W 系、观测模型放在 G 系」这个设计的代价，只在这一处付。

编号必须已经折算到 `[0, plate_count)`（`normalizeIndex`，`:139-145`）。它用的是数学取模而不是 C++ 的 `%`，负数输入会转正。

## 5.3 雅可比 `H`（`:167-194`）

`h(x) = M(θg)^T · u(x)`，所以每一列就是 `M(θg)^T` 乘上 `u` 对该分量的偏导：

```cpp
H.col(Px) = to_gimbal * Eigen::Vector3d(1.0, 0.0, 0.0);
H.col(Py) = to_gimbal * Eigen::Vector3d(0.0, 1.0, 0.0);
H.col(Pz) = to_gimbal * Eigen::Vector3d(0.0, 0.0, 1.0);

const Eigen::Vector3d tangential(-std::sin(psi), std::cos(psi), 0.0);
const Eigen::Vector3d radial(std::cos(psi), std::sin(psi), 0.0);
H.col(Yaw)             = to_gimbal * (radius * tangential);
H.col(radiusIndex(i))  = to_gimbal * radial;
```

`vx`、`vy`、`vz`、`omega` 四列恒零：位置不依赖速度，板心不依赖角速度。

**对 `theta_c` 的偏导和对 `r` 的偏导差 90 度**，这是本文件里最值得单独记的一句（`:184-189` 的注释就是这条）：

- 方位角转一点，板沿**切向**动，长度是 `radius`。
- 半径长一点，板沿**径向**动，长度是 1。

图省事共用同一个向量，滤波在慢转时会收敛到错误的半径，而且重投影误差照样很小。

`H` 一律走 `worldToGimbal` 求，不手抄 `Mᵀ` 的元素（`:176-178`）。手推雅可比唯一的保险是 `tests/test_ekf_predict.cpp` 用有限差分逐元素对拍，容差 1e-6。

# 六、观测噪声 `R`（`:255-267`）

```cpp
const double d = z.norm();
const double lateral = config_.lateral_noise_scale * d + config_.lateral_noise_base_m;
const double depth   = config_.depth_noise_scale   * d + config_.depth_noise_base_m;
Eigen::Matrix3d R = Eigen::Matrix3d::Zero();
R(0, 0) = depth * depth;
R(1, 1) = lateral * lateral;
R(2, 2) = lateral * lateral;
```

**轴序**：云台系是前 / 左 / 上，第 0 个分量沿视线，也就是**深度**；1、2 两个是横向。单目深度靠板宽反推，比横向差 5 倍（`0.010·d` 对 `0.002·d`）。**放错轴不会报错**，只会让滤波器该信的不信、该松的不松，表现为收敛慢、稳态抖。

**数值来历**（`ArmorEkf.cpp:30-33`）：仓库里已经实测过角点抖动，1.08 m 处单次重投影 0.70~0.79 px、同一角点两帧间最多动 1.41 px。按 `delta_px · d / f`（`f` 约 1805 px）估横向约 `0.0006·d`，再留约 3 倍余量取 `0.002·d + 0.005`。深度按同比例放大。这两个数字不是拍的。

**`R` 是「填」的，不是「算」的**。和 `Q` 一样它每帧现算，但每帧只是把两个标量按当前距离线性插一下。填得对不对，运行时唯一的检验量是 NIS。

一个待办的内部张力：R 的余量取了 3 倍，而进 `Stable` 的 `nis_mean_gate = 8.0` 又要求 NIS 均值偏低，两者方向相反。深版 12 节有记录，尚未定论。

# 七、初始协方差 `P0`（`:269-282`）

```cpp
P(Px,Px) = P(Py,Py) = P(Pz,Pz) = 1.0;                 // 位置 1 m^2
P(Vx,Vx) = P(Vy,Vy) = 25.0;  P(Vz,Vz) = 9.0;          // 速度 5 m/s
P(Yaw,Yaw) = 0.25;                                    // 约 0.5 rad

```

`P0` 是**第三样东西**，和 `Q`、`R` 都不同：它只在初始化的那几帧起作用，之后被更新自然收缩。给大一点的用处是「初始更信观测」，前几帧收敛快。对角上的数就是「这个量初始化时可能差多少」的标准差平方。

三者的关系别混：`P = E[(x - x̂)(x - x̂)ᵀ]` 是唯一「算出来」的量，10×10，和 `Q` 同维；`Q` 和 `R` 都是「填进去」的原料。

## 8.2 在四块板里挑一块（`:429-457`）

```cpp
for (int i = 0; i < config_.plate_count; ++i) {
    if (used_indices_[i]) continue;                       // 一帧内一块板只配一条观测
    const Eigen::Vector3d h = observationModel(x_, i, gimbal_yaw, ...);
    const Eigen::Vector3d residual = z - h;
    if (residual.norm() > config_.jump_gate_m) continue;  // 物理跳变闸 0.6 m
    const ObservationJacobian H = observationJacobian(x_, i, gimbal_yaw, ...);
    const Eigen::Matrix3d S = H * P_ * H.transpose() + R;
    const double nis = residual.transpose() * S.inverse() * residual;
    if (!std::isfinite(nis)) continue;
    if (nis < best_nis) { best_nis = nis; best_index = i; best_h = h; best_H = H; }
}
```

三个设计点：

**用马氏距离而不是最近欧氏距离**（`:427-428`）。侧板的横向不确定度大，直接用欧氏距离会把它误配进来。马氏距离把 `P` 和 `R` 都算进去了。

**`used_indices_` 保证一帧内一块板只配一条观测**（`:220-221`、`:435-437`）。同帧有两块板时，两个都配到同一个编号会让两条观测互相打架。这个数组在 `predict()` 开头清空。

**`S = H P Hᵀ + R` 是运行时的判断量**。答辩常问「怎么知道 R 填得对不对」，正确答案是这个比值，不是「Q 比 R」。`Q` 够不着这里，它绕道 `P` 才进来，而且两者量纲、维度都不同，不能直接相除。

## 8.3 全局统计闸（`:459-466`）

```cpp
if (best_nis > config_.nis_gate) { ++rejected_count_; return false; }   // 11.34 = chi2(3, 99%)
```

3 个观测分量，所以自由度是 3，99% 分位点 11.34。过了这一关的观测才会被吃下去。

三道闸的分工：**跳变闸**（0.6 m）挡物理上不可能的，**统计闸**（NIS）挡统计上不可能的，**重投影闸**（5 px）挡解算质量差的。

## 8.4 更新（`:468-477`）

```cpp
const Eigen::Matrix<double, 10, 3> K = P_ * best_H.transpose() * S.inverse();
x_ += K * residual;
const Covariance identity_minus_kh = Covariance::Identity() - K * best_H;
P_ = identity_minus_kh * P_ * identity_minus_kh.transpose() + K * R * K.transpose();

```

**Joseph 形式**。比 `(I - KH) P` 多一次矩阵乘法，但数值上不会失去正定性。长时间跑（上车要跑几分钟、几万帧）时这个差别是真的：标准形式在累积误差下可能让 `P` 出现负特征值，然后滤波器发散。多的一次乘法换稳定性。

更新后立刻包裹 `theta_c`（`:477`）。角度跨界时 `x += K · residual` 可能把它推到 `π` 外面。

```cpp
if (init_used_this_frame_) return false;                 // 同一帧只用第一条观测
init_used_this_frame_ = true;
...
const Eigen::Vector3d u = gimbalToWorld(gimbal_yaw) * z; // 先转到 W 系
if (init_count_ == 0) { init_mean_ = u; init_count_ = 1; }
else if ((u - init_mean_).norm() <= config_.init_consistency_m) {   // 0.3 m
    init_mean_ = (init_mean_ * init_count_ + u) / (init_count_ + 1);
    ++init_count_;
} else { init_mean_ = u; init_count_ = 1; }              // 不接近就重来
if (init_count_ < config_.init_frames) return false;     // 3 帧
```

为什么要「连续 3 帧板心彼此接近」：防止把两块不同的板拼成一个中心。

**同一帧只用第一条观测**是配套的（`ArmorEkf.hpp:232-234` 的注释）：一帧里如果有两块板，两块之间的间距会顶掉 0.3 m 的一致门，计数永远凑不满。

## 9.2 反推旋转中心（`:377-393`）

这是初始化里唯一需要想一下的地方：

```cpp
x_.setZero();
x_[Yaw] = wrapToPi(std::atan2(-init_mean_.y(), -init_mean_.x()));
x_[Radius1] = x_[Radius2] = config_.initial_radius_m;    // 0.25 m
x_[Px] = init_mean_.x() - config_.initial_radius_m * std::cos(x_[Yaw]);
x_[Py] = init_mean_.y() - config_.initial_radius_m * std::sin(x_[Yaw]);
x_[Pz] = init_mean_.z() - config_.plate_height_m[0];
P_ = initialCovariance();
```

板装在外侧、板面朝外，而检测的条件就是「板面法向朝向相机」。所以这块板的**径向方向与「板心指向相机」同向**，也就是板心视线的**反方位**。

所以 `theta_c` 用的是 `atan2(-y, -x)`（先取反再取方位角；注意这是标准数学约定的 `atan2(y, x)`，因此 `theta_c` 是左正），而不是板心自己的方位角。取错的话中心会偏 `2r·cos(δ/2)`，取对是 `2r·sin(δ/2)`（`:384-385`），`δ` 是这块板被看到的斜角。取对之后初始中心误差从「二三十厘米量级」降到「几厘米量级」。

这条就是 2026-10-13 修掉的那个 bug，提交 `d3a7ff3`。当时的夹具每帧喂两块背对相机的板，写反初始化的那一版反而全绿，所以夹具口径也一起改了（教训见深版 12.6.7）。

**编号是任意的全局相位**：把看到的这块板当作 0 号板，不影响物理，后续会随观测自动纠正（`:377-378`）。

# 十、状态机与 `crc`（`:493-532`）

`TrackingState` 的三个数值直接对应历史通信字段 `crc`（`AutoAimTypes.hpp:20-25`）：

```
NoTarget = 0,   Stable = 1,   Unstable = 2,
```

```cpp
if (updated_this_frame_) { miss_count_ = 0; ++hit_streak_; last_obs_ts_ = timestamp_seconds; }
else                     { ++miss_count_; hit_streak_ = 0; }
updated_this_frame_ = false;

// 回升

    const int required = ever_stable_ ? config_.recover_frames : config_.stable_frames;
    if (hit_streak_ >= required && covarianceIsStable() && recentNisMean() < config_.nis_mean_gate) {
        status_ = Stable; ever_stable_ = true;
    }
}
```

四个数决定全部行为：

| 参数 | 默认 | 作用 |
|---|---|---|
| `stable_frames` | 15 | 首次进 `Stable` 要连续命中 15 帧，165 fps 下约 90 ms |
| `recover_frames` | 10 | **曾经**稳定过之后，遮挡恢复只要 10 帧。这就是 `ever_stable_` 的用处 |
| `stable_hold_misses` | 3 | 丢 3 帧以内仍按 `Stable` 处理，纯预测足够准。单帧丢约 6 ms |
| `reset_timeout_s` | 1.5 | 超过 1.5 秒没有有效观测直接重置。这个门远大于真实遮挡（几百毫秒），不会误触发 |

**遮挡恢复的机制就落在这两个数上**：丢 3 帧以内不算丢；丢 4 到 10 帧转 `Unstable` 但状态还在，恢复只要 10 帧；丢超过 1.5 秒才推倒重来。这对应评分表验收重点第 6 条。

## 10.1 `covarianceIsStable`（`:534-542`）

```cpp

const double radius_std = std::sqrt(std::max(0.0, P_(Radius1,Radius1) + P_(Radius2,Radius2)));
const double yaw_std    = std::sqrt(std::max(0.0, P_(Yaw,Yaw)));
```

三道分量闸。注意它是**单向门**：只在 `Unstable -> Stable` 那一步查。进了 `Stable` 之后，只有连续丢 3 帧才降回 `Unstable`。所以 `Stable` 可以和远超门槛的协方差共存，深版 12.6.5 有实例。

# 十一、选板 `selectArmorIndex`（`:590-638`）

每帧要决定「瞄哪一块板」。两件事。

## 11.1 可见性：只考虑板面朝外的板

```cpp
const Eigen::Vector3d normal(std::cos(psi), std::sin(psi), 0.0);   // 板面法向，朝外
if (normal.dot(-p_world / norm) < facing_threshold) continue;      // facing_threshold = cos(60 度)
```

`-p_world / norm` 是从板指向云台原点的单位向量。要求法向与它的夹角小于 60 度，也就是这块板大致正对着相机。侧后方的板直接排除。

## 11.2 迟滞：新板要好过老板 5 度才切

```cpp
if (aim_index_ >= 0 && current_facing && aim_index_ != best) {
    const double current_abs_yaw =
        std::fabs(gimbalAzimuth(to_gimbal * platePositionWorld(x, aim_index_)));
    if (current_abs_yaw - best_abs_yaw < config_.aim_switch_margin_rad) best = aim_index_;
}
```

`aim_switch_margin_rad = 5 度`。没有迟滞的话，两块板势均力敌时 `aim_index_` 会每帧翻来覆去，输出的 `target_yaw` 跟着在 90 度之间跳，电控会看见一个突变指令。

`commit` 参数（`ArmorEkf.hpp:191-192`）是给弹道迭代用的：`commit = false` 时**只查询不写** `aim_index_`，否则试算值会把迟滞状态写脏（`:659-660` 的注释）。

**「切换」在数学上不跳变**：切换只是 `h` 里 `i` 的改选，中心、`theta_c`、`omega`、`r1 / r2` 在切换前后完全共享。会跳的量根本不在状态里。这是「切换不跳变」的保证，也是答辩可以直接讲的一句。

# 十二、`buildPrediction` 六步（`:640-770`）

## 第 1 步：取参数、算 `t0`

```cpp
const double latency = smoothedLatency(latency_s);            // 20 帧滑动均值，截 [0, 0.2]
const double bias = ... gimbal.prediction_bias_s ...;          // 电控下发，单位秒
const double t0 = std::clamp(latency + bias, 0.0, config_.max_prediction_s);
```

**`bias` 允许为负**（`:650-651`）：电控若想「少预测一点」就会下发负值，单边截正会把它吃掉。总时长 `t0` 仍然截在 `[0, 0.5]` 里，异常值照样挡得住。

`latency_s` 从哪来：适配器里用 `steady_clock::now() - timestamp_seconds`（`StudentTasks.cpp:205-208`）。`timestamp_seconds` 是相机采集帧的 `steady_clock` 纪元秒，所以这个差值正好是「采集到此处」消耗掉的检测加 PnP 时间。

## 第 2 步：两次迭代解开「飞行时间 与 预测时长」的循环依赖

飞行时间依赖距离，距离依赖预测到什么时候，预测到什么时候又依赖飞行时间。两次迭代就够：

```cpp
double flight_s = 0.0;
for (int iteration = 0; iteration < 2; ++iteration) {
    StateVector x_step = x_;
    propagate(x_step, t0 + flight_s);
    const int index = selectArmorIndex(x_step, gimbal_yaw, false);   // 只试算，不提交
    if (index < 0) break;
    const Eigen::Vector3d p_world = platePositionWorld(x_step, index);
    flight_s = solveBallistics(std::hypot(p_world.x(), p_world.y()),
                               p_world.z(), 0.0).flight_time_s;
}
const double t_pred = std::clamp(t0 + flight_s, 0.0, config_.max_prediction_s);
```

## 第 3 步：外推与选板

```cpp
StateVector x_pred = x_;
propagate(x_pred, t_pred);
const int aim_index = selectArmorIndex(x_pred, gimbal_yaw, true);     // 这一次提交
if (aim_index < 0) return PredictionResult{};
const Eigen::Vector3d p_world_aim = platePositionWorld(x_pred, aim_index);
const Eigen::Vector3d p_gimbal_aim = to_gimbal * p_world_aim;
```

## 第 4 步：相对角与弹道发射仰角

```cpp
const double rel_yaw   = gimbalAzimuth(p_gimbal_aim);     // atan2(-y, x)，右正
const double rel_pitch = gimbalElevation(p_gimbal_aim);   // atan2(z, hypot(x, y))，抬头为正

const double command_pitch =
    solveBallistics(std::hypot(p_world_aim.x(), p_world_aim.y()),
                    p_world_aim.z(),
                    gimbal_pitch + rel_pitch)             // 回退值 = 不作补偿的绝对几何仰角
        .launch_pitch_rad;
```

两个视线角函数在 `:44-50`，和 `main.cpp:448-450` 的 `pnp_yaw_rad` / `pnp_pitch_rad` **逐字同式**。集中在一处，别在调用处散抄。

### `command_pitch` 是 2026-10-16 改的那处

第三个参数是弹道解不收敛时的回退值，即「不作补偿的几何绝对仰角」 `gimbal_pitch + rel_pitch`。`solveBallistics`（`:64-84`）：

```cpp
Bullet_Model model(horizontal_m, vertical_m);
const float time = model.bullet_iteration_cal();
if (!std::isfinite(time) || time <= 0.0F) return solution;      // 不收敛，回落到几何角
solution.flight_time_s = time;
if (std::isfinite(model.beta) && std::fabs(model.z_diff) < model.err_max) {
    solution.launch_pitch_rad = model.beta;                     // 才是补偿后的角
    solution.converged = true;
}
```

`Bullet_Model`（`armor/src/BulletModel.cpp`）是一个带空气阻力的迭代弹道解：`Kf = 0.08`、`g = 9.81`、初速 `velo = 24`、收敛判据 `|z_diff| < 0.0001`、上限 100 次迭代。它返回的 `beta` 是**绝对发射仰角**（高于水平面），恒大于瞄准点的几何仰角 `η`，差值就是重力与空气阻力造成的下坠补偿。

小角度下这个差值几乎与高度无关：

```
beta - eta 约等于 g * d / (2 * v^2)
```

`v = 24 m/s` 时：1 m 是 0.49 度，3 m 是 1.46 度，5 m 是 2.44 度，10 m 是 4.88 度。

**宁可少补，也不能把一个没落到位的中途值发出去**：撞上 100 次迭代上限时 `z_diff` 还很大，说明 `beta` 是中途值，此时回落到纯几何角，等价于不作补偿。这是 `:78` 那个附加条件的用处。

依据：链路里写着「延迟和弹道补偿」，位置在「输出 yaw/pitch」之前，所以这是自瞄侧的活。学长 2026-10-16 的「补偿是算法组做」是印证。

## 第 5 步：角速度用中心差分

```cpp
constexpr double kRateHalfWindowS = 0.005;                  // 正负 5 ms
const double t_early = std::max(0.0, t_pred - kRateHalfWindowS);
const double t_late  =         t_pred + kRateHalfWindowS;
... propagate(x_early, t_early); propagate(x_late, t_late); ...
const double yaw_velocity   = wrapToPi(yaw_late - yaw_early) / dt_window;
const double pitch_velocity = (pitch_late - pitch_early) / dt_window;
```

不用状态里的 `omega` 直接换算，而是对**输出角**做中心差分。好处是切换装甲板、换半径这些非线性环节都被算进去了，输出的速率和输出的角严格自洽。

`pitch_early` / `pitch_late` **也各做一次弹道解**（`:713-720`），不是用几何角。理由在 `:711-712`：`target_pitch` 是补偿后的角，它的速率也必须来自补偿后的角，否则同一个上报结构里两个量对不上。

`yaw_velocity` 用 `wrapToPi` 包一道，因为两个时刻的角可能跨界。

## 第 6 步：填结果、开火门、有限性检查

```cpp
result.target_yaw   = static_cast<float>(gimbal_yaw + rel_yaw);   // 绝对云台指令
result.target_pitch = static_cast<float>(command_pitch);
```

**输出的是绝对云台角，不是相对角**。依据在 `:749-750`：框架的 `setSafeOutput` 把安全帧写成 `target_yaw = message.yaw`（`AppSupport.cpp:66-67`），意思是「保持当前」，误差 0。只有 target 是绝对角时这一句才自洽。

### `target_yaw` 会不会跟着 `gimbal.yaw` 一起漂

会，也不会，要分开看。

`target_yaw = gimbal_yaw + rel_yaw` 当然是加法，但 **`rel_yaw` 不是常数**，它每帧由滤波后的状态重算：先把世界系里的瞄准点用 `worldToGimbal(gimbal_yaw)` 转回当前云台系，再取方位角（`:682-686`）。所以云台自己转过去的过程中，两个操作数一增一减。

举例，瞄准点在世界系里的绝对方位角是 12（右正），云台从 10 转到 15：

| `gimbal.yaw` | `rel_yaw` | `target_yaw` |
|---|---|---|
| 10 | +2 | 12 |
| 15 | -3 | 12 |

**`target_yaw` 停在 12。** 物理上：一开始目标在炮口右偏 2，云台往右追了 5 之后变成左偏 3，指令始终是同一个绝对角。这就是「绝对角」的含义，也是 `testGimbalRotationIsNotTargetMotion` 在测的事：云台摆动 ±0.35 rad，估计出的目标位置一步没动。

要让 `target_yaw` 跟着 `gimbal.yaw` 一比一跑（10 到 15、12 到 17），需要 `rel_yaw` 恒为 +2，也就是瞄准点在云台系里一步没动，等于目标跟着云台一起转。**静止目标不是这种**。目标真的在动时 `target_yaw` 才变，而它的变化率是估出来的敌方角速度 `omega`，与 `gimbal.yaw` 的变化率无关。

**但有一种真正的 1:1 继承，要警惕**：`gimbal.yaw` 读数本身的误差会原样传进 `target_yaw`。观测是拿这个读数换到世界系的，参照系读数偏了 δ，整个世界系就跟着偏 δ，最后算出的绝对角也偏 δ。推导上它是可抵消的：`rel_yaw` 用同一个 δ 转出去又转回来，误差在 `rel_yaw` 里被抵掉，于是剩下的就是 `target_yaw = θg + rel_yaw` 里那个多出来的 δ。这条是纯代数推论，没有单独实测。结论是**我们对 `message.yaw` 的口径依赖是硬的**，不是「随便给个数都行」。这正是问题清单 1.7 那条要问清楚的（机械角还是 IMU 融合的场地角）。

开火门（`:759-764`）：

```cpp

    std::fabs(rel_yaw) < config_.fire_yaw_tolerance_rad &&                       // 0.02 rad = 1.15 度
    std::fabs(command_pitch - gimbal_pitch) < config_.fire_pitch_tolerance_rad;  // 同上

```

**仰角那项的写法本身是个坑**。yaw 的指令是 `gimbal_yaw + rel_yaw`，误差就是 `rel_yaw`；pitch 的指令是 `command_pitch`，一个绝对角，误差是 `command_pitch - gimbal_pitch`。**两者口径必须一致**。如果照抄 yaw 的写法写成 `|rel_pitch| < 容差`，那门会在 5 m 处早开 2.44 度（因为 `command_pitch` 比几何角高 2.44 度），落点低约 21 cm。这是 2026-10-16 和 `beta` 一起改掉的第二处。

最后一道（`:766-768`）：

```cpp

```

`predictionIsFinite`（`:88-101`）逐字段查，而且**米转毫米还要再乘一次 1000**（`AppSupport.cpp:87-88`），所以连 `center_x_m * 1000.0F` 也要查。任何一个非有限直接返回全零，框架收到 `state == NoTarget` 就降级成安全帧。宁可这一帧不开火，也不能把 NaN 发到串口。

# 十六、测试怎么钉住它

`tests/test_ekf_predict.cpp`，847 行 13 个用例，`ctest` 7/7。

| 用例 | 钉住什么 |
|---|---|
| 坐标变换 | `gimbalToWorld` 的方向、`det = +1`、`M(0) = I` |
| 无噪收敛 | **最强的一条**：观测由 `h` 自己生成，200 帧后 `x_est` 到真值 1e-6。真值的 `psi` 用左为正，把 `theta_c` 的符号钉死 |
| 有限差分对拍 | 解析 `H` 逐元素对拍，容差 1e-6 |
| 状态机时序 | 有观测，丢 20 帧，再回来，`crc` 序列必须出现 1 -> 2 -> 1；丢超过 1.5 秒必须变 0 |
| 安全不变量 | `crc != 1` 时 `fire_allowed` 恒假；空观测连调 100 帧不崩、输出有限 |
| 单板初始化回归 | 初始化分支锁定的那条 |
| 下坠补偿 | 2026-10-16 新加，实测输出 `指令仰角 0.04158 闭式 0.04108 距离 4.824 通过` |

这些钉的是**设计不变量**，不是「跑得好看」：变换方向的符号、雅可比、状态机时序、安全不变量。不需要相机也不需要真车。

夹具口径要小心：它必须只喂真实系统产生得出来的输入。2026-10-13 那次就是因为夹具每帧喂两块背对相机的板，把写反初始化的那一版喂成了全绿。

**别用 `CMAKE_BUILD_TYPE=Release`**。默认没有 `-DNDEBUG`，断言是活的；Release 带 `-DNDEBUG` 会抹掉 `tests/` 里的裸 `assert`，`ctest` 照样报通过但是假绿。要优化用 `-DCMAKE_CXX_FLAGS=-O2`，`CMakeLists.txt` 保持原样。

# 十七、已知问题

按会不会卡住 `Stable` 分两档。

## 17.1 会卡住 `Stable` 的

**慢转时卡住的是 yaw 闸，不是半径闸**。`omega = 0.6 rad/s` 时中心误差只有 0.06 cm，瞄准几何完全正确，`fire_allowed` 仍然是假。门槛约在 `omega = 0.8 rad/s`。逐档实测表见深版 12.6.3。

**这条闸是几何墙还是调参**：`omega > 0` 是调参问题，扫 `angular_accel_noise_rad_s2` 就能进门；`omega = 0` 是几何问题，怎么降都不收敛。定论见深版 12.6.4。

**`covarianceIsStable()` 是单向门**：`Stable` 可以和远超门槛的协方差共存，深版 12.6.5 有实例。是刻意留的滞回还是漏了回退闸，需要定。

**只看得到一块板时另一个半径拿不到观测**：一条观测只修得动一个奇偶的半径（`H.col(radiusIndex(i))` 是唯一非零的半径列）。目标在转时两个半径都会陆续拿到观测，只有 `omega = 0` 时另一个半径报的是先验。深版 12.6.2 有表。

**待定项**：整状态协方差闸换成「瞄准点自身的不确定度闸」。真正决定打不打的是瞄准点的不确定度，不是车体 yaw 的不确定度。未改，见深版 12.6.6。

## 17.2 已知欠账

- **`ekf_nis_mean` 打不出去**：`recentNisMean()` 是 private 且没有公开访问器。要看 NIS 曲线得先加 getter。
- **切换与遮挡的证据键漏不出来**：现在靠 `ekf_aim_index` 和 `ekf_streak` 间接看，没有直接的「这块板刚从视野消失」的量。
- **`plate_height_m` 默认全零**，对标准步兵是错的。代价只在 `center_z_m` 和两块板同框那几帧，不影响瞄准。
- **74.1 mm 枪口偏移没接上**：`solveBallistics` 的高度相对云台原点算，不是相对枪口。这个偏移在 `armor/src/Planner.cpp` 里是接上的。
- **`gimbalToWorld` 只去 yaw、不去 pitch，「世界系」其实是炮管系**：`gimbal.pitch` 没进过这个变换。云台俯仰时整个 W 跟着转，静止目标在 W 里的坐标会变，`center_z_m` 与 `vx / vy / vz` 会吃到这段视在运动，**仰角指令还会多带一份 `φ̇ · t_pred` 的提前量**（5 m、30 度每秒、`t_pred` 0.22 s 时 6.6 度，容差是 1.15 度）。改法是串一个 `Ry(gimbal.pitch)`，只动这一个函数，未做；**要在上车扫 Q/R 之前决定，扫完再改等于重扫**。另见 1.1「云台抬头了会怎样」。
- **相机光轴与炮管平行性未知**。
- **`gimbal.yaw` 符号未上车确认**：右正只是默认，翻转只有一处。
- **弹速 24 m/s 是默认值**：来自 `armor/src/BulletModel.cpp:5` 的构造函数，没人选过。同仓库还有 `Planner.hpp:47` 的 23.5 与 `Planner.cpp` 的 23.0。
- **EKF 之前没有目标筛选层**：链路里「数字识别与目标筛选」是识别阶段的一环，现在一帧里所有同色板全喂进同一个「单目标四板」模型。问题清单 §2.7b，未答。
- **`config/camera.yaml` 的外参 `t` 仍是 `(0.06711, 0, 0.0515)`**，按 handout 的轴序推导应是 `(0, -0.0515, 0.06711)`。红线相关，故意没动。
- **慢转 0.052 m 稳态残差**。
- **`7guard` 真值未闭环**。
