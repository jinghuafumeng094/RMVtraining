# 零、全景：数据怎么流过这几百行

**一句话**：每帧，`ekf_predict` 拿一批云台系板心和电控给的当前姿态，吐出**一条绝对云台指令**。

**拆开**，一帧的数据流是四段：

```
相机 -> 检测 -> PnP  ->  observations   一批云台系板心，vector<ArmorPose>
                        gimbal         电控下发的当前姿态，GimbalState
                                    |
                        ekf_predict(observations, gimbal, timestamp_seconds)
                                    |
        predict(dt) -> update(每条观测) -> advanceStateMachine(ts) -> buildPrediction(gimbal, latency)
                                    |
                            PredictionResult
                                    |
                    applyPrediction -> 64 字节串口帧
                    logPrediction   -> Web Debug 曲线
```

四个方法每帧按这个顺序各调一次，这是整个类唯一的入口约定（`ArmorEkf.hpp:148-156`）。

**举个例子**，某一帧的输入输出长这样：

| 四段 | 这一帧的值 |
|---|---|
| 输入 `observations` | 一条观测，板心在 G 系 `(3.2, 0.9, 4.5)` 米，`reprojection_error = 0.72` px |
| 输入 `gimbal` | `yaw = 0.30` rad、`pitch = 0.05` rad、`prediction_bias_s = 0.01` s |
| 输入 `timestamp_seconds` | 采集那一帧的 `steady_clock` 纪元秒 |
| 中间四步 | 外推 -> 把这条观测喂进去 -> 状态机 -> 算指令 |
| 输出 `PredictionResult` | `target_yaw`、`target_pitch`、`distance_m`、`state = 1`、`fire_allowed` |

**`ArmorEkf` 只依赖 Eigen 和标准库，不依赖 OpenCV。** 所以它可以独立构造，单测直接测类，不用走适配器。

# 一、坐标系：为什么非要一个世界系

**一句话**：**W 世界系就是「把 yaw 读成 0」之后的那一帧云台系。** 两系共用一个原点、共用一套轴的定义，差别只有一个偏航角 `θg = gimbal.yaw`。

**为什么非要有两个系**，两句话：

- **观测只能从 G 进来。** 相机固定在云台上，PnP 出的 `position_gimbal_m` 天然是云台系的坐标。
- **估计必须建在 W 里。** 状态若建在 G 里，云台一转、目标坐标就变，滤波器会把「云台在转」当成「目标在动」，估出来的速度是废的。

**拆开看，两系各装什么**：

| 记号 | 各轴 | 装什么 | 代码里在哪 |
|---|---|---|---|
| **W 世界系** | x 前、y 左、z 上 | 车体位置、速度、yaw、半径，整个 10 维状态 | `x_` |
| **G 云台系** | x 前、y 左、z 上 | 板心观测值 | `ArmorPose::position_gimbal_m` |

选 W 的轴序不是随手定的：弹道模型（`armor/include/BulletModel.hpp:6`）也在这个口径上，顺着它选就不用再串一层。

**举个例子**：取 `p_G = (5.00, 0, 0)`，也就是「云台正前方 5 m」这个方向，`p_W = M(θg) · p_G`：

| 云台 yaw | G 里的坐标 | 换到 W 里 | 在 W 里看是哪个方向 |
|---|---|---|---|
| 0 | (5.00, 0, 0) | (5.00, 0, 0) | 正前方 |
| 右 30 度 | (5.00, 0, 0) | (4.33, -2.50, 0) | 右前方 30 度 |

第二行是重点：**同一组数字，在两个系里指的是两个不同的方向**，夹角正好是云台转过的 30 度。y 为负是右，所以「云台正前方 5 m」在 W 里看是右前方，因为云台自己已经往右转了 30 度。

反过来问也成立。若是一个**固定不动的目标点**、云台朝它转过去，同一个点从 G 的 (5.00, 0, 0) 变成 (4.33, +2.50, 0)（y 为正是在左边，因为云台右转之后目标落到视线的左侧）。两种问法算的是同一件事，只是把「谁不动」按在了不同的系上。

再加上第三种情形：目标真动了，G 和 W 会一起动；云台只是自己转、目标没动时，**只有 W 是安静的，G 在乱动**。这正是估计必须建在 W 里的原因。

答辩问「原点一样、轴也一样，那不一样在哪」，答的就是这一句：**差在 G 跟着云台转、W 不跟着。** 这就是机器人里的 body frame / world frame。

## 1.1 原点在哪：两系共用云台 P 轴原点

**一句话**：两系的那个共同原点，就是**云台 P 轴的原点**。

**拆开看，这条结论有三层**，一层都不能少：

| 层 | 内容 | 依据 |
|---|---|---|
| 它是定义，不是观测 | 两系同原点，不是量出来的 | 变换函数里**没有平移项**（`:113-121`） |
| 也只能这么定 | 原点另有所指的世界系造不出来 | 整条链路没有任何自定位 |
| 它还有个隐含假设 | 偏航轴正好穿过这个点 | 按 `d = 0` 处理，没实测 |

**第一层：它是定义，不是观测。** 两系原点若不同，变换必须写成 `p_W = M · p_G + t`，多一个三维平移。代码没有这一项，所以「两系同原点」和「变换是纯旋转」是同一件事的两种说法，不是两条独立结论。这条要在答辩时讲清，别被当成实测结论。

**第二层：也必须这么定，因为原点另有所指的世界系造不出来。** 要建那样的系，得知道自己在那里面在哪。整条链路没有任何自定位：`GimbalState`（`AutoAimTypes.hpp:27-33`）只有 `yaw` / `pitch` / `roll` / `prediction_bias_s` 四个角和一个时间，**一个位置量都没有**；`PredictionResult` 报的是目标中心在 W 里的坐标，不是自己的位姿。没有场地位置、没有里程计。所以不是不想建，是建它需要的三个数拿不到，同原点是唯一能算的选择。

这也解释了外参平移那一项的起点：`config/camera.yaml` 写着「云台 P 轴 -> 相机光心 = (67.11, 0, 51.5) mm」。外参平移量的是**从云台 P 轴出发**的向量，所以把原点放在那里最省事。

**handout 里没有这句话。** `云台外参.md` 只管云台系：正式部分写「相机原点在云台坐标系中的位置，即从云台原点指向相机原点的 3x1 平移向量」，正文写「相机光心到云台 P 轴的向量」，两句合起来只说明**云台原点 = 云台 P 轴**，对世界系一个字没提。文档目录下那张坐标系图里的「原点 = 云台旋转中心（P 轴）」是自行标注的，不是 handout 原话。

**第三层：隐含假设。** 纯旋转等价于假设偏航轴正好穿过这个原点。云台原点是俯仰轴上的一个点，若那个参考点沿俯仰轴偏离了两轴交点 `d`，云台偏航时它会扫出半径 `d` 的圆，严格变换应多一个平移项，量级 `2d·sin(θg/2)`：

| 偏离 `d` | 转 90 度时多出的平移 |
|---|---|
| 1 cm | 1.4 cm |
| 5 cm | 7.1 cm |

现在按 `d = 0` 处理，这是默认值，没有实测。要确认得问学长「P 轴那个参考点是不是俯仰轴与偏航轴的交点」。

## 1.2 为什么两系只差一个旋转矩阵

**一句话**：同原点去掉平移项，只绕 z 转去掉 x、y 的耦合，两件事合起来就只剩一个 3x3 旋转矩阵。

**拆开是两个原因，缺一个都不成立**：

| 原因 | 去掉什么 | 反例 |
|---|---|---|
| 同原点 | 平移项 `t` | 相机系到云台系那一跳：相机光心离云台原点前 67.11 mm、上 51.5 mm，所以那里必须带 `t`（`StudentTasks.cpp:167-168`） |
| 只绕 z 转 | x、y 的耦合 | `M` 的第三行第三列是 1，z 分量原样通过 |

**正交且 `det = +1`，所以逆矩阵等于转置** —— `worldToGimbal` 才敢直接返回 `transpose()`（`:123-125`）。这是一次矩阵乘法和一次转置的区别，转置不用重新算 `sin / cos`。

## 1.3 两系到底差在哪：只差 `θg` 一个自由度

**一句话**：两系的差别只有一个自由度，就是偏航角 `θg`，而这个角每帧都在变。

**拆开看**。「轴的定义相同」说的是两系对 x、y、z **各指什么东西**叫法一样，**不是任何时刻三根轴都指向同一个方向**。云台转过 `θg` 之后，G 的 x、y 相对 W 的 x、y 各偏了 `θg`，**只有 z 因为本身就是那根转动轴而始终同向**。

**`θg = 0` 的那一刻两者完完全全重合**，`M` 是单位阵，三根轴也指向同一方向；云台一转，G 跟着转、W 不转，x 与 y 立刻分开。**两个系是同一个系的两种状态，不是两个不同的系。**

**`M` 就是这件差事的具体形式**：把一个在某一系里量出来的坐标，改用另一系的轴重新表达。它只混 x 和 y（第三行第三列是 1），正是「只有 x、y 分开、z 没分」的代码痕迹。观测雅可比里 `H.col(Pz) = to_gimbal * (0, 0, 1)`，算出来就是 `(0, 0, 1)`（`:193`）—— **云台转角根本没进 z 那一分量。**

**这个数在别处还有一个名字**：`θg` 就是 `gimbal.yaw`，电控每帧给的标量。

## 1.4 为什么不把原点挪到自己的车心

「车心」有两种读法，这里先说自己的，目标车心另起一节。

**一句话**：能挪，但没好处，代价还不小。

**能挪。** 云台原点到自己车心是一个常向量：两点都在自己车上，而 W 不随云台 yaw 转，所以这个偏移在 W 里不随时间变。改原点就是 `p_W = p_W_原 - t`，整个状态平移一下，EKF 的估计一个字不用改。

**代价有四条**：

| 代价 | 具体 | 量级 |
|---|---|---|
| 这个向量手上没有 | 已知的只有相机光心到云台 P 轴、云台 P 轴到摩擦轮两组；云台 P 轴到车心，仓库、handout、`config/` 里一处都没有 | |
| 这个偏移永远估不出来 | 它会与目标中心位置完全共线：PnP 观测约束的是相对几何，`t` 偏多少、目标中心就跟着偏多少，任何一帧里都分不开，不可观测 | |
| 喂错了直接进瞄准角 | 瞄准角是从原点指向瞄准点的方向，原点横移 `δ` 会让它偏大约 `δ / R` | 见下表 |
| 云台原点本来就是更好的锚点 | 它是三个轴的交点，按定义在俯仰轴上，所以俯仰时不动；变换又假设偏航轴穿过它，所以偏航时也不动；roll 同理。它是这辆车上唯一在云台任何转动下都不动的点 | |

原点偏差进瞄准角的具体数：

| 原点偏差 δ | 5 m 处的角度偏差 | 对照开火容差 |
|---|---|---|
| 5 cm | 0.010 rad = 0.57 度 | `fire_yaw_tolerance_rad = 0.02 rad` |
| 10 cm | 0.020 rad = 1.15 度 | 刚好吃光 |

重投影、深度、NIS 三个闸门都看不见这种偏差，因为偏差在参照系上，不在观测上。

**结论**：车心原点的世界系能建但没用。EKF 要的是相对几何——目标相对自己多远、往哪动、转多快——这些量换原点前后一样。换原点唯一改变的是上报的 `center_x/y/z`，一个常数平移。真想让「目标相对车心」更好读，应该在输出那一层减，不在状态里建。

## 1.5 更不行：把原点放在目标车心

如果「车心」指的是**目标车的车心**，那不是划不划算的问题，是根本立不住。

**一句话**：那个向量不是已知量，它就是状态本身。

**拆开是四条**：

**一、它不是已知量，它是待估量。** 已知的常向量只有云台原点到相机光心（外参）。云台原点到目标车心是**每帧要估的未知量**，就是状态的前三维 `[Px, Py, Pz]`。它是整个系统里最难估的三个数，慢转 0.052 m 稳态残差与 `omega = 0` 不收敛说的都是它。拿它当原点，等于把要测的量定义掉了。

**二、PnP 给的是板心，不是车心。** 观测只有板心，从板心到车心要反解 `platePositionWorld`（`:206-213`）：

```
板心 = 车心 + r * (cos(psi), sin(psi), 0)        psi = theta_c + i * pi/2
```

反求车心要先知道 `theta_c`、`r`、`i` 三个量，而这三个正是滤波器在估的。**单帧 3 个测量对 6 个未知，欠定。**

**三、目标不转时连多帧都定不出来。** 车心可以绕着这块板滑一圈、同时把半径改掉，观测序列完全一样。这是深版 12.6.2 里 `omega = 0` 一列中心误差不收敛的成因，那条方向上的分量永远学不出来。所以「PnP 知道板的位置和距离，就也应该知道车心」这一步不成立：**板心是读出来的，车心是解出来的，而且解它需要目标在转。**

**四、原点只能放在量具所在的地方。** 观测是 PnP 出的板心，天然相对相机；外参把相机原点挪到云台原点，于是所有观测天然都是相对云台原点的。要让原点是目标车心，得先知道云台原点相对目标车心的位置，而整条链路没有自定位。就算估出来了，那个向量每帧都在变，原点跟着目标跑，车心恒等于零向量——那已经不是世界系，是目标体坐标系。

**要的其实是另一样东西。** 如果目的是拿到「目标车心相对云台」这个读数，它现在就有：状态在 W 里，乘一次 `worldToGimbal(gimbal_yaw)` 即到云台系，`buildPrediction` 对瞄准点做的正是这件事（`:697-698`）。上报的 `center_x_m/y_m/z_m`（`:758-760`）是 **W 系口径**，注释里也这么写。想在 Web Debug 上加三个云台系口径的数，在输出层乘一次 `M^T` 即可，与「把原点挪走」不是一回事。

## 1.6 它不是惯性系

名字比性质好听。

**一句话**：它只跟云台 yaw 无关，不跟世界无关。

**拆开是两条限制**：

| 限制 | 后果 |
|---|---|
| 随车平移 | 原点在云台上，车一动原点就动。它是「与云台 yaw 无关」，不是「与世界无关」 |
| 只去掉 yaw，没去掉 pitch | `gimbal.pitch` 从头到尾没进过 `gimbalToWorld`，函数签名只收一个 `gimbal_yaw`。云台一抬头，整个 W 跟着俯仰一起转 |

所以更准确的说法是：**它其实是炮管系。** 展开见下节。

## 1.7 云台抬头了会怎样

**一句话**：两系之间的关系一个字不变，变的是 **W 的 z 不再是竖直方向，而是炮管的「上」**。

**拆开看，后果按严重程度排四条**：

| # | 后果 | 量级 |
|---|---|---|
| 一 | 上报的竖直量带上 `d · sin(pitch)` 的台阶 | 5 m 处抬头 10 度差 0.87 m |
| 二 | `vx` / `vz` 吃到一段假速度 | 5 m 处 30 度每秒 = 2.6 m/s |
| 三 | 仰角指令多带一份提前量 `φ̇ · t_pred` | 30 度每秒、`t_pred` 0.22 s 时 0.115 rad = 6.6 度，**五倍于 0.02 rad 的容差** |
| 四 | 方位角基本不受影响 | 俯仰绕 y 轴转，`y` 分量不动，偏差是 `φ` 的二阶小量 |

**第一条**：`center_z_m` / `ekf_z_m` 是当绝对值报的，5 m 处抬头 10 度就差 0.87 m。这就是上车手册要求「读 z 之前先把俯仰归零」的原因。

**第二条**：云台以 `φ̇` 抬头时，静止目标在 W 里的坐标也以 `d · φ̇` 旋转。滤波器分辨不出这段运动是目标在动还是参照系在动，会照单收下。

**第三条最要紧**，因为它直接进开火判据。目标是静止的、就在正前方时，理想指令是仰角 0。代码把状态在 W 里外推到 `t_pred`，而 W 自身还在以 `φ̇` 转，预测到的仰角因此多出 `φ̇ · t_pred`，加回 `gimbal.pitch` 之后并不归零。

**对照 yaw 那一半**：正因为 yaw 被去掉了，同一情形下 `target_yaw = θg + rel_yaw` 精确归零；pitch 没去掉，这笔账就没平。

**这一条与「不外推时精确抵消」不矛盾**：不外推时 `rel_pitch` 在炮管系里量、加回 `gimbal.pitch` 正好回到世界系仰角，误差为零；误差是外推那一步引进来的，随 `φ̇` 与 `t_pred` 一起长大。

**改法**：给 `gimbalToWorld` 补一层 `Ry`，`M = Rz(-yaw) · Ry(pitch)`，`p_W = M · p_G`。`worldToGimbal` 照旧返回转置，`:186-188` 那条「不手抄 `M^T`」的规矩正好用上：**只有这一个函数要改**。补完 W 是真水平系，第二、三条消失，第一条的台阶也没了，而 `target_pitch = gimbal.pitch + rel_pitch` 的抵消照旧成立——`rel_pitch` 变成「真世界里还差多少」，加回当前仰角仍回到世界系仰角。

**两个前提得先定**：一是 `Ry(∓pitch)` 取哪个符号、串联顺序是不是先 yaw 后 pitch，要问电控；二是**要在上车扫 Q/R 之前改**，否则扫出来的噪声参数会把这份视在运动一并吃进去，等于给一个参照系的毛病配了套参数，之后再改就得重扫。

**上面四条是读代码加推算，没有实测过**，列为已知欠账，见第十七节。最省事的验证：目标不动、只抬云台俯仰，看 `ekf_z_m` 动不动；按现写法**会动**，补完 `Ry` 之后不该动。

**`pitch` 之外，`roll` 也没进变换。** 电控给三个角，`gimbalToWorld` 只吃 yaw，**pitch 和 roll 都被丢掉**，区别在误差形状：目标偏离炮管 `α` 时，绕炮管转 `ρ` 造成的瞄准角误差约 `ρ · α`，**正对炮管那一瞬间恰好为零**；而 pitch 的账是 `φ` 本身，与 `α` 无关。

| 横滚 `ρ` | 偏离炮管 5 度 | 11.3 度 | 20 度 |
|---|---|---|---|
| 2 度 | 0.17 | 0.39 | 0.68 |
| 5 度 | 0.44 | 0.98 | 1.71 |
| 10 度 | 0.87 | 1.95 | 3.40 |

单位度，取仰角那一列（方位角那列还小一个量级），容差 1.15 度。**跟踪时云台一直把 `α` 往 0 压，所以开火那一刻这笔误差本就接近零**，会疼的是大幅调转的中间过程。RM 云台是两轴，`roll` 不是被控量、是车体姿态透上来的，不平的路上才会大。

表里的数是 `Rx(ρ)` 作用在视线向量上算出来的，**没有实测**。

**补的话就是同一行改动。** `gimbalToWorld` 现在返回 `Rz(-yaw)`，改成 `Rz(-yaw) · Ry(-pitch) · Rx(-roll)`，`worldToGimbal` 照旧取转置，`rel_yaw` / `rel_pitch` 就变成「云台真实姿态下的相对角」，横滚的污染跟着消失。**这不是两件事**：第十七节那条「补 `Ry`」本来就要在上车扫 Q/R 之前做，roll 是同一个函数里顺手加的一项，边际成本接近零。所以准确的说法是 **roll 不该单独立项，但该在补 pitch 时一起补**。

**动它之前必须先问清 `roll` 的定义**：若它指的是车体横滚而不是相机的横滚，符号或零点与云台差一点，直接串 `Rx(roll)` 等于注入一个新错误。和 pitch 的符号、串联顺序是同一张问单上的事。

**横滚还带出一段视在速度**，与第二条同理，但同样乘一个 `α`：`d · sin(α) · ρ̇`。5 m、偏 11.3 度、横滚 30 度每秒时是 0.51 m/s，同条件下 pitch 是 2.57 m/s；正对炮管时 roll 是 **0**，pitch 仍是 2.62。

## 1.8 唯一的变换函数

**一句话**：`gimbalToWorld` 是**全代码唯一允许出现坐标系变换的地方**，四个调用点都走它，谁都不许手抄矩阵元素。

```cpp
// ArmorEkf.cpp:113-121
Eigen::Matrix3d ArmorEkf::gimbalToWorld(double gimbal_yaw) {
    const double s = std::sin(gimbal_yaw);
    const double c = std::cos(gimbal_yaw);
    Eigen::Matrix3d m;
    m << c, s, 0.0,
         -s, c, 0.0,
         0.0, 0.0, 1.0;
    return m;
}
```

**拆开看，这个矩阵可以自己手验三条**：

| 检查 | 手算结果 | 对不对 |
|---|---|---|
| `θg = 0` 时是单位阵 | 视线朝 `+x`，正前方 | 对 |
| 云台向右转 `θg > 0` | 正前方的东西落到 `x > 0`、`y < 0`；y 朝左，y 为负就是右 | 对 |
| 展开成基本旋转 | `M(θg) = Rz(-θg)`，行列式 `+1` | 是纯旋转不是镜像 |

`worldToGimbal` 直接返回它的转置（`:123-125`）。

**为什么集中在一处**：手抄等于把同一个约定写两遍，换约定时容易只改一处，而错了不报错。理由写在 `:186-188`。

**由此得出一条关键推论**：**`gimbal.yaw` 是观测模型的输入，不是状态的一部分。** 滤波器不需要估云台角，因为电控每帧直接告诉它。

## 1.9 `gimbal.yaw` 是标量，矩阵只是它的包装

**一句话**：`gimbal.yaw` 是电控给的一个 float；`gimbalToWorld` 返回的 3x3 是拿这个数算出来的。

**拆开看，两者的关系**：

```cpp
double gimbal_yaw = gimbal.yaw;                  // 一个标量，单位 rad
Eigen::Matrix3d m = gimbalToWorld(gimbal_yaw);   // 由它算出的 3x3
```

9 个元素里只有 `cos` 和 `sin` 两个独立量，而这两个又都由同一个 `θg` 决定。所以矩阵**不携带任何 yaw 之外的信息，自由度只有 1，不是 9**。

包成矩阵的理由是它能直接作用在三维向量上，`p_W = M · p_G` 一句话写完，约定也不用散落到每个调用点。不包也等价：把方位角减掉 `θg`、半径和高度不动，结果一样。

**同一个 yaw 在代码里有三处用法，只有一处是矩阵**：

```
:670   to_gimbal  = worldToGimbal(gimbal_yaw)        // 包成矩阵
:701   rel_yaw    = gimbalAzimuth(to_gimbal * p_W)   // 从转回来的点里量角度
:771   target_yaw = gimbal_yaw + rel_yaw             // 标量直接相加
```

三行连着读：**先用 yaw 把世界系的点转回云台系，量一个相对角，最后又把同一个 yaw 加回去**。转出去又转回来，是因为 `target_yaw` 要的是世界系里的绝对方位角。最后那一行是标量加法，与矩阵无关；如果 yaw 本身就是矩阵，这里写不出来。

**它也不是「云台的姿态」。** 云台姿态是 3 个自由度，`GimbalState` 里确实有 `yaw` / `pitch` / `roll` 三个角，但 `gimbalToWorld` 只吃 yaw 一个：

| 电控给的角 | EKF 里的去向 |
|---|---|
| `yaw` | 唯一进变换的，`M(θg)` 全部由它决定 |
| `pitch` | 不进变换，只当绝对仰角参照：开火门、弹道回落的基准 |
| `roll` | 一次都没用过，只在 `main.cpp:115` 查有效性、`AppSupport.cpp:56` 透传 |

所以 `M` 是「云台姿态里 yaw 那一份」的矩阵形式，**不等于云台姿态**。没去掉 pitch，正是 1.7 里那条「它其实是炮管系」。

## 1.10 两套 yaw 符号共存，是有意的

**一句话**：状态里的 `theta_c` 用 `atan2(y, x)`（左为正），输出用的 `gimbal.yaw` / `target_yaw` 用 `atan2(-y, x)`（右为正），两套符号同时存在。

**拆开看**（`ArmorEkf.hpp:34-38`）：

| 量 | 约定 | 正方向 |
|---|---|---|
| `theta_c`（状态第 6 维） | `atan2(y, x)`，而 y 朝左 | **左为正** |
| `gimbal.yaw`、`target_yaw`、`pnp_yaw_rad` | `atan2(-y, x)` | **右为正** |

两者各自只在一个地方用一次，滤波器因此仍然自洽，不需要强行统一。

**但有个连带约束必须记住**：输出是 `target_yaw = gimbal_yaw + rel_yaw`，这要求两个操作数同号。**一旦上车确认电控是左正，`ArmorEkf.cpp:44-46` 的 `gimbalAzimuth` 与 `main.cpp:448` 的 `pnp_yaw_rad` 必须一起翻**，只改一处会差两倍角。这条已写进 `docs/上车前问题清单.md` §1.5。

# 二、状态向量：10 维

**一句话**：状态是这 10 个数，前 3 个是**旋转中心**的位置，中间 3 个是它的速度，再 2 个描述**车体转向**，最后 2 个是**两块装甲板的半径**。

```cpp
// ArmorEkf.hpp:12-18
//   x = [ px, py, pz, vx, vy, vz, theta_c, omega, r1, r2 ]^T
```

**拆开看，逐个是什么**：

| 分量 | 下标 | 物理量 | 单位 | 怎么读 |
|---|---|---|---|---|
| px py pz | 0 1 2 | 旋转中心在 W 系的位置 | m | 敌车「转轴」在哪 |
| vx vy vz | 3 4 5 | 旋转中心速度 | m/s | 那个轴在往哪移动 |
| theta_c | 6 | 车体偏航角，W 系方位角，左为正 | rad | 车头现在朝哪 |
| omega | 7 | 车体偏航角速度 | rad/s | 车转多快 |
| r1 r2 | 8 9 | 偶数 / 奇数编号装甲板到旋转中心的半径 | m | 板装得多远 |

下标用枚举（`ArmorEkf.hpp:47-59`），文件里搜不到 `x_[0]` 这种写法。

**举个例子**，一辆标准的静止步兵，车头朝 `+x`，停在云台正前方 5 m：

| 分量 | 值 | 含义 |
|---|---|---|
| px py pz | (5.00, 0.00, 0.10) | 转轴在正前方 5 m、离地 10 cm |
| vx vy vz | (0, 0, 0) | 没在动 |
| theta_c | 0 | 车头朝 `+x` |
| omega | 0 | 没在转 |
| r1 r2 | (0.25, 0.25) | 四块板都在半径 25 cm 上 |

此时 0 号板（`i=0`）的板心 = 中心 + 半径沿 `psi = theta_c + 0 = 0` 方向 = `(5.25, 0, 0.10)`。转 90 度之后 `theta_c = π/2`，同一个 0 号板跑到 `(5.00, 0.25, 0.10)`——**轴没动，板绕着它转。**

三条设计理由：

**为什么状态里是「旋转中心」而不是「某一块板」。** 车在转，板跟着转，板的坐标随时间摆动。只有中心是不动的。把中心当状态，过程模型就退化成匀速直线，`F` 里只剩 4 个 `dt`。

**两块半径为什么只有两个。** 0 / 2 号板共用 r1，1 / 3 号共用 r2。这就是 `PredictionResult::radius_1_m` / `radius_2_m` 对应的东西（`AutoAimTypes.hpp:81-82`）。标准步兵两块板同量级，`r1 ≈ r2`；前哨站是三块交替半径。

**高度 `h_i` 为什么不进状态**（`ArmorEkf.hpp:62-76`）。高度只进一个方程 `z = pz + h_i`，而 `pz` 也只在那一个方程里出现。所以**高度方程和其余九个状态完全解耦**：滤波器把「当前看得见那块板」的真实高度吃进 `pz`，瞄准点照样对。填错的代价只有两个：`center_z_m` 这个上报量偏了，以及两块板同框那几帧的 `±Δh/2`。默认全零表示四块共面，对标准步兵是错的，但它不报错，只是静默偏一点点。**所以不用上车量离地高度。**

标准步兵与哨兵的真实高度表是「相对两块等高、相邻两块有高差」，也就是 `{h0, h1, h0, h1}`，与 `r1 / r2` 的奇偶配对同一套（`ArmorEkf.hpp:63-68`）。上车量出来按这个形状填。

# 三、主循环四步

**一句话**：每帧固定调这四个方法，顺序不能变。

```cpp
// ArmorEkf.hpp:148-156
filter.predict(dt);                                  // 1. 外推，x 和 P 都推到当前
for (const ArmorPose& o : observations) {
    filter.update(o, gimbal.yaw);                    // 2. 关联 + 门控 + 更新，每条观测一次
}
filter.advanceStateMachine(timestamp_seconds);       // 3. 状态迁移 + 超时重置
filter.buildPrediction(gimbal, latency_s);           // 4. 生成指令
```

**拆开看，四步各干什么**：

| 步 | 方法 | 输入 | 输出 | 不改什么 |
|---|---|---|---|---|
| 1 | `predict(dt)` | 帧间隔 | 先验 `x`、先验 `P` | 不吃观测 |
| 2 | `update(o, yaw)` | 一条观测 | 后验 `x`、后验 `P` | 观测空时一次都不调 |
| 3 | `advanceStateMachine(ts)` | 时间戳 | `status_`、计数 | 不碰 `x`，只碰状态机 |
| 4 | `buildPrediction(gimbal, latency_s)` | 当前姿态、检测耗时 | `PredictionResult` | 不改状态，只读 |

三个必须记住的约定：

- **`predict` 一定先于 `update`**。它把 `F` 从上一帧推到这一帧，再把 `used_indices_`、`updated_this_frame_`、`init_used_this_frame_` 三个每帧标志清掉（`:316-318`）。
- **`advanceStateMachine` 每帧都要调，包括没有观测的帧**。数「连续丢了几帧」的是它，不是 `update`。
- **没有观测时 `update` 一次都不调**，但 `predict` 和 `advanceStateMachine` 照调。这就是「纯预测」的来源。

**顺序反了的后果很隐蔽**：先 `update` 后 `predict`，等于拿旧状态去关联新观测，滤波器能跑、曲线看着也平滑，只是每一帧都在用上一帧的 `F`。

# 四、预测步：`f`、`F`、`Q`

**一句话**：预测步就是「拿上一帧的状态，猜这一帧在哪」，由三样东西构成——`f` 是猜法本身，`F` 是这个猜法对每个状态的敏感度，`Q` 是承认这个猜法不完美。

**拆开看，三样各是什么**：

| 记号 | 名字 | 一句话 | 形状 | 代码 |
|---|---|---|---|---|
| `f` | 过程模型 | 匀速直线加匀角速度，半径不动 | 10 维进 10 维出 | `:219-224` |
| `F` | 状态转移矩阵 | `f` 的雅可比，`f` 是线性的所以就是它本身 | 10x10 | `:226-232` |
| `Q` | 过程噪声 | 「匀速直线」这个假设被违反了多少 | 10x10，每帧重算 | `:234-263` |

**三者关系**：`x_pred = F · x`、`P_pred = F · P · Fᵀ + Q`。`F` 推状态，`Q` 撑开不确定度。

**举个例子**，`dt = 6 ms`（165 fps）：

| 量 | 算出来 |
|---|---|
| `x[Px] += x[Vx] * dt` | 速度 2 m/s 时，位置前进 12 mm |
| `F(Px, Vx) = dt` | 0.006 |
| `Q(Vx, Vx) = σ_a² · dt²` | 6² × 3.6e-5 ≈ 1.3e-3 |
| 同一个 `Q(Vx, Vx)`，若 `dt = 50 ms` | 6² × 2.5e-3 = 0.09，**差 70 倍** |

最后一行的意思是：`Q` 不能写死成一个常数矩阵，它每帧随 `dt` 变。

## 4.1 状态外推 `propagate`（:219-224）

```cpp
x[Px] += x[Vx] * dt;
x[Py] += x[Vy] * dt;
x[Pz] += x[Vz] * dt;
x[Yaw] = wrapToPi(x[Yaw] + x[YawRate] * dt);
```

**一句话**：四行里前三行是 `位置 += 速度 × 时间`，第四行是 `角度 += 角速度 × 时间`，其余六个状态（半径、`omega` 等）原样不动。

第四行外面套了 `wrapToPi`，这是防止角度跑到 `10π` 之后 `cos / sin` 精度掉光的主防线。`theta_c` 外推后立刻包裹回 `(-π, π]`。

## 4.2 状态转移 `F`（:226-232）

```cpp
F.setIdentity();
F(Px, Vx) = dt;  F(Py, Vy) = dt;  F(Pz, Vz) = dt;  F(Yaw, YawRate) = dt;
```

**一句话**：10x10 的单位阵，加 4 个 `dt`。

**拆开看，为什么是单位阵加 4 个 `dt`**：`F[i][j] = ∂f_i / ∂x_j`。`f` 里 `px` 只依赖 `px` 和 `vx`，所以 `F` 的 `Px` 那一行只有两个非零元：对角上的 1（`∂px/∂px`）和 `(Px, Vx)` 位置的 `dt`（`∂px/∂vx`）。四组 `[位置, 速度]` 配对各一组，其余位置 `f_i` 不依赖 `x_j`，所以是 0。对角全 1 是因为「半径不动、`omega` 不变」这些项对自身求导等于 1。

**它必须和 `propagate` 逐字对应**，这是硬要求：`F` 是 `f` 的雅可比，两者不一致时 `P` 长的速度和状态跑的速度对不上，短期看不出来，几秒后 `P` 会被喂爆。

**举个例子**：把 `F(Yaw, YawRate)` 从 `dt` 错写成 `1.0`，`omega` 的不确定度会被当成 `theta_c` 的不确定度原样搬过去（不乘时间），`P(Yaw,Yaw)` 一帧涨一个 `P(YawRate,YawRate)`，几百帧后涨到天文数字，`covarianceIsStable` 永远进不去。

## 4.3 过程噪声 `Q`（:234-263）

**一句话**：`Q` 是「匀速直线这个假设，每帧被违反了多少」，按随机加速度模型离散化，每帧随 `dt` 重算。

**怎么来的**：假设每个 `[位置, 速度]` 轴对的加速度是白噪声，功率谱密度 `σ_a²`，积分两次得到

```
Q_pv = σ_a² · [[ dt^4/4, dt^3/2 ],
               [ dt^3/2, dt^2   ]]
```

```cpp
const double linear = config_.accel_noise_m_s2 * config_.accel_noise_m_s2;
for (const auto& pair : pairs) {
    Q(pair[0], pair[0]) = linear * dt4 / 4.0;
    Q(pair[0], pair[1]) = linear * dt3 / 2.0;
    Q(pair[1], pair[0]) = linear * dt3 / 2.0;
    Q(pair[1], pair[1]) = linear * dt2;
}
```

**拆开看，三个物理量各给一份原料**：

| 原料 | 默认 | 物理含义 | 为什么取这个数 |
|---|---|---|---|
| `accel_noise_m_s2` | 6.0 m/s² | 中心三轴的加速度标准差 | RM 步兵 0 到 20 m/s 约 1~2 秒，瞬时机动约 10 m/s²，取一半 |
| `angular_accel_noise_rad_s2` | 12.0 rad/s² | 车体 yaw 角加速度标准差 | 车能快速起旋停旋 |
| `radius_drift_m` | 0.2 m | 半径随机游走强度 | 另加地板 `(1 mm)²` 防冻死 |

**`Q` 是每帧现算的矩阵，那三个数是原料，不是「加权和」。** 这点答辩最容易被问倒，见上面那张 `dt = 6 ms` 对 `dt = 50 ms` 的表，差 70 倍。

**量纲自检**：`σ_a²` 是 m²/s⁴，乘 dt⁴ 得 m²、乘 dt² 得 (m/s)²。**`Q` 和 `R` 的对角线都必须是方差不是标准差。** 代码里 `Q` 用 `σ²`（`:241` 已经平方）、`R` 用 `sigma*sigma`（`:273`/`:274` 显式平方），两处写法不同，**漏平方是 3 倍量级的偏差且不报错**。

半径那一行（:257-262）：

```cpp
const double radius_variance =
    std::max(config_.radius_drift_m * config_.radius_drift_m * dt2,
             config_.radius_variance_floor_m2);
```

**一句话**：半径那一项不是加速度模型，是随机游走，另外压了一个地板值。

半径物理上几乎不变，但完全给 0 会让滤波器把先验的 0.25 m 冻死、再也学不到真值。**加地板是留一点自由度，不是「这里噪声真的这么大」。**

# 五、观测模型 `h` 与雅可比 `H`

**一句话**：`h` 是一台翻译机，把「我猜的状态」翻译成「按这个状态，我应该看到板心在哪」；`H` 是这台翻译机的导数，说每个状态动一点，看到的板心会动多少。

**拆开看，`h` 的输出由三块拼成**：

| 块 | 是什么 | 来自哪个状态 |
|---|---|---|
| 方位角 `psi` | 这块板在车上的**方向** | `theta_c` 加上编号偏移 |
| 半径 `radius` | 这块板离转轴**多远** | `x[Radius1]` 或 `x[Radius2]` |
| 高度 `h_i` | 这块板比转轴**高多少** | 常量表 `plate_height_m[i]` |

拼起来是 `u = 中心 + 半径 × (cos psi, sin psi) 的高度补丁`，再换回云台系就是 `h`。

## 5.1 观测量的选择

**一句话**：只用板心的三维坐标，不用任何角度（`ArmorEkf.cpp:9-13`）。

**为什么不用角度**：`armor_solve` 输出的 `armor_yaw` 实现成「板面法向的偏航角」，而任务书三处措辞指的是「板心方位角」，**两者差 90 度**。把它当观测量，符号错了会把整个滤波带偏，而且不会报错。三维板心没有这个歧义。

## 5.2 观测模型 `h`（:163-175）

```cpp
const int i = armor_index;
const double psi = x[Yaw] + static_cast<double>(i) * plate_spacing_rad;
const double radius = x[radiusIndex(i)];
Eigen::Vector3d u;
u << x[Px] + radius * std::cos(psi),
     x[Py] + radius * std::sin(psi),
     x[Pz] + plate_height_m[i];
return worldToGimbal(gimbal_yaw) * u;
```

**一句话**：第 `i` 块板在 W 系里的方位角是 `psi_i = theta_c + i * spacing`，板心 = 旋转中心 + 半径沿这个方位角，最后换回云台系。

**拆开看逐项**：

| 代码 | 是什么 | 谁给的 |
|---|---|---|
| `psi` | 第 `i` 块板的**方位角**，`spacing` 默认 90 度 | `theta_c` 是 0 号板的方位角，其余三块按编号顺序挂上去 |
| `radius` | 这块板用的那个半径 | `radiusIndex(i)`：偶数号取 `r1`，奇数号取 `r2` |
| `u` | 板心在 **W 系**里的三维坐标 | 前两行是极坐标展开，第三行加高度 |
| `worldToGimbal(...) * u` | 换回 **G 系** | 因为观测值本来就在 G 系里 |

**`h` 和 `z` 同系，不需要把观测搬到世界系。** 这是「运动模型放在 W 系、观测模型放在 G 系」这个设计的代价，只在这一处付。

**举个例子**，取 `theta_c = 0.3` rad、`radius = 0.25 m`、`pz = 0.1 m`、高度全零，四块板的方位角与板心：

| `i` | `psi_i` | 角度 | 板心相对中心的方向 | 是车上哪一块 |
|---|---|---|---|---|
| 0 | 0.300 | 17.2 度 | 车头往左偏 17 度 | 0 号 |
| 1 | 1.871 | 107.2 度 | 车左侧偏后 17 度 | 1 号 |
| 2 | 3.442 | 197.2 度 | 车尾偏左 17 度 | 2 号 |
| 3 | 5.012 | 287.2 度 | 车右侧偏前 17 度 | 3 号 |

`i = 0` 那块：`u = (5.00 + 0.25 × cos 0.3, 0 + 0.25 × sin 0.3, 0.1) = (5.2388, 0.0739, 0.1000)`。再乘一次 `worldToGimbal(0.30)` 就得到这一帧应该看到的板心。

**注意 `psi` 是「板心方向」，不是「板面朝向」。** 两者在 RM 车上数值上恰好重合（板装在半径上、板面朝外），但代码里 `psi` 的职责是**摆板的位置**，不是描述朝向。

编号必须已经折算到 `[0, plate_count)`（`normalizeIndex`，`:149-155`）。它用的是数学取模而不是 C++ 的 `%`，**负数输入会转正**。

**`i` 不是固定的物理位置**：每帧由关联临场决定现在看到的是几号，见第八节。

## 5.3 雅可比 `H`（:177-204）

**一句话**：`h(x) = M(θg)^T · u(x)`，所以 `H` 的每一列就是 `M(θg)^T` 乘上 `u` 对该分量的偏导。

```cpp
H.col(Px) = to_gimbal * Eigen::Vector3d(1.0, 0.0, 0.0);
H.col(Py) = to_gimbal * Eigen::Vector3d(0.0, 1.0, 0.0);
H.col(Pz) = to_gimbal * Eigen::Vector3d(0.0, 0.0, 1.0);

const Eigen::Vector3d tangential(-std::sin(psi), std::cos(psi), 0.0);
const Eigen::Vector3d radial(std::cos(psi), std::sin(psi), 0.0);
H.col(Yaw)             = to_gimbal * (radius * tangential);
H.col(radiusIndex(i))  = to_gimbal * radial;
```

**拆开看，10 列各是什么**：

| `H` 的列 | 内容 | 物理含义 |
|---|---|---|
| `Px` / `Py` / `Pz` | `to_gimbal * 单位轴` | 中心往右挪 1 mm，板心也往右挪 1 mm，1:1 |
| `Yaw` | `to_gimbal * (radius * tangential)` | 方位角转 1 rad，板沿**切向**动，长度是 `radius` |
| `radiusIndex(i)` | `to_gimbal * radial` | 半径长 1 米，板沿**径向**动，长度是 1 |
| `vx` `vy` `vz` `omega` | 恒零 | 位置不依赖速度，板心不依赖角速度 |

**两个静默陷阱，都在这一节。**

**陷阱一：对 `theta_c` 的偏导和对 `r` 的偏导差 90 度。** 这是全文件最值得单独记的一句（`:194-199` 的注释就是这条）：

- 方位角转一点，板沿**切向**动；
- 半径长一点，板沿**径向**动。

图省事共用同一个向量，滤波在慢转时会收敛到错误的半径，而且重投影误差照样很小。

**陷阱二：只有一列带 `radius` 因子。** `Yaw` 那一列乘了 `radius`，`radiusIndex(i)` 那一列没有。原因是「角度转 1 rad 走多长的弧」要乘半径，「半径长 1 米」本来就是一米。

**举个例子**，取 `psi = 0`，也就是 0 号板正好在车头方向，两个向量一眼能分开：

| 动的状态 | 板心怎么动 | 用哪个向量 |
|---|---|---|
| `theta_c` 转 +1 rad | 板沿左（`+y`）移动 `radius` 米 | `tangential = (0, 1, 0)` |
| `r1` 长 +1 m | 板沿前（`+x`）移动 1 米 | `radial = (1, 0, 0)` |

两者的方向正好垂直。**如果偷懒共用 `(−sin psi, cos psi, 0)`，`r1` 那一列会变成「半径变化时板沿切向动」，与 `theta_c` 列完全共线，滤波器就再也分不开「车转了多少」和「半径有多大」**——这正是慢转时半径收敛慢的来源之一。

`H` 一律走 `worldToGimbal` 求，不手抄 `Mᵀ` 的元素（`:186-188`）。手推雅可比唯一的保险是 `tests/test_ekf_predict.cpp` 用有限差分逐元素对拍，容差 1e-6。

# 六、观测噪声 `R`（:265-277）

**一句话**：`R` 是「这个板心观测有多不准」，单位 m²，而且每帧随观测距离线性变大。

```cpp
const double d = z.norm();
const double lateral = config_.lateral_noise_scale * d + config_.lateral_noise_base_m;
const double depth   = config_.depth_noise_scale   * d + config_.depth_noise_base_m;
Eigen::Matrix3d R = Eigen::Matrix3d::Zero();
R(0, 0) = depth * depth;
R(1, 1) = lateral * lateral;
R(2, 2) = lateral * lateral;
```

**拆开看，三个对角分量**：

| 分量 | 轴 | 公式 | 含义 |
|---|---|---|---|
| `R(0,0)` | 云台系 x，也就是**沿视线** | `0.010 · d + 0.010` | **深度**。单目靠板宽反推，最不准 |
| `R(1,1)` | 云台系 y | `0.002 · d + 0.005` | **横向**。靠像素精度 |
| `R(2,2)` | 云台系 z | 同横向 | 同上 |

**轴序是个静默点**：云台系是前 / 左 / 上，所以第 0 个分量沿视线，是**深度**。**放错轴不会报错**，只会让滤波器该信的不信、该松的不松，表现为收敛慢、稳态抖。

两个系数差 5 倍（`0.010` 对 `0.002`），所以只看随距离那一项，**深度的方差是横向的 25 倍**。

**举个例子**，`d = 5 m` 时：

| 量 | 值 | 换算 |
|---|---|---|
| `lateral` | 0.002 × 5 + 0.005 = 0.015 m | 标准差 1.5 cm |
| `depth` | 0.010 × 5 + 0.010 = 0.060 m | 标准差 6 cm |
| `R(0,0)` | 0.0036 m² | |
| `R(1,1) = R(2,2)` | 0.000225 m² | |
| 实际方差比 | 16 倍 | 系数比 25 倍，但 `_base_m` 把比值拉近了 |

**数值来历**（`ArmorEkf.cpp:30-33`）：仓库里已经实测过角点抖动，1.08 m 处单次重投影 0.70~0.79 px、同一角点两帧间最多动 1.41 px。按 `delta_px · d / f` 估横向约 `0.0006 · d`，再留约 3 倍余量取 `0.002 · d + 0.005`。深度按同比例放大。这里用的 `f` 是 1805 px，**量那批角点时的本机标定**，不是现在 `config/camera.yaml` 里车上那台的 1783 px——差 1% 量级，落在 3 倍余量里，`scale` 不用改。**这两个数字不是拍的。**

**`R` 是「填」的，不是「算」的。** 和 `Q` 一样它每帧现算，但每帧只是把两个标量按当前距离线性插一下。填得对不对，运行时唯一的检验量是 NIS。

**一个待办的内部张力**：`R` 的余量取了 3 倍，而进 `Stable` 的 `nis_mean_gate = 8.0` 又要求 NIS 均值偏低，两者方向相反。深版 12 节有记录，尚未定论。

# 七、初始协方差 `P0`（:279-292）

**一句话**：`P0` 是「刚初始化那几帧，每个状态可能差多少」的标准差平方。

```cpp
P(Px,Px) = P(Py,Py) = P(Pz,Pz) = 1.0;                 // 位置 1 m^2
P(Vx,Vx) = P(Vy,Vy) = 25.0;  P(Vz,Vz) = 9.0;          // 速度 5 m/s
P(Yaw,Yaw) = 0.25;                                    // 约 0.5 rad
P(YawRate,YawRate) = 9.0;                             // 3 rad/s
P(Radius1,Radius1) = P(Radius2,Radius2) = 0.0225;     // 0.15 m
```

**拆开看，每个数开方就是标准差**：

| 分量 | `P0` 对角 | 开方（标准差） | 读作 |
|---|---|---|---|
| 位置 | 1.0 m² | 1.0 m | 初始中心可能差 1 米 |
| 速度 | 25 (m/s)² | 5 m/s | 初始速度可能差 5 m/s |
| 速度 z | 9 (m/s)² | 3 m/s | 竖直方向给得小一些 |
| `theta_c` | 0.25 rad² | 0.5 rad = 29 度 | 车头朝向可能差 29 度 |
| `omega` | 9 (rad/s)² | 3 rad/s | 角速度可能差 3 rad/s |
| 半径 | 0.0225 m² | 0.15 m | 半径可能差 15 cm |

**`P0` 是第三样东西，和 `Q`、`R` 都不同**：它只在初始化的那几帧起作用，之后被更新自然收缩。给大一点的用处是「初始更信观测」，前几帧收敛快。

**三者的关系别混**：

| 量 | 怎么来 | 什么时候起作用 | 维度 |
|---|---|---|---|
| `P = E[(x - x̂)(x - x̂)ᵀ]` | **算出来**的 | 每帧 | 10x10，和状态同维 |
| `Q` | **填**进去的原料 | 每帧随 `dt` | 10x10，状态空间 |
| `R` | **填**进去的原料 | 每帧随距离 | 3x3，观测空间 |
| `P0` | **填**进去的原料 | 只在前几帧 | 10x10 |

**举个例子**：初始给位置 1 m²，前几帧观测一看中心其实只差几厘米，`P(Px,Px)` 会被 `K` 一步压到 1e-3 量级；如果 `P0` 反过来给 1e-6，第一帧 `K ≈ 0`，滤波器会固执地相信自己那个瞎猜的初值，收敛反而慢。

# 八、关联与三道闸，Joseph 更新

`associateAndUpdate`，`:422-497`。这是 EKF 里最像「工程」的一段。

**一句话**：这一整段回答一个问题——**这一帧看到的这块板，是四块里的哪一块，收不收，收进来之后状态怎么改。**

**拆开看，四步**：

| 步 | 干什么 | 代码 |
|---|---|---|
| 入口两道检查 | 数值有限吗、重投影误差过门吗 | `:423-433` |
| 在四块板里挑一块 | 谁的**马氏距离**最小就配给谁 | `:439-467` |
| 全局统计闸 | 挑出来的那个离谱吗 | `:469-476` |
| 更新 | `K` 加权修正，Joseph 形式写协方差 | `:478-487` |

## 8.1 入口两道检查（:423-433）

```cpp
if (!z.allFinite() || !std::isfinite(observation.reprojection_error)) { ++rejected_count_; return false; }
if (observation.reprojection_error > config_.max_reprojection_error_px) { ++rejected_count_; return false; }
```

**一句话**：板心坐标必须全是有限数，重投影误差必须小于 5 px。

**这 5 px 是重投影闸**。真实帧实测角点抖动不超过 1.41 px、重投影 0.70~0.79 px，**余量 6.4 倍**。

## 8.2 在四块板里挑一块（:439-467）

```cpp
for (int i = 0; i < config_.plate_count; ++i) {
    if (used_indices_[i]) continue;                       // 一帧内一块板只配一条观测
    const Eigen::Vector3d h = observationModel(x_, i, gimbal_yaw, ...);
    const Eigen::Vector3d residual = z - h;
    if (residual.norm() > config_.jump_gate_m) continue;  // 物理跳变闸 0.6 m
    const ObservationJacobian H = observationJacobian(x_, i, gimbal_yaw, ...);
    const Eigen::Matrix3d S = H * P_ * H.transpose() + R;
    const double nis = residual.transpose() * S.inverse() * residual;
    if (!std::isfinite(nis)) continue;
    if (nis < best_nis) { best_nis = nis; best_index = i; best_h = h; best_H = H; }
}
```

**一句话**：对四块板逐个假设「观测是这一块」，算一个残差，谁最不离谱就配给谁。

**拆开看，三个设计点**：

**一、用马氏距离而不是最近欧氏距离**（`:437-438`）。侧板的横向不确定度大，直接用欧氏距离会把它误配进来。马氏距离把 `P` 和 `R` 都算进去了——**它把「哪块板更可能」带上了方向性**，欧氏距离给不了这个。

**二、`used_indices_` 保证一帧内一块板只配一条观测**（`ArmorEkf.hpp:243`、`:445-447`）。同帧有两块板时，两个都配到同一个编号会让两条观测互相打架。这个数组在 `predict()` 开头清空。

**三、`S = H P Hᵀ + R` 是运行时的判断量**。答辩常问「怎么知道 `R` 填得对不对」，正确答案是这个比值，**不是「`Q` 比 `R`」**。`Q` 够不着这里，它绕道 `P` 才进来，而且两者量纲、维度都不同，不能直接相除。

**举个例子**，`S` 两项同量纲（3x3，m²）才可比：

| 项 | 是什么 | `d = 5 m` 时量级 |
|---|---|---|
| `H P Hᵀ` | 模型侧不确定度投影到观测空间 | 收敛后约 1e-4 m² 量级 |
| `R` | 传感器侧 | 1e-4 ~ 1e-3 m² |

**谁大就信谁少**。`R` 一大，`K` 就小，滤波器主要靠自己预测。

## 8.3 全局统计闸（:469-476）

```cpp
if (best_index < 0)              { ++rejected_count_; return false; }
if (best_nis > config_.nis_gate) { ++rejected_count_; return false; }   // 11.34 = chi2(3, 99%)
```

**一句话**：连最好的那块都离谱，这条观测就不要了。

**11.34 怎么来的**：3 个观测分量，所以自由度是 3，卡方分布 99% 分位点就是 11.34。过了这一关的观测才会被吃下去。

**三道闸的分工**：

| 闸 | 门槛 | 挡什么 |
|---|---|---|
| 跳变闸 | 0.6 m | 物理上不可能的 |
| 统计闸（NIS） | 11.34 | 统计上不可能的 |
| 重投影闸 | 5 px | 解算质量差的 |

**举个例子**：一条观测算出来的残差是 `(0.3, 0.05, 0.02)` 米，`S` 的对角是 `(0.06², 0.015², 0.015²)` m²（`d = 5 m` 时的 `R`）。跳变闸查 `‖residual‖ = 0.305 m < 0.6 m`，过。NIS 大约是 `(0.3/0.06)² + …`，深度那一项单独就 25，远超 11.34，**拒**。这就是深度上的离谱值被抓住的样子。

## 8.4 更新（:478-487）

```cpp
const Eigen::Matrix<double, 10, 3> K = P_ * best_H.transpose() * S.inverse();
x_ += K * residual;
const Covariance identity_minus_kh = Covariance::Identity() - K * best_H;
P_ = identity_minus_kh * P_ * identity_minus_kh.transpose() + K * R * K.transpose();
x_[Yaw] = wrapToPi(x_[Yaw]);
```

**一句话**：`x += K × 残差`，`K` 是「该信观测几成」，协方差用 Joseph 形式写。

**拆开看**：

| 行 | 干什么 | 关键点 |
|---|---|---|
| `K = P Hᵀ S⁻¹` | 卡尔曼增益 | 10x3，`R` 小则 `K` 大，更信观测 |
| `x_ += K * residual` | 状态修正 | 修正量按残差大小和 `K` 分配 |
| Joseph 形式 | 协方差修正 | 比 `(I - KH) P` 多一次矩阵乘 |
| `x_[Yaw] = wrapToPi(...)` | 再包一次角 | `x += K · residual` 可能把它推到 `π` 外面 |

**为什么非要用 Joseph 形式**：比标准形式多一次矩阵乘法，但**数值上不会失去正定性**。长时间跑（上车要跑几分钟、几万帧）时这个差别是真的：标准形式在累积误差下可能让 `P` 出现负特征值，然后滤波器发散。多的一次乘法换稳定性。

# 九、初始化（:352-420）

**一句话**：初始化就是把「第一块看到的板」，反推成「车心在哪、车头朝哪个方向」。

**拆开看，两件事**：

| 步 | 干什么 | 代码 |

| 三帧一致门 | 确认连续 3 帧看到的是同一块板 | `:353-385` |
| 反推旋转中心 | 由板心、板面朝向、半径，算出 `theta_c` 和中心位置 | `:387-403` |

## 9.1 三帧一致门（:353-385）

```cpp
if (init_used_this_frame_) return false;                 // 同一帧只用第一条观测
init_used_this_frame_ = true;
...
const Eigen::Vector3d u = gimbalToWorld(gimbal_yaw) * z; // 先转到 W 系
if (init_count_ == 0) { init_mean_ = u; init_count_ = 1; }
else if ((u - init_mean_).norm() <= config_.init_consistency_m) {   // 0.3 m
    init_mean_ = (init_mean_ * init_count_ + u) / (init_count_ + 1);
    ++init_count_;
} else { init_mean_ = u; init_count_ = 1; }              // 不接近就重来
if (init_count_ < config_.init_frames) return false;     // 3 帧
```

**一句话**：连续 3 帧的板心彼此相差不到 0.3 m，才算「盯住了同一块板」，才开始初始化。

**为什么要这样**：防止把两块不同的板拼成一个中心。

**同一帧只用第一条观测是配套的**（`ArmorEkf.hpp:254-256` 的注释）：一帧里如果有两块板，两块之间的间距会顶掉 0.3 m 的一致门，计数永远凑不满。

**举个例子**：一帧里两块板相距 0.5 m，第一帧取到 A 板、第二帧取到 B 板，`(u - init_mean_).norm() = 0.5 > 0.3`，计数被打回 1，永远到不了 3。

## 9.2 反推旋转中心（:387-403）

这是初始化里唯一需要想一下的地方：

```cpp
x_.setZero();
x_[Yaw] = wrapToPi(std::atan2(-init_mean_.y(), -init_mean_.x()));
x_[Radius1] = x_[Radius2] = config_.initial_radius_m;    // 0.25 m
x_[Px] = init_mean_.x() - config_.initial_radius_m * std::cos(x_[Yaw]);
x_[Py] = init_mean_.y() - config_.initial_radius_m * std::sin(x_[Yaw]);
x_[Pz] = init_mean_.z() - config_.plate_height_m[0];
P_ = initialCovariance();
```

**一句话**：板装在外侧、板面朝外，而检测的条件就是「板面法向朝向相机」，所以这块板的**径向方向与「板心指向相机」同向**，也就是板心视线的**反方位**。

**拆开看每一行**：

| 行 | 算的是 | 为什么 |
|---|---|---|
| `x_[Yaw] = atan2(-y, -x)` | 0 号板的方位角 | 板心视线的**反**方位（取负号的原因） |
| `r1 = r2 = 0.25` | 两个半径 | 先给个名义值，让观测去修 |
| `Px = x - r·cos(Yaw)` | 中心横坐标 | 中心 = 板心 - 半径沿方位角 |
| `Py = y - r·sin(Yaw)` | 中心纵坐标 | 同上 |
| `Pz = z - h_0` | 中心高度 | 减掉 0 号板的常量高度 |

**注意 `atan2(y, x)` 是标准数学约定，因此 `theta_c` 是左正。**

**举个例子**，看到一块板，板心在 W 系是 `(5.25, 0, 0.10)`，半径 0.25 m：

| 量 | 取对（用 `atan2(-y, -x)`） | 取错（用板心自己的方位角 `atan2(y, x)`） |
|---|---|---|
| `theta_c` | `atan2(0, -5.25) = π` = 180 度 | `atan2(0, 5.25) = 0` |
| `Px` | `5.25 - 0.25 × cos(π) = 5.50` m | `5.25 - 0.25 × cos(0) = 5.00` m |
| 中心误差 | 0 | **0.50 m** |

取错时正好偏 `2r = 0.50 m`，对上了 `2r·cos(δ/2)` 在 `δ = 0` 时的值（`:394-395`）；`δ` 是这块板被看到的斜角。取对之后初始中心误差从「二三十厘米量级」降到「几厘米量级」。

**物理上讲一遍**：板心在正前方 5.25 m、朝向我们，说明车心在**更远处** 5.50 m，车头朝 180 度（0 号板在车的后侧、正对我们）。所以中心比板心更远，不是更近。

这条就是 2026-10-13 修掉的那个 bug，提交 `d3a7ff3`。当时的夹具每帧喂两块背对相机的板，写反初始化的那一版反而全绿，所以夹具口径也一起改了（教训见深版 12.6.7）。

**编号是任意的全局相位**：把看到的这块板当作 0 号板，不影响物理，后续会随观测自动纠正（`:387-388`）。

# 十、状态机与 `crc`（:503-542）

**一句话**：状态机就是 `crc` 三个值之间的迁移规则，全部行为由四个数决定。

**拆开看，三态是什么**（`TrackingState` 直接对应历史通信字段 `crc`，`AutoAimTypes.hpp:20-25`）：

```
NoTarget = 0,   Stable = 1,   Unstable = 2,
```

| 值 | 意思 | 什么时候 |
|---|---|---|
| 0 `NoTarget` | 没有目标 | 从头没抓到，或丢失超过 1.5 秒被推倒重来 |
| 2 `Unstable` | 有目标，但还不准 | 刚初始化，或刚丢了几帧 |
| 1 `Stable` | 跟住了 | 连续命中够久、协方差够小、NIS 够低 |

```cpp
if (updated_this_frame_) { miss_count_ = 0; ++hit_streak_; last_obs_ts_ = timestamp_seconds; }
else                     { ++miss_count_; hit_streak_ = 0; }
updated_this_frame_ = false;

// 长时间丢失
if (last_obs_ts_ > 0.0 && timestamp_seconds - last_obs_ts_ > config_.reset_timeout_s) { reset(); return; }

// 短时丢失的滞回
if (status_ == Stable && miss_count_ >= config_.stable_hold_misses) status_ = Unstable;

// 回升
if (status_ == Unstable) {
    const int required = ever_stable_ ? config_.recover_frames : config_.stable_frames;
    if (hit_streak_ >= required && covarianceIsStable() && recentNisMean() < config_.nis_mean_gate) {
        status_ = Stable; ever_stable_ = true;
    }
}
```

**拆开看，四个数**：

| 参数 | 默认 | 作用 | 换算成时间 |
|---|---|---|---|
| `stable_frames` | 15 | 首次进 `Stable` 要连续命中 15 帧 | 165 fps 下约 90 ms |
| `recover_frames` | 10 | **曾经**稳定过之后，遮挡恢复只要 10 帧 | 这就是 `ever_stable_` 的用处 |
| `stable_hold_misses` | 3 | 丢 3 帧以内仍按 `Stable` 处理，纯预测足够准 | 单帧丢约 6 ms |
| `reset_timeout_s` | 1.5 | 超过 1.5 秒没有有效观测直接重置 | 远大于真实遮挡（几百毫秒），不会误触发 |

**遮挡恢复的机制就落在这两个数上**：丢 3 帧以内不算丢；丢 4 到 10 帧转 `Unstable` 但状态还在，恢复只要 10 帧；丢超过 1.5 秒才推倒重来。这对应评分表验收重点第 6 条。

**举个例子**，目标被挡住的完整时间线（165 fps，一帧约 6 ms）：

| 丢失帧数 | 累计时间 | `status_` | 说明 |
|---|---|---|---|
| 0 | 0 | `Stable` | 正常跟踪 |
| 1~3 | 0~18 ms | `Stable` | 纯预测顶着，`rel_yaw` 照样准 |
| 4~10 | 24~60 ms | `Unstable` | 状态还在，只是不许开火 |
| 11 帧后重新看到 | 约 66 ms | `Unstable` -> 3 帧后 | 因为 `ever_stable_` 已是真，只要 10 帧 |
| 连续丢 > 1.5 s | 1.5 s | `NoTarget` | `reset()`，回到从零开始 |

## 10.1 `covarianceIsStable`（:544-552）

```cpp
const double center_std = std::sqrt(std::max(0.0, P_(Px,Px) + P_(Py,Py)));
const double radius_std = std::sqrt(std::max(0.0, P_(Radius1,Radius1) + P_(Radius2,Radius2)));
const double yaw_std    = std::sqrt(std::max(0.0, P_(Yaw,Yaw)));
return center_std < 0.10 && radius_std < 0.05 && yaw_std < 0.10;
```

**一句话**：`P` 的对角线开方，三个分量都够小才放行。

**拆开看三个门槛**：

| 检查 | 门槛 | 读作 |
|---|---|---|
| 中心 | 0.10 m | 车心位置的标准差小于 10 cm |
| 半径 | 0.05 m | 半径的标准差小于 5 cm |
| `yaw` | 0.10 rad | 车头朝向的标准差小于 5.7 度 |

**注意它是单向门**：只在 `Unstable -> Stable` 那一步查。进了 `Stable` 之后，只有连续丢 3 帧才降回 `Unstable`。**所以 `Stable` 可以和远超门槛的协方差共存**，深版 12.6.5 有实例。

# 十一、选板 `selectArmorIndex`（:600-648）

**一句话**：每帧要决定「瞄哪一块板」，由可见性和迟滞两件事决定。

**拆开看**：

| 件 | 规则 | 代码 |
|---|---|---|
| 可见性 | 板面大致朝着相机的板才考虑 | `:600-648` 前半 |
| 迟滞 | 新板要好过老板 5 度才切 | 同后半 |

## 11.1 可见性：只考虑板面朝外的板

```cpp
const Eigen::Vector3d normal(std::cos(psi), std::sin(psi), 0.0);   // 板面法向，朝外
if (normal.dot(-p_world / norm) < facing_threshold) continue;      // facing_threshold = cos(60 度)
```

**一句话**：`-p_world / norm` 是从板指向云台原点的单位向量，要求板面法向与它的夹角小于 60 度。

**拆开看**：法向与「板指向相机」的夹角小于 60 度，就是这块板大致正对着相机。侧后方的板直接排除。

**举个例子**：目标车头朝左转 90 度，此刻正对我们的是一块侧板，正前方那块板的法向和视线夹角接近 90 度，`cos(90 度) = 0 < cos(60 度) = 0.5`，被排除。

## 11.2 迟滞：新板要好过老板 5 度才切

```cpp
if (aim_index_ >= 0 && current_facing && aim_index_ != best) {
    const double current_abs_yaw =
        std::fabs(gimbalAzimuth(to_gimbal * platePositionWorld(x, aim_index_)));
    if (current_abs_yaw - best_abs_yaw < config_.aim_switch_margin_rad) best = aim_index_;
}
```

**一句话**：`aim_switch_margin_rad = 5 度`。没有迟滞的话，两块板势均力敌时 `aim_index_` 会每帧翻来覆去，输出的 `target_yaw` 跟着在 90 度之间跳，电控会看见一个突变指令。

**`commit` 参数**（`ArmorEkf.hpp:213-214`）是给弹道迭代用的：`commit = false` 时**只查询不写** `aim_index_`，否则试算值会把迟滞状态写脏（`:672-673` 的注释）。

**「切换」在数学上不跳变**：切换只是 `h` 里 `i` 的改选，中心、`theta_c`、`omega`、`r1 / r2` 在切换前后完全共享。**会跳的量根本不在状态里。** 这是「切换不跳变」的保证，也是答辩可以直接讲的一句。

**举个例子**：从 0 号板切到 1 号板，`psi` 从 `theta_c + 0` 换成 `theta_c + π/2`，`h` 的输出从「车头那块」换成「左侧那块」。但状态里没有一个数被重置，所以预测曲线在切换那一刻没有跳。

# 十二、`buildPrediction` 六步（:650-790）

**一句话**：从「滤波后的状态」到「一条串口指令」，中间六步。

**拆开看，六步各干什么**：

| 步 | 干什么 | 代码 |
|---|---|---|
| 1 | 取参数、算「从现在到该打的那一刻」有多久 `t0` | `:656-671` |
| 2 | 两次迭代解开「飞行时间与预测时长」的循环依赖 | `:672-689` |
| 3 | 把状态外推到 `t_pred`，选一块板来瞄 | `:691-698` |
| 4 | 算相对角，解弹道得到发射仰角 | `:700-711` |
| 5 | 角速度用中心差分 | `:713-745` |
| 6 | 填结果、开火门、有限性检查 | `:747-790` |

## 第 1 步：取参数、算 `t0`

```cpp
const double latency = smoothedLatency(latency_s);            // 20 帧滑动均值，截 [0, 0.2]
const double bias = ... gimbal.prediction_bias_s ...;          // 电控下发，单位秒
const double t0 = std::clamp(latency + bias, 0.0, config_.max_prediction_s);
```

**一句话**：`t0` 是「从现在到炮弹该出膛那一刻」的时间，由检测耗时和电控下发的偏置两项相加。

**拆开看**：

| 项 | 是什么 | 单位 | 典型值 |
|---|---|---|---|
| `latency` | 本帧「采集到此处」消耗的检测 + PnP 耗时，20 帧滑动均值抑噪 | s | 十几毫秒 |
| `bias` | 电控下发的 `prediction_bias_s`，想多预测一点就给正的 | s | 十毫秒量级 |
| `t0` | 两者相加，总长截在 `[0, 0.5]` 里 | s | 几十毫秒 |

**`bias` 允许为负**（`:660-661`）：电控若想「少预测一点」就会下发负值，单边截正会把它吃掉。总时长 `t0` 仍然截在 `[0, 0.5]` 里，异常值照样挡得住。

**`latency_s` 从哪来**：适配器里用 `steady_clock::now() - timestamp_seconds`（`StudentTasks.cpp:205-208`）。`timestamp_seconds` 是相机采集帧的 `steady_clock` 纪元秒，**所以这个差值正好是「采集到此处」消耗掉的检测加 PnP 时间**，不需要额外的计时器。

## 第 2 步：两次迭代解开「飞行时间 与 预测时长」的循环依赖

**一句话**：飞行时间依赖距离，距离依赖预测到什么时候，预测到什么时候又依赖飞行时间——循环了，两次迭代就够。

```
t0 = latency + bias
第 1 次: 假设 t_flight = 0  -> 算距离 -> 得 t_flight
第 2 次: 用刚才那个 t_flight -> 再算距离 -> 得新的 t_flight
t_pred = t0 + t_flight
```

```cpp
const Eigen::Matrix3d to_gimbal = worldToGimbal(gimbal_yaw);   // 后面几步共用

double flight_s = 0.0;
for (int iteration = 0; iteration < 2; ++iteration) {
    StateVector x_step = x_;
    propagate(x_step, t0 + flight_s);
    const int index = selectArmorIndex(x_step, gimbal_yaw, false);   // 只试算，不提交
    if (index < 0) break;
    const Eigen::Vector3d p_world = platePositionWorld(x_step, index);
    // 弹道从枪口量起。先在云台系里减掉枪口常向量，再取水平距离与高度差。
    const BallisticInputs inputs =
        ballisticInputsFromMuzzle(to_gimbal * p_world, config_.muzzle_offset_m);
    flight_s = solveBallistics(inputs.horizontal_m, inputs.vertical_m, 0.0)
                   .flight_time_s;
}
const double t_pred = std::clamp(t0 + flight_s, 0.0, config_.max_prediction_s);
```

**举个例子**，5 m 处：第 1 次迭代算得距离 5.0 m、飞行时间 0.21 s；第 2 次用 `t_pred = t0 + 0.21` 重新外推，距离可能是 5.03 m，飞行时间变成 0.211 s。差 1 ms 对仰角是 0.005 度量级，第二次就够。

## 第 3 步：外推与选板

```cpp
StateVector x_pred = x_;
propagate(x_pred, t_pred);
const int aim_index = selectArmorIndex(x_pred, gimbal_yaw, true);     // 这一次提交
if (aim_index < 0) return PredictionResult{};
const Eigen::Vector3d p_world_aim = platePositionWorld(x_pred, aim_index);
const Eigen::Vector3d p_gimbal_aim = to_gimbal * p_world_aim;
```

**一句话**：把状态外推到「炮弹该出膛那一刻」，然后挑一块板作为瞄准点，再把瞄准点转回云台系。

这一步的 `commit = true`，会真的写 `aim_index_`；第 2 步里那次是 `false`，只试算。

## 第 4 步：相对角与弹道发射仰角

```cpp
const double rel_yaw   = gimbalAzimuth(p_gimbal_aim);     // atan2(-y, x)，右正
const double rel_pitch = gimbalElevation(p_gimbal_aim);   // atan2(z, hypot(x, y))，抬头为正

const BallisticInputs aim_inputs =
    ballisticInputsFromMuzzle(p_gimbal_aim, config_.muzzle_offset_m);

const double command_pitch =
    solveBallistics(aim_inputs.horizontal_m, aim_inputs.vertical_m,
                    gimbal_pitch + rel_pitch)             // 回退值 = 不作补偿的绝对几何仰角
        .launch_pitch_rad;
```

**一句话**：`rel_yaw` / `rel_pitch` 是「瞄准点在云台系里的角度」，`command_pitch` 是要抬到多高、已经算上重力下坠。

**拆开看两个视线角**：

| 角 | 公式 | 正方向 | 含义 |
|---|---|---|---|
| `rel_yaw` | `atan2(-y, x)` | 右为正 | 瞄准点偏左还是偏右 |
| `rel_pitch` | `atan2(z, hypot(x, y))` | 抬头为正 | 瞄准点偏上还是偏下 |

两个函数在 `:44-50`，和 `main.cpp:448-450` 的 `pnp_yaw_rad` / `pnp_pitch_rad` **逐字同式**。集中在一处，别在调用处散抄。

### 为什么弹道输入要先换到云台系再减枪口

**一句话**：枪口比云台 P 轴原点前 74.1 mm，弹道该从枪口量起，而**这个偏移在云台系里是常量**。

**拆开看**：相机、云台 P 轴、摩擦轮三者刚体固定在同一个俯仰层上，云台怎么转这个向量都不变。云台系与世界系只差一个绕 z 的 yaw，`hypot(x, y)` 与 z 都不过 yaw，**所以在云台系里减，与在世界系里减掉那个已经转过 yaw 的向量逐位相同**。

**反过来，若在世界系里直接减常向量 `(0.0741, 0, 0)`，误差随 yaw 走**。目标在云台系正前方 5 m 时，实测水平距离误差：

| 云台 yaw | 水平距离误差 |
|---|---|
| 30 度 | 10.07 mm |
| 60 度 | 37.46 mm |
| 90 度 | **74.65 mm** |

90 度时正好错整整一个偏移量，因为那时枪口在世界系里跑到了 `(0, -0.0741, 0)`。

偏移是常量、又只进输出层，不进状态也不进观测，**所以补它不用重扫 Q/R**。`distance_m` 也**没有**跟着挪到枪口，仍是 `p_gimbal_aim.norm()`，与 `pnp_distance_m` 同口径。

### `command_pitch` 是 2026-10-16 改的那处

第三个参数是弹道解不收敛时的回退值，即「不作补偿的几何绝对仰角」 `gimbal_pitch + rel_pitch`。`solveBallistics`（`:64-84`）：

```cpp
solution.launch_pitch_rad = geometric_pitch_rad;                // 先放回退值
if (!std::isfinite(horizontal_m) || !std::isfinite(vertical_m)) return solution;
Bullet_Model model(horizontal_m, vertical_m);
const float time = model.bullet_iteration_cal();
if (!std::isfinite(time) || time <= 0.0F) return solution;      // 不收敛，回落到几何角
solution.flight_time_s = time;
if (std::isfinite(model.beta) && std::fabs(model.z_diff) < model.err_max) {
    solution.launch_pitch_rad = model.beta;                     // 才是补偿后的角
    solution.converged = true;
}
```

**`Bullet_Model` 是什么**（`armor/src/BulletModel.cpp`）：一个带空气阻力的迭代弹道解，`Kf = 0.08`、`g = 9.81`、初速 `velo = 24`、收敛判据 `|z_diff| < 0.0001`、上限 100 次迭代。**它返回的 `beta` 是绝对发射仰角**（高于水平面），恒大于瞄准点的几何仰角 `eta`，**差值就是重力与空气阻力造成的下坠补偿。**

小角度下这个差值几乎与高度无关：

```
beta - eta 约等于 g * d / (2 * v^2)
```

**举个例子**，`v = 24 m/s` 时：

| 距离 | 该多抬 |
|---|---|
| 1 m | 0.49 度 |
| 3 m | 1.46 度 |
| 5 m | 2.44 度 |
| 10 m | 4.88 度 |

**宁可少补，也不能把一个没落到位的中途值发出去**：撞上 100 次迭代上限时 `z_diff` 还很大，说明 `beta` 是中途值，此时回落到纯几何角，等价于不作补偿。这是 `:79` 那个附加条件的用处。

**依据**：链路里写着「延迟和弹道补偿」，位置在「输出 yaw/pitch」之前，所以这是自瞄侧的活。学长 2026-10-16 的「补偿是算法组做」是印证。

## 第 5 步：角速度用中心差分

```cpp
constexpr double kRateHalfWindowS = 0.005;                  // 正负 5 ms
const double t_early = std::max(0.0, t_pred - kRateHalfWindowS);
const double t_late  =         t_pred + kRateHalfWindowS;
... propagate(x_early, t_early); propagate(x_late, t_late); ...
const double yaw_velocity =
    dt_window > 0.0 ? wrapToPi(yaw_late - yaw_early) / dt_window : 0.0;
const double pitch_velocity =
    dt_window > 0.0 ? (pitch_late - pitch_early) / dt_window : 0.0;
```

**一句话**：不用状态里的 `omega` 直接换算，而是对**输出角**在 `t_pred ± 5 ms` 做中心差分。

**好处**是切换装甲板、换半径这些非线性环节都被算进去了，**输出的速率和输出的角严格自洽**。

`pitch_early` / `pitch_late` **也各做一次弹道解**（:733-740），不是用几何角。理由在 `:727-728`：`target_pitch` 是补偿后的角，它的速率也必须来自补偿后的角，否则同一个上报结构里两个量对不上。

`yaw_velocity` 用 `wrapToPi` 包一道，因为两个时刻的角可能跨界。

**举个例子**：正负 5 ms 的窗口，两个时刻的 `rel_yaw` 分别是 0.100 与 0.101 rad，`yaw_velocity = 0.001 / 0.010 = 0.1 rad/s`。

## 第 6 步：填结果、开火门、有限性检查

```cpp
result.target_yaw   = static_cast<float>(gimbal_yaw + rel_yaw);   // 绝对云台指令
result.target_pitch = static_cast<float>(command_pitch);
```

**一句话**：输出的两个角都是**绝对云台角**，不是相对角。

**依据**在 `:769-770`：框架的 `setSafeOutput` 把安全帧写成 `target_yaw = message.yaw`（`AppSupport.cpp:66-67`），意思是「保持当前」，误差 0。只有 target 是绝对角时这一句才自洽。

### `target_yaw` 会不会跟着 `gimbal.yaw` 一起漂

**会，也不会，要分开看。**

`target_yaw = gimbal_yaw + rel_yaw` 当然是加法，但 **`rel_yaw` 不是常数**，它每帧由滤波后的状态重算：先把世界系里的瞄准点用 `worldToGimbal(gimbal_yaw)` 转回当前云台系，再取方位角（`:697-702`）。**所以云台自己转过去的过程中，两个操作数一增一减。**

**举个例子**，瞄准点在世界系里的绝对方位角是 12（右正），云台从 10 转到 15：

| `gimbal.yaw` | `rel_yaw` | `target_yaw` |
|---|---|---|
| 10 | +2 | 12 |
| 15 | -3 | 12 |

**`target_yaw` 停在 12。**

物理上：一开始目标在炮口右偏 2，云台往右追了 5 之后变成左偏 3，指令始终是同一个绝对角。**这就是「绝对角」的含义**，也是 `testGimbalRotationIsNotTargetMotion` 在测的事：云台摆动 ±0.35 rad，估计出的目标位置一步没动。

要让 `target_yaw` 跟着 `gimbal.yaw` 一比一跑（10 到 15、12 到 17），需要 `rel_yaw` 恒为 +2，也就是瞄准点在云台系里一步没动，等于目标跟着云台一起转。**静止目标不是这种。** 目标真的在动时 `target_yaw` 才变，而它的变化率是估出来的敌方角速度 `omega`，与 `gimbal.yaw` 的变化率无关。

**但有一种真正的 1:1 继承，要警惕**：`gimbal.yaw` 读数本身的误差会原样传进 `target_yaw`。观测是拿这个读数换到世界系的，参照系读数偏了 `δ`，整个世界系就跟着偏 `δ`，最后算出的绝对角也偏 `δ`。推导上它是可抵消的：`rel_yaw` 用同一个 `δ` 转出去又转回来，误差在 `rel_yaw` 里被抵掉，于是剩下的就是 `target_yaw = θg + rel_yaw` 里那个多出来的 `δ`。**这条是纯代数推论，没有单独实测。** 结论是**对 `message.yaw` 的口径依赖是硬的**，不是「随便给个数都行」。这正是问题清单 1.7 那条要问清楚的（机械角还是 IMU 融合的场地角）。

开火门（:779-784）：

```cpp
const bool aligned =
    std::fabs(rel_yaw) < config_.fire_yaw_tolerance_rad &&                       // 0.02 rad = 1.15 度
    std::fabs(command_pitch - gimbal_pitch) < config_.fire_pitch_tolerance_rad;  // 同上
const bool spin_ok = std::fabs(x_[YawRate]) < config_.fire_spin_tolerance_rad_s; // 1.0 rad/s
result.fire_allowed = status_ == TrackingState::Stable && aligned && spin_ok;
```

**拆开看三个条件**：

| 条件 | 门槛 | 意思 |
|---|---|---|
| `aligned` 的 yaw 项 | 1.15 度 | 炮口已经横向对准 |
| `aligned` 的 pitch 项 | 1.15 度 | 炮口已经抬到发射仰角 |
| `spin_ok` | 1.0 rad/s | 目标转得不太快 |
| `status_ == Stable` | | 状态机放行 |

**仰角那项的写法本身是个坑**。yaw 的指令是 `gimbal_yaw + rel_yaw`，误差就是 `rel_yaw`；pitch 的指令是 `command_pitch`，一个绝对角，误差是 `command_pitch - gimbal_pitch`。**两者口径必须一致。**

**如果照抄 yaw 的写法写成 `|rel_pitch| < 容差`，那门会在 5 m 处早开 2.44 度**（因为 `command_pitch` 比几何角高 2.44 度），**落点低约 21 cm**。这是 2026-10-16 和 `beta` 一起改掉的第二处。

最后一道（:786-788）：

```cpp
if (!predictionIsFinite(result)) return PredictionResult{};
```

**`predictionIsFinite`**（`:88-101`）逐字段查，而且**米转毫米还要再乘一次 1000**（`AppSupport.cpp:87-88`），所以连 `center_x_m * 1000.0F` 也要查。任何一个非有限直接返回全零，框架收到 `state == NoTarget` 就降级成安全帧。**宁可这一帧不开火，也不能把 NaN 发到串口。**

# 十三、适配器与 `main.cpp` 的接线

**一句话**：`ekf_predict` 是个薄适配器，只负责跨帧状态、`dt` 和检测耗时，别的都交给 `ArmorEkf`。

## 13.1 `StudentTasks.cpp:190-216`

```cpp
static ArmorEkf filter;
static double last_timestamp = 0.0;

const double dt = (last_timestamp > 0.0 && std::isfinite(timestamp_seconds))
                      ? std::clamp(timestamp_seconds - last_timestamp, 0.0, 0.5) : 0.0;
if (std::isfinite(timestamp_seconds)) last_timestamp = timestamp_seconds;     // 别把 NaN 写进 static
const double now_seconds = ...steady_clock::now()...;
const double latency_s = std::clamp(now_seconds - timestamp_seconds, 0.0, 0.2);

filter.predict(dt);
for (const ArmorPose& observation : observations) {
    filter.update(observation, static_cast<double>(gimbal.yaw));
}
filter.advanceStateMachine(timestamp_seconds);
return filter.buildPrediction(gimbal, latency_s);
```

**拆开看，适配器只做四件事**：

| 做什么 | 为什么 |
|---|---|
| 跨帧状态放函数内 `static` | `main.cpp` 的操作线程是唯一调用者，没有并发 |
| 算 `dt` 并截在 `[0, 0.5]` | 防时间戳跳变 |
| 算 `latency_s` 并截在 `[0, 0.2]` | 防检测耗时异常 |
| 按四步调用 | 就是第三节那个入口约定 |

`ArmorEkf` 本身可以独立构造，所以单测直接测类，不走这个适配器。

**`:200` 那行注意一下**：**时间戳非有限时不要把 NaN 写进 `static`**，否则后面每一帧的 `dt` 都是 NaN。

## 13.2 `main.cpp:459-482`

```cpp
const double time_stamp = ...frame_time.time_since_epoch()...count();
translator.message.latency = ...(frame_time - process_start) 毫秒...;

const PredictionResult prediction = ekf_predict(observations, gimbal, time_stamp);
bool prediction_valid = applyPrediction(translator, prediction);

```

**一句话**：调用 EKF、把结果写进串口帧、顺手打曲线；降级时用安全帧覆盖。

## 17.1 会卡住 `Stable` 的

**慢转时卡住的是 yaw 闸，不是半径闸**。`omega = 0.6 rad/s` 时中心误差只有 0.06 cm，瞄准几何完全正确，`fire_allowed` 仍然是假。门槛约在 `omega = 0.8 rad/s`。逐档实测表见深版 12.6.3。

**这条闸是几何墙还是调参**：`omega > 0` 是调参问题，扫 `angular_accel_noise_rad_s2` 就能进门；`omega = 0` 是几何问题，怎么降都不收敛。定论见深版 12.6.4。

**`covarianceIsStable()` 是单向门**：`Stable` 可以和远超门槛的协方差共存，深版 12.6.5 有实例。是刻意留的滞回还是漏了回退闸，需要定。

**只看得到一块板时另一个半径拿不到观测**：一条观测只修得动一个奇偶的半径（`H.col(radiusIndex(i))` 是唯一非零的半径列）。目标在转时两个半径都会陆续拿到观测，只有 `omega = 0` 时另一个半径报的是先验。深版 12.6.2 有表。

**待定项**：整状态协方差闸换成「瞄准点自身的不确定度闸」。真正决定打不打的是瞄准点的不确定度，不是车体 yaw 的不确定度。未改，见深版 12.6.6。

## 17.2 已知欠账

- **`ekf_nis_mean` 打不出去**：`recentNisMean()` 是 private 且没有公开访问器。要看 NIS 曲线得先加 getter。
- **切换与遮挡的证据键漏不出来**：现在靠 `ekf_aim_index` 和 `ekf_streak` 间接看，没有直接的「这块板刚从视野消失」的量。
- **`plate_height_m` 默认全零**，对标准步兵是错的。代价只在 `center_z_m` 和两块板同框那几帧，不影响瞄准。
- ~~74.1 mm 枪口偏移~~ **2026-10-16 已接上**，`solveBallistics` 的输入改从枪口量起，做法与理由见 12「为什么弹道输入要先换到云台系再减枪口」。
- **`gimbalToWorld` 只去 yaw、不去 pitch 也不去 roll，「世界系」其实是炮管系**：`gimbal.pitch` 与 `gimbal.roll` 都没进过这个变换。云台俯仰时整个 W 跟着转，静止目标在 W 里的坐标会变，`center_z_m` 与 `vx / vy / vz` 会吃到这段视在运动，**仰角指令还会多带一份 `φ̇ · t_pred` 的提前量**（5 m、30 度每秒、`t_pred` 0.22 s 时 6.6 度，容差是 1.15 度）。改法是串 `Ry(gimbal.pitch) · Rx(gimbal.roll)`，只动这一个函数，未做；**要在上车扫 Q/R 之前决定，扫完再改等于重扫**。另见 1.7「云台抬头了会怎样」，roll 那一档也在那里。
- **相机光轴与炮管平行性未知**。
- **`gimbal.yaw` 符号未上车确认**：右正只是默认，翻转只有一处。
- **弹速 24 m/s 是默认值**：来自 `armor/src/BulletModel.cpp:5` 的构造函数，没人选过。同仓库还有 `Planner.hpp:47` 的 23.5 与 `Planner.cpp` 的 23.0。
- **EKF 之前没有目标筛选层**：链路里「数字识别与目标筛选」是识别阶段的一环，现在一帧里所有同色板全喂进同一个「单目标四板」模型。问题清单 §2.7b，未答。
- **`config/camera.yaml` 的外参 `t` 仍是 `(0.06711, 0, 0.0515)`**，按 handout 的轴序推导应是 `(0, -0.0515, 0.06711)`。红线相关，故意没动。
- **慢转 0.052 m 稳态残差**。
- **`7guard` 真值未闭环**。
