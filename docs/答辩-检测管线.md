## 1.1 为什么要加三个「参数结构体」而不是把数字写在函数里

现场调试时最怕的是：十几个阈值散在代码各处，改完不知道是哪一个起了作用。
所以把它们**按"负责哪一级"分组**，每组一个结构体：

| 结构体 | 管哪一级 | 里面的数是什么量纲 |
|---|---|---|
| `MaskParams` | 颜色掩膜 | **绝对灰度值**（0~255） |
| `BarParams` | 灯条提取 | **像素**（面积、长度） |
| `PairCriteria` | 灯条配对 | **比值 / 角度**（无量纲） |
| `PatchParams` | 数字补丁裁剪 | 毫米 + 像素密度 |
| `DetectParams` | 把上面四个**打包**，外加两个总参数 | — |

**这个分组有一条很实用的推论，答辩时能直接用**：

- `PairCriteria` 里全是比值，**换分辨率一个都不用改**；
- `BarParams` 里全是像素，**换分辨率必须按比例重调**。

（海康整图的分辨率比 640×480 的笔记本摄像头高得多，两者**不能共用同一组 `BarParams`**。
答辩被问"参数怎么适配不同相机"时，这句话就是答案。）

# 二、这次新用到的语法（只列以前没出现过的）

前面那 14 条（`#include`/`namespace`/`struct`/`const&`/`static_cast`/`assert`…）
在 `docs/答辩问答.md` 第二部分，这里不重复。以下是本文档里**第一次出现**的：

## 2.1 `cv::Scalar` —— 一个"颜色/四元组"

```cpp
const cv::Scalar kBlueBar(254.0, 245.0, 74.0);   // 测试文件里
cv::Mat image(240, 320, CV_8UC3, kBackground);   // 造一张填充该颜色的图
```
`cv::Scalar` 就是个能装 4 个 `double` 的小盒子。画图、填色时用它表示颜色。
**顺序还是 B、G、R**（和 `cv::Mat` 一致），不是 RGB。
（上面那三个数是**海康整图上实测到的灯条像素值**，不是"理想的红 (0,0,255)"。）

## 2.2 `.at<unsigned char>(行, 列)` —— 取一个像素

```cpp
assert(blue_mask.at<unsigned char>(100, 100) == 255);
```
`<>` 里是"这个位置存的是什么类型"。掩膜是 `CV_8UC1`，存的就是 0~255 的整数
（C++ 里叫 `unsigned char`，意思是"无符号的字符"，其实就是 1 字节）。
**注意参数顺序是 (行, 列) 也就是 (y, x)，不是 (x, y)** —— 写反了不报错，只是取到别处的像素。

## 2.3 lambda —— 写在用它的地方的临时函数

```cpp
std::sort(order.begin(), order.end(),
          [&boxes](std::size_t a, std::size_t b) {
              return boxes[a].area() > boxes[b].area();
          });
```
读法：`std::sort` 需要知道"怎么算谁大"。第三个参数就是回答这个的一小段函数。
- `[&boxes]` 叫**捕获列表**，意思是"这段小函数里要用到外面的 `boxes`"。
  `&` 表示按引用用（不复制）。
- `(std::size_t a, std::size_t b)` 是它收的两个参数。
- 返回 `true` 表示"a 应该排在 b 前面"。

## 2.4 `cv::Rect` 的 `&` 是求交集

```cpp
const float intersection = (a & b).area();
```
`&` 平时是按位与，但对 `cv::Rect` 它被重载成了**求两个矩形的重叠区域**。
不重叠时得到一个空矩形，`.area()` 是 0 —— 所以后面不用特判。

## 2.5 `std::vector<bool>` —— 一排"是/否"

```cpp
std::vector<bool> suppressed(detections.size(), false);
```
第二个参数 `false` 是"初始全填 false"。
用法和普通数组一样：`suppressed[i] = true;`。

## 2.6 `emplace_back` 与 `push_back` 的区别

```cpp
pairs.emplace_back(a, b);   // 直接用 a、b 在末尾"就地造"一个 pair
bars.push_back(bar);        // 把一个已经造好的 bar 复制/搬进去
```
功能上等价，`emplace_back` 少一次拷贝。写哪个都对，风格问题。

# 三、逐行讲解

## 3.1 `buildColorMask`（`ArmorDetector.cpp:314-350`）—— ① 颜色掩膜

**作用**：给一张**三通道 BGR** 彩图 + 本队颜色，还回一张**黑白掩膜**（255 = 这里像本队灯条）。

### 第 316-322 行：先拒绝，不猜

```cpp
if (bgr.empty() || bgr.type() != CV_8UC3) {
    return cv::Mat();
}
```
`CV_8UC3` 读作"8 位无符号、3 通道" = 普通彩图。

**为什么直接返回空，而不是"如果是灰度图就当成三个通道一样"？**
灰度图**没有颜色信息**，任何"猜一个通道顺序"的做法都不会报错，
只会让整条管线安静地全错。**明确拒绝比默默猜错好查一百倍** —— 这是本次贯穿全篇的一个设计原则。

`return cv::Mat();` 是造一个空矩阵当"我做不到"的信号。

> **四通道（BGRA）故意不在这里处理。** 归一化只在**一处**做 ——
> `detectArmors` 的入口（`ArmorDetector.cpp:504-515`），那里转一次，
> 后面每一级就都只面对三通道。理由见 4.12。

### 第 324-325 行：把三个通道拆开

```cpp
cv::Mat channels[3];
cv::split(bgr_only, channels);  // 0 = B，1 = G，2 = R
```
一张 BGR 彩图其实是三张单色图叠在一起。`split` 把它们拆成三个独立矩阵：
`channels[0]` 全是蓝的值，`[1]` 绿，`[2]` 红。
**顺序是 B、G、R**，不是 R、G、B —— 记反了不报错，只是颜色全乱。

### 第 327-329 行：按队伍选主/副通道

```cpp
const bool is_blue = (team == TeamColor::Blue);
const cv::Mat& main  = is_blue ? channels[0] : channels[2];
const cv::Mat& other = is_blue ? channels[2] : channels[0];
```
`条件 ? 甲 : 乙` 是三目运算符："成立取甲，否则取乙"。
蓝队：`main` = 蓝通道，`other` = 红通道。红队反过来。

### 第 336-337 行：**本函数唯一的坑**

```cpp
cv::Mat diff;
cv::subtract(main, other, diff);
```
`cv::subtract` 是逐像素相减。对 8 位无符号图它是**饱和**的：
像素只能是 0~255，算出来是负数就**截成 0**。所以蓝队这里等价于 `max(B-R, 0)` ——
蓝像素留一个大正数，红像素变成 0。

> ### 换成 `cv::absdiff` 会怎样？（必答）
>
> `absdiff` 求的是 `|B-R|`。红灯条 `|42-254| = 212`，蓝灯条 `|254-74| = 180` ——
> **两边都成了大数**。
> 后果：红队和蓝队看到**一模一样**的结果，**对面队伍的车全都变成目标**。
> 而且**一个错误都不报**，检测看起来还特别"灵"。
>
> 这就是为什么测试里专门有一对断言钉死它（见 `test_armor_pipeline.cpp:73-74`）：
> 同一张图里同时画一根蓝灯条和一根红灯条，**蓝队掩膜必须"认蓝、不认红"**。
> 少任何一条断言都抓不到这个 bug。

### 第 339-342 行：两条门槛

```cpp
cv::Mat strong;  // 通道差够大
cv::Mat bright;  // 主通道本身够亮
cv::threshold(diff, strong, params.min_channel_diff, 255.0, cv::THRESH_BINARY);
cv::threshold(main, bright, params.min_channel_value, 255.0, cv::THRESH_BINARY);
```
`cv::threshold(输入, 输出, 门槛, 最大值, 模式)` 做**二值化**：
逐像素问"你大于门槛吗"，大于变 255（白），否则变 0（黑）。

- `min_channel_diff = 60`：差值要够大。灯条是纯色的，蓝比红高一大截；背景的灰、白、黑蓝红差不多。
- `min_channel_value = 100`：**主通道自己还要够亮**。一个 `B=80,R=10` 的暗蓝像素差值 70 也合格，
  但它多半是阴影不是灯条，靠这条踢掉。

### 第 347-349 行：两条判据求交

```cpp
cv::Mat mask;
cv::bitwise_and(strong, bright, mask);
```
`bitwise_and` 按位与。对黑白图来说效果就是"**两张图都是白的地方才留白**"。
只用差值会漏进暗蓝；只用亮度偏色高光会漏进来；两个都要才干净。

### 阈值 60 / 100 是怎么定的（必答）

从海康那 69 张整图上**量出来**的，不是拍的：

| 量 | 实测值 |
|---|---|
| `\|B-R\| < 20` 的像素占比 | **99.78%**（背景、场地、地板全在这里） |
| `\|B-R\| ≥ 120` 的像素占比 | **0.13%**（灯条本体） |
| `>60 且主通道 >100` 之后，一帧剩下的斑块数 | **0 ~ 40 个** |

60 落在"背景极密、灯条极疏"中间那段空档里，两边各有近 5 倍余量。
**这一点对现场调参很重要**：在 60 附近挪动不会突然崩。

## 3.2 `extractLightBars`（`ArmorDetector.cpp:356-422`）—— ② 灯条提取

**作用**：从掩膜里挑出那些"细长的白块"，每块转成一个 `LightBar`（记着上下两个端点）。

**先认一个词：轮廓（contour）** —— 把一片连通白区域的外沿描一圈，得到一串点。
`findContours` 就是干这个的。

### 第 363-368 行：找轮廓

```cpp
std::vector<std::vector<cv::Point>> contours;
cv::findContours(mask, contours, cv::RETR_EXTERNAL, cv::CHAIN_APPROX_SIMPLE);
```
`contours` 是一个"装着很多条轮廓"的容器，所以类型是两层 `vector`。

- `RETR_EXTERNAL` = **只要最外面那一圈**。
- **为什么必须用它（必答）**：灯条过曝时中间会烧成纯白、边缘反而稍暗。
  用 `RETR_LIST` / `RETR_TREE` 会把**同一根灯条拆成里外两三个轮廓**，
  每一圈都被当成独立灯条去配对，于是同一块板配出一堆假目标 ——
  而且看起来"检测很灵"，最难发现。
- `CHAIN_APPROX_SIMPLE` = 直边上只留拐点，省内存。

### 第 371-374 行：面积太小直接扔

```cpp
for (const std::vector<cv::Point>& contour : contours) {
    if (cv::contourArea(contour) < params.min_area) {
        continue;
    }
```
`for (X : Y)` 是"把 Y 里的每一项依次取出来叫 X"。`continue` = 这一项不要了，看下一项。

### 第 376-388 行：求最小外接旋转矩形，再分长短边

```cpp
const cv::RotatedRect rect = cv::minAreaRect(contour);

cv::Point2f pts[4];
rect.points(pts);
const float edge0 = static_cast<float>(cv::norm(pts[1] - pts[0]));
const float edge1 = static_cast<float>(cv::norm(pts[2] - pts[1]));
const bool edge0_is_short = edge0 <= edge1;
const float short_side = edge0_is_short ? edge0 : edge1;
const float long_side  = edge0_is_short ? edge1 : edge0;
```
`minAreaRect` 找一个**刚好套住轮廓、可以旋转的矩形**。
为什么不用正着的矩形？因为车开过来时板子是斜的，正着的矩形会把斜灯条框成一大块。

> ### 为什么不直接用 `rect.angle`？（必答）
>
> OpenCV 4.5 起，`RotatedRect::angle` 的**取值范围和符号语义都改过**
> （3.x 是 `[-90,0)`，4.5 是 `[0,90)`）。靠它判断"哪条边是长边"会随版本变，
> 今天对明天可能就错。
> **直接比两条边的长度没有任何歧义，永远对。** 多写两行换一个不随版本漂移的判据，值。

### 第 394-400 行：三道形状检查

```cpp
if (short_side <= 0.0F || long_side < params.min_long_side) {
    continue;
}
const float aspect = long_side / short_side;
if (aspect < params.min_aspect || aspect > params.max_aspect) {
    continue;
}
```
`aspect` = 长边/短边。**`min_aspect = 1.5` 这条最重要**：
场地上的正方形白色标记面积和长度都合格，**唯一能挡住它们的就是这一条**。

> ### `min_long_side` 比的是"长边"，不是"竖直高度"（必答）
>
> 这个字段原来叫 `min_height`，名字暗示"画面里的竖直高度"，**已经误导过一次讨论**
> ——实际上它比的是**旋转矩形的长边**，也就是灯条自己的长度。斜着的灯条
> 竖直跨度可以远小于它的长度，两者不是一回事。
> 已改名为 `min_long_side`，并加了测试钉住语义（造一根斜 60° 的灯条：
> 长边 30 合格、竖直跨度只有 22 不合格，实现若按竖直高度过滤就会红）。
>
> **它是三个门槛里唯一决定"最远能看多远"的那个**（详见 4.13）。

门槛的来源（同一批 69 帧实测）：

| 量 | 分布 |
|---|---|
| 长边/短边 | p5 = 1.79，p25 = 2.64，p50 = 3.53，p90 = 6.25，max = 16.0 |
| 面积 | p10 = 83，p50 = 364 |
| **长边** | min = 9.3，p1 = 25.7，p5 = 27.6，p50 = 53.2，max = 115.5 |

也就是说 69 帧里**只有 1 个斑块不满足 1.5** —— 所以这条下限几乎不会误杀真灯条。

**长边那一行要单独看**：69 帧里只有 36 帧真的有板子，过门槛的灯条最短 **24.7**、
最长 115.5（最近），**距离跨度约 4.7 倍**。
门槛取 **20**：最短那根 24.7 离它还有 4.7 像素（约 24%）的余量。
门槛若留在 25，这根 24.7 的**真灯条就会被丢掉**（差 0.3 像素）——
这批照片正好拍在门槛边上。**为什么是 20 而不是更低，见 4.13。**
详见 4.13。

### 第 405-418 行：定灯条的两端

```cpp
LightBar bar;
if (edge0_is_short) {
    bar.top    = (pts[0] + pts[1]) * 0.5F;
    bar.bottom = (pts[2] + pts[3]) * 0.5F;
} else {
    bar.top    = (pts[1] + pts[2]) * 0.5F;
    bar.bottom = (pts[3] + pts[0]) * 0.5F;
}
if (bar.top.y > bar.bottom.y) {
    std::swap(bar.top, bar.bottom);
}
```
灯条的"两端"就是两条**短边**的中点。矩形四点是按顺序绕一圈的，
所以短边要么是 (0,1) 和 (2,3)，要么是 (1,2) 和 (3,0) —— 由上面比出来的结果选一组。
`(pts[0] + pts[1]) * 0.5F` 是求两点中点。

**最后那个 `swap` 不能省**：图像坐标 y 向下增长（左上角是 (0,0)），
所以 y 小的在上面。`minAreaRect` 给的点序跟朝向有关，**不保证哪一头在上面**；
而 `tiltDegrees()` 的正负号全押在"top 在上"这个约定上 ——
有一半灯条头尾反了的话，倾角符号就随机翻转，配对判据 3（倾角接近）直接失效。

## 3.3 `pairLightBars` 的**判据 5**（`ArmorDetector.cpp:157-187`）—— 本次新加的

前四条判据（等长 / 竖直对齐 / 倾角接近 / 间距比合理）是上次做的，这里只讲新加的。

```cpp
const float pair_top    = std::min(a.top.y, b.top.y);
const float pair_bottom = std::max(a.bottom.y, b.bottom.y);
const float x_lo = std::min(a.center().x, b.center().x);
const float x_hi = std::max(a.center().x, b.center().x);
bool has_bar_inside = false;
for (std::size_t k = 0; k < count && !has_bar_inside; ++k) {
    if (k == i || k == j) { continue; }
    const cv::Point2f c = bars[k].center();
    if (c.x <= x_lo || c.x >= x_hi) { continue; }        // 横向不在这一对中间
    if (c.y <= pair_top || c.y >= pair_bottom) { continue; }  // 纵向错开
    has_bar_inside = true;
}
if (has_bar_inside) { continue; }
```

逐句读：

1. 先算出这一对**左右横跨的范围** `[x_lo, x_hi]` 和**纵向共同覆盖的高度带** `[pair_top, pair_bottom]`。
2. 遍历其它所有灯条：如果哪一根的中心**既**在横向区间内、**又**在高度带里，就标记 `has_bar_inside`。
   `&& !has_bar_inside` 是提前退出，找到一根就不用再找。
3. 有夹着的 → 这一对扔掉。

**判据本身与真实帧无关**：真实装甲板中间不会竖着第三根灯条。

**纵向只在共同高度带内判**，是为了避免把背景里**远处、纵向错开**的目标误当成"夹在中间"。

### 为什么要加这一条（本次最有价值的产出）

在实测帧 `20261008231729930` 上，4 根灯条在 x = 263 / 514 / 721 / 909：

| 配对 | 间距比 | 面积 | 结果（修之前） |
|---|---|---|---|
| (514, 721) | 2.53 | 16960 | 保留 |
| **(514, 909)** | **5.05** | **30072 ← 最大** | **保留（错的就是它）** |
| (721, 909) | 2.46 | 13803 | 被 NMS 合并 |

`(514, 909)` 这一对**中间夹着 x=721 的灯条**，间距比 5.05 落在合法区间 `[1.2, 6.0]` 里，
**前四条判据全过**。而它的外接矩形最大，**NMS 按面积取大，正好把它留下来** ——
于是中央裁剪框落到了中间那根灯条上，抠出来的"数字补丁"其实是**灯条本身**。

**修法的效果**：这一帧现在正确报出 2 块板，跨板的大框消失了。

## 3.4 `boundsOf` / `intersectionOverUnion` / `suppressOverlaps`（`:425-498`）—— ⑦ 去重

**为什么需要去重**：3 根灯条排一排时，"左+中"和"中+右"能配成两块板，它们互相重叠。
不合并的话同一块板报两次，下游 EKF 会当成两个目标去追。

**什么是 IoU**：两个矩形重叠的程度 = `交集面积 ÷ 并集面积`。完全重合是 1.0，不沾边是 0。

### 第 438-441 行：求外接矩形

```cpp
cv::Rect2f boundsOf(const std::array<cv::Point2f, 4>& corners) {
    return cv::boundingRect(std::vector<cv::Point2f>(corners.begin(), corners.end()));
}
```
> ### `cv::boundingRect` 对**点集**有个反直觉的约定（容易被追问）
>
> 宽 = `x_max - x_min + 1`，高 = `y_max - y_min + 1` —— **含两端**。
> 所以四点跨 200 像素时给出的宽是 **201**，不是笔误。
> 后果：这里的 IoU 会比"按坐标区间手算"略大一点点。
> **实测**：201×61 与 101×61 的重叠算出来是 **0.5025**，不是 0.5（`101/201`）。
> 对 NMS 这种只看相对大小的判据没影响，但对账时要记得这件事。

### 第 443-447 行：IoU

```cpp
float intersectionOverUnion(const cv::Rect2f& a, const cv::Rect2f& b) {
    const float intersection = (a & b).area();      // Rect 的 & 就是求交
    const float total = a.area() + b.area() - intersection;
    return total > 0.0F ? intersection / total : 0.0F;
}
```
`total` 就是并集面积（两块加一起，重叠部分数了两遍，减掉一次）。
最后那个三元运算符是防零除。

### 第 464-477 行：按面积从大到小排

```cpp
std::vector<std::size_t> order(detections.size());
for (std::size_t i = 0; i < order.size(); ++i) { order[i] = i; }
std::sort(order.begin(), order.end(),
          [&boxes](std::size_t a, std::size_t b) {
              return boxes[a].area() > boxes[b].area();
          });
```
排的是**下标**（0,1,2,...），不是数据本身 —— 这样后面还要按下标去查 `boxes` 和 `suppressed`。
`>` 表示降序（大的在前）。

> ### 为什么按面积排，不按置信度？（必答）
>
> 这是本函数**最关键的设计决定**。
>
> 置信度回答的是"**有多确定这是某个数字**"，**不是**"这是不是一块真板"。
> 板子上什么都没写的时候，分类器会很有把握地报"9neg（无数字）"，**置信度一样可以很高**。
> 而面积大同时说明**离得近、像素多、数字更好读**，是更强的"这是个真目标"的证据。
>
> 换句话说：按置信度排序，等于让"分类器对自己的判断有多自信"来决定"这块板存不存在" ——
> 这是把两个不同的问题混在一起了。

### 第 479-496 行：贪心保留

```cpp
std::vector<bool> suppressed(detections.size(), false);
for (std::size_t i = 0; i < order.size(); ++i) {
    const std::size_t candidate = order[i];
    if (suppressed[candidate]) { continue; }        // 已经被更大的框吃掉了
    kept.push_back(detections[candidate]);          // 留下它
    for (std::size_t j = i + 1; j < order.size(); ++j) {
        const std::size_t other = order[j];
        if (suppressed[other]) { continue; }
        if (intersectionOverUnion(boxes[candidate], boxes[other]) > iou_threshold) {
            suppressed[other] = true;               // 和它重叠太多，划掉
        }
    }
}
```
从最大的开始，留下它，然后把和它重叠超过 `nms_iou = 0.3` 的都划掉。
**全程没用置信度**，纯粹按面积和重叠。

# 四、答辩问答

## 4.1 「为什么不直接用 `cv::absdiff` 求通道差？」

因为 `absdiff` 求的是 `|B-R|`，**红蓝两队看到一样多的目标**，对面队伍的车全变成目标，
而且**不报任何错**。`cv::subtract` 对 8 位无符号图是**饱和**减法（负数截成 0），
蓝队得到 `max(B-R, 0)`，红队得到 `max(R-B, 0)` —— 正是"只留本队颜色"。
测试里用"一张图里同时画蓝、红两根灯条"来钉死它。

## 4.2 「阈值 60 / 100 是怎么定的？为什么不是 80 或者 40？」

从海康 69 张整图上量的：`|B-R| < 20` 占 99.78%（背景），`|B-R| ≥ 120` 占 0.13%（灯条）。
60 落在这两段之间，**两边各有近 5 倍余量** —— 所以现场在 60 附近挪动不会突然崩。
这一点比"60 这个数本身"重要：**要能被问"如果光照变了怎么办"时有话答。**

## 4.3 「为什么 `findContours` 用 `RETR_EXTERNAL`？」

灯条过曝时中间是纯白、边缘偏暗。用 `RETR_LIST`/`RETR_TREE` 会把同一根灯条
拆成里外两三个轮廓，每一圈都被当成独立灯条去配对 → 同一块板配出一堆假目标。
**而且它看起来"检测很灵"，最难发现。** 只用最外层轮廓，一根灯条就是一个轮廓。

## 4.4 「为什么不用 `cv::RotatedRect::angle` 判断哪条边是长边？」

OpenCV 4.5 起 `angle` 的取值区间和符号语义都改过（3.x 是 `[-90,0)`，4.5 是 `[0,90)`）。
**直接比较两条边的长度没有任何歧义，永远对。** 多写两行换一个不随版本漂移的判据。

## 4.5 「NMS 为什么按面积排序，不按置信度？」

置信度回答的是"有多确定这是某个数字"，**不是**"这是不是一块真板"。
板子上没有数字时分类器会很有把握地报"9neg"，**置信度一样高**。
面积大则说明离得近、像素多、数字更好读，是更强的"这是真目标"的证据。
按置信度排序等于让"分类器有多自信"决定"这块板存不存在"。

## 4.6 「`cv::boundingRect` 算出来的宽怎么比手算多 1？」

它对**点集**用的是**含两端**的约定：宽 = `x_max - x_min + 1`。
所以四点跨 200 像素时宽是 201。实测 201×61 与 101×61 的 IoU = **0.5025**（= 101/201），
不是 0.5。对 NMS 这种只看相对大小的判据没影响，但对账时会差一点点。

## 4.7 「判据 5 会不会误杀真目标？」（**这条要诚实答**）

风险是存在的：如果两根真灯条之间**恰好**有一根噪声通过了全部形状门槛
（面积 ≥ 30、长宽比 ≥ 1.5、长边 ≥ 20）并且纵向落在共同高度带里，那一对就被误拒。

但判据的取向是**故意偏保守**的：
- 只在那根第三灯条的中心**严格落在**两根之间时才拒（`<=` / `>=` 都算"在外面"）；
- 纵向还要求它落在两根的**共同高度带**内，背景里纵向错开的目标不会误伤；
- 而它换来的收益很实在 —— 修之前那一帧报出的"数字补丁"**其实是灯条本身**，
  也就是说误拒的代价是"可能少一块板"，误留的代价是"报一块位置完全错的板还带个假编号"。
  **后者严重得多。**

> 这条判据**没有单独量化过误拒率**（69 帧里没有真实并排双车同时出现的场景）。
> 如果老师追问，就照实说：这是基于"真板中间不会有第三根灯条"这个物理事实的判据，
> 收益是杀掉跨板假配对，代价是理论上可能误拒，需要在有双车并排的场地数据后再评估。

## 4.8 「`detectArmors` 里为什么抠补丁失败不 `continue`？」

因为**角点是好的，PnP 还能用**，只是没有可报的目标编号。
丢掉的话，"检测坏了"和"分类坏了"在 Web Debug 上完全分不出来（`armor_count` 都是 0）。
这是评分表「目标丢失处理」要求的行为，也是**可观测性**上的考虑。

## 4.9 「参数换了分辨率要重调吗？」

**要分两类答**：
- `PairCriteria` 全是比值和角度，**与分辨率和距离都无关，一个都不用改**；
- `BarParams` 全是像素，**换分辨率必须按比例重调**。

但**往哪个方向调，这里先前写反了，一并纠正**：`BarParams` 这一组是**按那 69 张海康整图
（1440×1080）定的**，不是按 640×480 定的。依据就写在 `ArmorDetector.hpp:152-176` 的注释里，
而且可复现 —— 门槛从 25 放到 20 只多收的那根真灯条是 **24.7 px**、抬到 30 会让灯条从
**143 掉到 120**。这两个数只有在 1440×1080 上才成立。

同一组参数（`DetectParams` 全默认）在两个分辨率上实跑，也印证这一点
（蓝方，69 帧；640×480 是把整图缩下去的）：

| 分辨率 | 灯条 | 检出的板子 | 有检测的帧 |
|---|---:|---:|---:|
| **1440×1080（海康，即定标分辨率）** | **143** | **38** | **29 / 69** |
| 640×480（缩图） | 71 | 16 | 14 / 69 |

所以正确的说法是：

- **换到海康 1440×1080：`BarParams` 一个都不用动** —— 它本来就是海康域的；
- **反过来，退回 640×480 才要按比例缩小**。照先前那句"往海康方向放大"（20 → 45）做，
  会把上面那批 24.7 px 的最远真灯条**全部杀掉**，最远探测距离直接腰斩。

`min_quad_area_px`（长度²量纲）同理不用动：它是**防退化的地板**、不是调参旋钮，
1440×1080 下真实装甲板的四边形面积远在 100 之上，这道门几乎不参与筛选。

（`PairCriteria` 那组仍然一个都不用动。）

## 4.10 「你怎么知道这些测试是有效的？」

沿用上次的做法做**变异测试**：把实现改坏，看测试是否变红。

| 变异 | 应该让谁变红 |
|---|---|
| `subtract` → `absdiff` | `test_armor_pipeline.cpp:73-74`（认蓝不认红） |
| 删掉 `min_aspect` 判据 | 正方形亮块那条断言（`:195-200`） |
| `suppressed` 改成按输入顺序取 | "故意把小的放前面"那条（`:238-248`） |
| 删掉判据 5 | 跨板配对那段（`:288-325`） |
| 让 `buildColorMask` 重新"接受" BGRA（自己猜通道顺序） | 那条"BGRA 必须返回空掩膜"的断言（`:105-124`） |

**每一条都能被抓住** —— 这比"测试全绿"更有说服力。

## 4.11 「本次踩的最大的坑是什么？」（这题答好了是加分项）

看第五部分。一句话版：**四条几何判据各自都对，但它们都是"局部"判据 ——
只看两根灯条的关系，看不出"这两根其实隔了很远"**；
而 NMS 按面积取大，**在假配对恰好最大时会把真的挤掉**。

## 4.12 「四通道为什么只在入口归一化一次？」

**因为"归一化通道格式"是一件只该做一次的事。** 分散到各级去做，多做一处的代价不是多一份代码，而是**多一处漏掉的可能**。

具体到这份代码：

- `get_pic`（`StudentTasks.cpp:81-91`）已经在取流时把 3 通道直接透传、4 通道 `BGRA2BGR`、单通道 `GRAY2BGR`。
  也就是说，走到 `detectArmors` 时**实际已经是三通道 BGR 了**。
- 那么 `buildColorMask` / `toGray` 里再各写一份"如果是四通道就转一下"，在真实链路上**永远执行不到**。
  这就是本次删掉的那段死代码。
- 更关键的是：**删掉它不会产生错误的答案，只会产生明确的失败**（返回空掩膜）。
  如果反过来保留着，一旦哪天 `get_pic` 换了、或者有人直接调 `detectArmors` 传灰度图，
  那个"猜通道顺序"的分支就会安静地按错的颜色去算 —— 红蓝反、掩膜全空、一帧都检测不到，
  **而且不报任何错**。

所以现在的规矩是：

| 层 | 负责什么 | 判错时的行为 |
|---|---|---|
| `detectArmors`（入口） | 唯一做归一化的地方：`CV_8UC4` → BGR，`CV_8UC3` 浅拷贝，别的类型直接返回空结果 | 返回空 vector，看得见 |
| `buildColorMask` | 只接受 `CV_8UC3`，别的类型返回空矩阵，**不猜** | 返回空 mask，看得见 |
| `extractDigitPatch` / `toGray` | 只认 `CV_8UC1` / `CV_8UC3`，别的返回 `false` | 返回 false，看得见 |

**一句话**：四通道不是"多余"，是**归一化这个动作放错了位置**。
放在入口，它是一道只走一次的闸；放在每一级，它就是三份各自可能忘记更新的副本。

## 4.13 「`min_long_side` 这个下限在防什么？换成 `min_area` 不行吗？」

**不能用 `min_area` 代替，因为两者管的量纲不同。**

| 门槛 | 量纲 | 决定什么 |
|---|---|---|
| `min_area` | 长度² | 这块亮斑有多大 |
| `min_aspect` | 无量纲比值 | 形状像不像灯条 |
| **`min_long_side`** | **长度** | **端点能不能定准** |

要防的东西是**短到端点定不准的碎块**：遮挡、半过曝、噪点都会让一根灯条只露出一小截。

**为什么长度短就不准**：端点的量化是**1 像素的阶跃**，而 `PairCriteria` 里每个阈值
都是**除以灯条长度**的比值，误差按 `1/长边` 放大。注意下面这张表有两列，别混
（初版文档把"**绝对**误差"当成了百分比，**大了 2.37 倍**，2026-10-09 修正）：

| 长边 | 比值的**绝对**误差 | 比值的**相对**误差 | 倾角误差（最坏） |
|---|---|---|---|
| 50 | 0.047 | **2.0%** | 1.1° |
| 25 | 0.095 | **4.0%** | 2.3° |
| **20**（现取值） | 0.119 | **5.0%** | 2.9° |
| 10 | 0.237 | **10%** | 5.7° |
| 5 | 0.474 | **20%** | 11.4° |

（绝对误差 = 比值 2.37 × 1/长边；相对误差 = 1/长边。判据预算：倾角差 15°。）

**这张表的上半段是实测的。** 把同一根灯条整体平移**半个像素**（线性插值，边缘变
过渡带），量出来的长边直接跳 1 像素；0.75 像素处两端一起跳、长度又回到标称值
—— 是台阶不是斜坡：

| 标称长边 | 位移 0 / 0.25 px | 位移 0.5 px | 位移 0.75 px | 间距比 | 相对误差 |
|---|---|---|---|---|---|
| 22 | 22.00 | **23.00** | 22.00 | 2.500 → 2.391 | **4.3%** |
| 16 | 16.00 | **17.00** | 16.00 | 2.500 → 2.353 | **5.9%** |
| 11 | 11.00 | **12.00** | 11.00 | 2.545 → 2.333 | **8.3%** |
| 9 | 9.00 | **10.00** | 9.00 | 2.444 → 2.200 | **10.0%** |

和 `1/长边` 吻合。合成实验里两根灯条同步平移、中心距那项误差抵消了，所以上表是
**偏乐观的下界**；真机上中心距也带误差，最坏合计 `~1.4/长边`。

**长边掉到 9 附近，先坏的哪一条**：不是大小分类（小板 2.37 要翻过 3.0 需要 27%
的误差，得短到 ~4 px 才会发生），而是**判据 3（倾角差）** —— 两根灯条各带一份
误差，最坏 ~12°，而预算只有 15°。所以**低于 ~12 之后判据就没余量了**。

**门槛取 20 的来由**：比值的相对误差 5%、倾角 2.9°，都只有预算的五分之一上下。
实测这批 69 帧里，从 25 放到 20 只多收一根真灯条（24.7 px 那根）、多 0 个噪点，
最远探测距离往外推 25%。往上抬的代价不对称：抬到 30 直接掉 **23** 根灯条
（143 → 120）—— 最远那批真灯条正好挤在 25.7~27.6 这 2 个像素里。
**再往下也不划算**：低于 12 判据没余量；低于 ~9 时这道门已经低于 `min_area`
隐含的 9.1 px 面积下限，等于撤掉（见 4.14）。

**面积替代不了长度门槛**：一个又细又长的碎块（40×1）面积很小但长度够，角度还是
准的；反过来一个 9×4 的小方块面积够（36）但长度只有 9，端点和角度全都不可信。
**需要一个线性的长度门槛。**（反过来也一样成立 —— 长度门槛也替代不了面积，
两个方向都有实测例，见 4.14。）

**它同时是距离上限。** 长边 ∝ 1/距离，三个门槛里只有这一条与距离线性相关
（`min_aspect` 与距离无关；`min_area` 要长度掉到 10 像素附近才轮到它先卡）。
所以"长边 ≥ 门槛"直接等价于一条**最远距离线**，超出之后不是检测变差，
是**一根灯条都提不出来**。拿到相机内参后可以算成米数：

```
Z_max = f × 0.057 m / 20        ← 0.057 m 是装甲板高 57mm，20 是 min_long_side
```

## 4.14 「那 `min_area` 呢？撤掉它会发生什么？」

**撤掉它，绝对下限会从 20 px 塌到 ~9 px**，而且**配对判据一条都拦不住** —— 原因
和 4.13 第一条同一个：`PairCriteria` 全是比值、尺度无关，两根灯条一起缩小，
所有比值原样不变。

先看它在这批 69 帧上**实际**在做什么（`min_long_side = 20`，逐帧全量扫描）：

| `min_area` | 灯条数 | 配对数 | 检测数 | 有检测的帧 |
|---|---|---|---|---|
| **0**（撤掉） | 146 | 39 | **39** | 29 |
| 15 | 145 | 39 | 39 | 29 |
| **30**（现取值） | **143** | **38** | **38** | **29** |
| 50 | 137 | 35 | 35 | **27** ← 开始割肉 |

掩膜之后全图一共只有 179 个斑块（每帧平均 2.6、最多 8），其中 **34 个面积 < 30**。
把这 34 个逐个过一遍后三级门槛，**只有 1 个**是"只被 `min_area` 挡住"的：

```
Image_20261008231407105.bmp   面积 16.0   长边 29.3   短边 1.8   长宽比 16.04
```

**它是什么**：一根真灯条被**色掩膜切碎之后剩下的白热点**。同一帧的横切面：

| x | B | G | R | B−R | 掩膜 |
|---|---|---|---|---|---|
| 1088 | 21 | 3 | 0 | 21 | — |
| **1089** | 255 | 97 | 16 | **239** | ✓ |
| 1090 | 255 | 223 | 39 | 216 | ✓ |
| **1091** | 137 | 33 | 3 | 134 | ✓ |
| 1092–1098 | ≤ 31 | … | … | ≤ 30 | — |
| **1099** | 255 | 192 | 165 | **90** | ✓ |
| 1100 | 55 | 33 | 6 | 49 | — |

一个约 12 px 宽的灯条，掩膜只留下了 **3 px 的饱和蓝芯**（x=1089–1091，B−R = 239）
和 8 px 外**一个近白像素**（x=1099，B=255 / G=192 / R=165）。那个近白像素能过掩膜
是因为 `B−R` 还有 90 —— **"过曝到发白"并不会让 B−R 掉到 60 以下**（白像素的 B、R
一起抬高，差值取决于相机偏色量）。这是 `min_channel_diff = 60` 的一个边界情形，
答辩被问到时可以主动提。

后果：撤掉 `min_area` 之后那一帧多出 1 个检测（1 → 2），多出来的框是
`(1023, 659) 79×39` —— **右边界正好落在那 1 像素宽的白热点上**。也就是说这个
"装甲板"的右侧两个角点是拿一根 1.8 px 宽的碎渣定出来的。4.13 的表里没有它的位置，
因为那张表假设"端点来自一根完整的灯条"。

**所以两道门槛的分工是**：

| 形状 | 面积 | 长边 | 谁挡得住 |
|---|---|---|---|
| 29.3×1.8 细丝（真灯条的白热点） | 16 ✗ | 29.3 ✓ | **只有 `min_area`** |
| 9.3×4.2 小块 | 39 ✓ | 9.3 ✗ | **只有 `min_long_side`** |

**一句话**：`min_area` 管"粗细"，`min_long_side` 管"长短"，**两道正交、缺一漏一类**。
撤掉 `min_area` 在这批数据上只多出 1 个检测，代价不大；它换来的是"细渣不进配对"
这条保证 —— 而细渣的端点恰恰最不可信。另外它便宜（`contourArea` 就是一遍求和），
放在最前面筛正好。**但它也不能往上抬**：抬到 50 已经掉 2 帧，30 就在真灯条的面积
下限附近了。

# 五、实测数字与踩过的坑

## 5.1 本次修掉的 bug：跨板配对（完整过程）

**现象**：红板帧 `20261008231729930` 上报出 1 个检测，但抠出来的"数字补丁"怎么看都不像数字。

**定位过程**（三步）：
1. **打印出所有能配成的对**，看间距比和面积 —— 发现 `(514, 909)` 面积最大（30072）。
2. **把这块板正射出来看**（四边形拉正、放大 4 倍存成图）—— 一眼看出**框横跨了两块板**，
   中间那根灯条（x=721）正好落在框的正中央。
3. **回头想为什么没被挡住**：间距比 5.05 在合法区间 `[1.2, 6.0]` 内，四条判据全过；
   面积最大 → NMS 留它 → 中央裁剪窗落到中间灯条上。

**修法**：判据 5（中间不许夹着第三根灯条）。

**教训（答辩时可以直接说）**：
- 合成图**测不出这个** —— 因为合成图里根本不会画出"4 根灯条排成一排"这种布置。
- **这就是为什么必须拿真实帧验证**：几何判据全绿不等于结果对。

## 5.2 我在这件事上纠正的**两个错误结论**（诚实记录）

1. 早先说"69 帧里有 29 帧至少产出过一个 7guard 目标" —— **那批输出不能当数**。
   ⚠️ 但**别把这话读成"7guard 是噪声类"**：`7guard` 是数据集里的**真实类别**，
   指的是装甲板上那个**哨兵图标**（同理 `6outpost`/`8base` 也是图标，不是数字 6/8）。
   错的是**这批图** —— 参数没锁死、配对/裁剪窗又错位，抠出来的补丁本身是坏的；
   分类器对一张坏补丁照样会吐一个类别出来。所以"报了 7"**不等于**"板上真有图标"。
   证据：同一帧两块板的补丁肉眼几乎一样，却一个判 7（置信度 0.51）一个判 0（0.53），
   全都挤在 0.50 附近。**0.50 正好等于"最小间隔 = 0"**，就是"这输入不像任何一类"。

2. 后来说"红板帧能稳定判出 6 号，说明曝光够、裁剪规则对" —— **也是错的**。
   那个"干净的高对比白色竖条"**就是被误裁进来的灯条**，不是数字。
   修掉配对 bug 之后，红板一样读不出数字。

> **这两个错误的共同点：把"程序输出了东西"当成了"程序算对了"。**
> 反过来，也正是"去看了一眼补丁长什么样"才发现的 —— 打印中间结果比盯着最终输出有用。

## 5.3 修完之后的全量统计（69 帧）

| 项 | 值 |
|---|---|
| 灯条总数 | 253 根 |
| 检测总数 | 70 个 |
| `target_id` 分布 | `0: 63`，`4: 1`，`7: 6` |
| 有非零 id 的帧 | 只有 7 帧 |
| 置信度 | 绝大多数 0.50 ~ 0.62（**零间隔附近**） |

`0.83 / 0.78` 那几帧是"**全黑板面 → 正确地报无数字**"，属于正确行为。

> 表里那 6 个 `7` 来自**坏裁剪**（见 5.2），**不代表板上真有哨兵图标** ——
> 它们和 63 个 `0` 的区别，只是分类器对两张坏补丁分别给了 0.50 和 0.51。

## 5.4 根因：数字根本没被照亮（这条对后续很重要）

修掉配对 bug、裁剪窗终于落在真正的板面上之后，量中央窗的灰阶：

| 位置 | p50 | p90 | max |
|---|---|---|---|
| 红板 A | **0** | — | **25** |
| 红板 B | — | 21 | 23 |
| 蓝板 | — | 18 | 21 |
| **灯条** | — | — | **213 ~ 234** |

**灯条最亮 213~234，板面最亮只有 21~25，差 9~11 倍。**

要把板面推到中灰（约 120）需要大约 **5 倍光**；当前曝光 5000 µs，5 倍就是 **25 ms** ——
**打运动目标根本不可能**。

> **结论：要加光（补光灯 / 提高环境照度），不是加曝光时间。**
> 这是下一阶段上真车前必须解决的前置条件，也是答辩被问"为什么读不出数字"时的标准答案。

## 5.5 另外两条实测事实（都被写进代码注释了）

1. **板面中央那块图案不是数字。** 量出来是 **81.0mm × 48.0mm**（板宽的 60%、板高的 84%，居中），
   远超中央裁剪窗的 40.7mm；而且**红板 B 与蓝板（不同车、不同队、不同时刻）中央窗相关 0.9657**
   —— 数字因车而异，这块图案每块板都一样 → **是板体结构/反光边界，不是数字**。
   **裁剪窗该多宽，要等一张正常曝光的图才能定。**

2. **剖面相关性**：数据集自类平均相关 **0.87 ~ 0.999**；
   而真实帧抠出来的补丁与任何一类的最高相关**只有 +0.32**
   → 分类器给出的编号**没有任何剖面证据支持**。（这是计划里要求的"机械判据"那一步，已实跑。）
